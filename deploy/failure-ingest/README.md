# Field-failure ingest — VPS puller

Pulls sealed failure-report segments from the Hostinger box that runs
`failure-report.php` (firekeep-site repo), independently re-validates every
line against the same closed vocabulary the collector itself enforces,
aggregates by signature, and POSTs the result to this deployment's Sentinel
as durable events. See
`docs/superpowers/specs/2026-08-22-field-failure-reporting-design.md` ("VPS
ingest") for the design.

Two files, both running directly on the Firekeep VPS host (not in a
container, no venv):

- `pull-failures.sh` — cron entrypoint. Pings the collector, scp's sealed
  `failures.*.log` segments into a local inbox, then hands off to `ingest.py`.
- `ingest.py` — stdlib-only Python. Validates, aggregates, and POSTs.

## Install

```sh
# On the Firekeep VPS host, as the user that runs the compose stack:
sudo mkdir -p /opt/firekeep/failure-ingest
sudo cp deploy/failure-ingest/ingest.py deploy/failure-ingest/pull-failures.sh \
    /opt/firekeep/failure-ingest/
sudo chmod +x /opt/firekeep/failure-ingest/pull-failures.sh

# Cron (every 30 minutes):
crontab -e
# add:
*/30 * * * * FIREKEEP_INTERNAL_KEY="$(...)" /opt/firekeep/failure-ingest/pull-failures.sh >> /var/log/firekeep/failure-ingest.log 2>&1
```

`ingest.py` needs only `python3` (3.9+; stdlib only, no pip install). It is
loaded and driven by `pull-failures.sh`'s final step — it is not meant to be
symlinked into a venv or packaged.

## Where `FIREKEEP_INTERNAL_KEY` comes from

It is not generated by this script. It's whatever internal API key this
deployment's `.env` (or key-management flow — see `deploy/bootstrap-keys.sh`)
has minted for server-to-server calls, sent as `X-API-Key` to Sentinel's
`POST /events`. Source it into the crontab line (as above) or export it from
a root-only file the crontab entry sources first — never commit it, never put
it in `pull-failures.sh` itself.

**If `AUTH_ENABLED=false`** on this Sentinel deployment (the default posture
for a VPS reachable only over the tailnet — see `CLAUDE.md` "VPS reachability
is the tailnet"), the tailnet bind is the actual security boundary and the
`X-API-Key` header is simply ignored by Sentinel. `--api-key-env` can still
point at an unset variable in that case; `ingest.py` sends no header at all
when the variable is empty.

## Durability model

1. `pull-failures.sh` fetches each sealed segment fully via `scp`, verifies
   the byte count matches the remote file, and only then deletes the remote
   copy. A crash between fetch and delete just means a harmless refetch next
   run.
2. `ingest.py` moves a segment from `inbox/` to `done/` **only after** a `202`
   from Sentinel's `POST /events`. If that POST fails (network blip, Sentinel
   restart, non-202 response), the segment stays in `inbox/` and is retried
   whole on the next cron tick — nothing is dropped, and nothing is
   double-aggregated, because `details.batch` is deterministic
   (`{segment}|{sha256(kind|stage|error|os|client)}`), so a downstream
   consumer can collapse a replayed batch to the same key.
3. `inbox/` and `done/` are this VPS's own raw retention, not a system of
   record — Sentinel already has the aggregated events once a segment reaches
   `done/`. `pull-failures.sh`'s tail deletes anything in `done/` older than
   14 days.

## The 500-signature ceiling

A single pull aggregates at most `PER_PULL_CEILING` (500) distinct
`kind|stage|error|os|client` signatures per segment. Past that, the first 500
(in first-occurrence order within the segment) are each posted as their own
event; every remaining signature is folded into one extra `event_type:
"ingest-summary"` event whose summary names how many signatures and lines
were folded. This is a deliberate design choice: it bounds a single pathological segment's cost against Sentinel, but it never silently
drops data the way a hard truncation would.

## Watchdog

Every run, after processing, `ingest.py` checks: is the inbox now empty
(everything pulled has been posted and moved to `done/`), **and** is
`last-ping-ok` (a marker file `pull-failures.sh` touches only on a `200` from
the collector's maintenance ping) older than 7 days? If both hold, it posts
one `event_type: "collector-watchdog"`, `severity: "warning"` event with
summary `"no successful collector ping for 7 days"`.

This is a "the whole pipe has been dark for a week" signal, not a
per-segment alert — a healthy pipe with genuinely zero field failures never
trips it, because the ping marker keeps refreshing every 30 minutes as long
as `https://firekeep.ai/failure-report.php` is reachable.

**Not debounced beyond that.** `ingest.py` keeps no state of its own across
runs, so once the marker goes stale it re-fires this warning on *every* cron
tick (every 30 minutes) until connectivity to the collector is restored and
the marker refreshes. That's intentional simplicity, not an oversight — treat
a stream of these as "still broken," not as N separate incidents, and file a
Sentinel-side alert-dedup rule if the repetition becomes noisy in practice.

## Manual runs

```sh
# See what would happen without posting or moving anything:
python3 /opt/firekeep/failure-ingest/ingest.py \
    --inbox /var/lib/firekeep/failure-ingest/inbox \
    --done /var/lib/firekeep/failure-ingest/done \
    --sentinel http://100.91.3.51:8060 \
    --api-key-env FIREKEEP_INTERNAL_KEY \
    --dry-run
```

Drop `--dry-run` to actually validate, aggregate, POST, and move segments.
