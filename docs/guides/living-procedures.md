## Living Procedures (`cortex/app/procedures/`)
Makes a skill an **observed procedure** rather than advice text nobody watches. When work matching one of its steps happens, Cortex opens an execution record, notices which sibling steps do and do not happen, appends an advisory (in round 1, never a block) when an earlier load-bearing step has no evidence, and nightly aggregates per-step frequency — and, when the outcome signal permits, efficacy — into proposals a human approves. Round 1 is entirely server-side — **no client release is required for it**, because `pre_tool` already prints advisories on an `allow` decision. Round 2 (Enforced Runbooks, below) adds `command` steps and human-armed enforcement up to `block`, which DOES take a client release (0.1.44+) and its own section. Design: `docs/superpowers/specs/2026-08-06-living-procedures-design.md` (round 1), `docs/superpowers/specs/2026-08-15-enforced-runbooks-design.md` (round 2). Opt-in — `PROCEDURE_ENABLED=false`.

**Five stages, each riding a seam that already existed.**

1. **Compile** — `StepSpec` (`app/procedures/models.py`): `id` (minted `uuid4().hex[:12]` when blank, **and stable thereafter** — `merge_step_specs` carries each id forward across a wholesale spec rewrite by matching on `text`, because nothing on the agent path can hold ids still: `skill_add_step_specs`' documented entry shape has no `id`, no MCP surface ever RETURNS one, and its own docstring tells the caller to resend the whole list to add a single step. Without it every wording fix re-keyed all five steps and orphaned the procedure's entire recorded history. Text is the right join — a step whose text changed *is* a different step and its evidence should not follow — and an id the caller names always wins), `text` (≤500 chars), `kind` (`file_glob` | `unobservable`), `pattern` (fnmatch glob, ≤200 chars, required non-empty for `file_glob` and force-cleared otherwise), `load_bearing`. Specs are **self-contained — each carries its own `text`, never an index into the skill body** — because `create_skill` folds `steps` into one Markdown string after the literal heading `## Steps` and `parse_skill_content` returns `body` as one undivided blob: an index would desync the moment a human PATCHes `content`, silently and undetectably. Written to the Qdrant payload key `step_specs` by the create/PATCH path **only** (I3). Deliberately **not** in `SEMANTIC_PATCH_FIELDS`, so a spec-only PATCH goes through `set_payload` and never re-embeds — specs describe how to OBSERVE the steps, not what the skill means, and re-embedding would put an embedding-backend outage in the path of every spec edit. The cap lives twice by necessity (a pydantic validator cannot read `Settings`): `MAX_STEP_SPECS_PER_SKILL = 50` in `app/models.py` and `PROCEDURE_MAX_SPECS = 50` in config, kept honest by `cortex/tests/test_procedure_config.py`. **The authoring agent compiles its own specs — the server runs no LLM for this**, the same argument that makes client-authored skills work on a GPU-less deploy.
2. **Index** — `store.scan_active_skills` pages every **active** skill point to exhaustion (500 per scroll, following the cursor) and `store.write_index` denormalises the `file_glob` specs into one Redis key (`proc:index`) plus a per-skill **coverage** summary (`proc:coverage`: `{trigger, spec_count, observable}`). Coverage is a separate product of the same scan because the matcher index holds observable specs only — deriving the rollup from the index alone made a procedure whose steps are *all* `unobservable` vanish from `GET /procedures` and report `specs_total: 0`, which is the cold-start message, shown to a human who has just compiled the specs. `order` is the position in the **full** spec list, not the filtered one: an `unobservable` step still occupies its position, and renumbering would make the earlier-step check compare the wrong steps. Rebuilt on the skills write path when `step_specs` are present **and unconditionally by the nightly pass** — a draft→active PATCH changes index membership without touching a spec, so the write-path rebuild alone would strand that skill's steps until the next pass. The scroll used to be a bare `limit=1000` with the cursor discarded, silently truncating the index above 1000 active skills.
3. **Recognise + Observe + Warn** — `ProcedureObserver.plan(req, action_id=...)` (`app/procedures/observe.py`), called from `AgentGatewayService.decide()` immediately after the policy-reason advisory loop, with the WRITE deferred to `PendingObservation.commit()` until the decision is final (I7). Deliberately **not** a policy rule: `PolicyContext` carries exactly five fields and **no action type**, so a rule cannot tell a file path from a `run_command` target before globbing, while `ActionBeforeRequest` can — and a rule constructor error removes *all* policy rules behind one log line, whereas this stage's own `try/except` bounds the blast radius to itself. Gates, in order: `PROCEDURE_ENABLED`, `req.action.type == "edit_file"`, a live Redis client, a non-empty index, a match — **and only then** a session id not in `{"", "unknown", "none", "null"}`. That check is last on purpose: an execution that cannot be joined to an outcome is not evidence, but the drop is worth counting only once work was RECOGNISED (`store.bump_unjoinable`, surfaced as `unjoinable_edits` — spec §4 Stage 2 says of exactly this drop "counted and surfaced, not hidden"), and checking it earlier would put a Redis write on every edit of a deployment that has no specs at all. Warn-once per `(execution, step)` via `store.claim_warn` (`SET NX EX`, the `RethinkCounter` shape) — the **only** such mechanism; the execution hash used to carry a `warned` field as well, written and parsed on every read and consulted by nobody. The advisory is `code="procedure_step_missing"` (a new `AdvisoryCode` literal) and its **statistics are pre-formatted into `message`**, because the client joins only `a.get("message")` and flattens advisories with `"; "`. `evidence_event_id` carries **our own `exec_id`**, not a replay event id — `emit()` returns the Redis *stream* id rather than the `event_id` that `GET /replay/events/{id}` resolves, and that index TTLs at 30 days behind a `trim_old_events()` that is never scheduled. **Caveat the two-phase split introduced, stated because the sentence above would otherwise overstate it:** on a `block` or `rethink`, `plan()` mints an `exec_id` and quotes it in the advisory, but `abort()` never writes the record and the resubmission mints a fresh one — so an advisory returned on a NON-allow decision names a record that does not exist and never will. Harmless today (nothing resolves a procedures `evidence_event_id`, which is why the slot was free to claim), but it is a promise the receipt does not keep on that path, and a future resolver must treat an unknown `exec_id` as "the edit was refused", not as corruption. **The stage is two halves, and that is I7:** `plan()` matches and builds the advisory *in place* — so it keeps its position ahead of any `rethink_limit` advisory the escalation appends — while `commit()` performs every write and runs only once `decide()` has settled on `allow`; `abort()` gives back the warn latches instead. Writing at match time recorded edits that **never happened**: `PathDenyRule` can already have blocked, and the rethink-limit escalation blocks *afterwards*. Each phantom observation inflated Tier A frequency with work that did not occur AND suppressed that step's warn for the rest of the execution (the next call reads `observed` as the earlier-step evidence), and a rethink — where the agent resubmits the same edit — double-counted it. `observe()` survives as `plan()`-then-`commit()` for a caller that already knows the action is going ahead.
4. **Harden** — nightly Celery pass `app.procedures.harden.run_procedure_hardening` (beat entry `procedure-hardening`, `PROCEDURE_SCHEDULE_HOURS`). `run_pass(redis_client, replay_r, vector, settings)` takes **two** Redis clients and the distinction is silent if swapped: `proc:*` keys live on the cortex **data** DB (`REDIS_URL`), evals and timelines on the **replay** DB (`RP_REDIS_URL`). Per-step stats carry seven int keys — `observed`, `skipped`, `executions` (Tier A, uncapped) and `observed_scored`, `observed_success`, `skipped_scored`, `skipped_success` (Tier B, rate-limited by `PROCEDURE_AGENT_CAP`).

**Two tiers, and the split is the design's answer to a measured weakness rather than a hedge.** **Tier A — frequency and `spec_drift` — needs no outcome at all**: "this procedure ran 41 times; step 3 was skipped in 24 of them" is true and useful from the first execution. **Tier B — efficacy verdicts — is gated hard**, and on **two** conditions, because the first alone is not enough.

**Knowability is not discrimination, and conflating them is how this feature would have shipped harmful.** The gate began as `outcome_backed >= PROCEDURE_MIN_EXECUTIONS` — a count of executions whose outcome can be *resolved*, which says nothing about whether the resolved outcomes *differ*. Measured: `_failure_rate` (`evals/scorers.py`) returns `0.0` when no event carries an outcome, `post_tool` defaults `success` to `True` for every non-failing edit, and **this same changeset made the reconcile emit stamp that value** — so every session now resolves as a success, `outcome_backed` tracks the feature's own traffic 1:1, and the gate opens on a signal that separates nothing. `compute_efficacy` then collapses both buckets to `(n + prior/2)/(n + prior)`, which branch fires is decided by bucket SIZE alone, and the pass writes `"…skipped in 20 of 40 executions with no measurable cost (0.83 vs 0.83). Remove it?"` against an author-declared load-bearing step — verbatim the harm spec §F1 says the two-tier split exists to prevent, arrived at through the prerequisite fix that was supposed to help. So `run_pass` reports **three** states and names which: `tier_b: "insufficient outcome signal"` (too few knowable outcomes), `"uniform outcome signal"` (knowable, but every scored session agrees, so a comparison would measure nothing), or `"open"`. **Closed is the correct state, not an error** — the two closed states are kept distinct because their remedies differ: one needs more sessions, the other needs sessions that actually differ, and reporting the second as the first sends an operator to collect more of what cannot help. The verdict is persisted (`proc:run`, the DreamState/CollectorState precedent) and surfaced by `GET /procedures`' `run` field and the dashboard panel's subtitle; before that it existed only as a Celery return value, so a shut gate rendered identically to an open one that found nothing. **That `tier_b` string is a REPORT, not an authorisation, and treating it as one was the same defect a level down.** It sums `outcome_success`/`outcome_failure` across every execution of every skill, so **one failing session anywhere in the deployment flipped it to `open`** — and the comparison it authorised is per step. Applied to a step whose own scored buckets are uniformly successful, `compute_efficacy` returns the *identical* Beta-prior value for both, `eff_skip >= eff_obs - delta` holds exactly, and a `dead_step` ("remove it?") is emitted on a signal that separated nothing. The check that actually authorises a verdict is therefore **per step, over that step's own scored buckets** (`harden._discriminates`): both outcome classes must be present, or the step yields nothing — all-failure refused for the mirror reason, since every step of a procedure that only ever ran in failing sessions would otherwise read as load-bearing. `tier_b` stays in the run record because it is a true statement about the deployment. A verdict additionally needs `min_n` scored executions in **both** buckets, which — with `PROCEDURE_AGENT_CAP` spent across both buckets combined and both defaulting to `5` — means **no step can reach a verdict from fewer than two distinct `agent_id`s** (H10 below). That interaction is real and deliberately left as-is — the cap exists precisely so one identity cannot decide a team's procedure — but it is no longer invisible: the run record carries `verdict_ready_steps`, now counting every gate that authorises a verdict (both bucket minimums **and** discrimination), and the dashboard says so, because "open, zero proposals, forever" reads exactly like "open and nothing found". `load_bearing` therefore stays **author-declared** in round 1 and the warn stands on the author's declaration — statistics only ever *add* a sentence once Tier B has earned one.

**Proposals are written, never applied.** Three kinds ship: `load_bearing` (`efficacy(skipped) < efficacy(observed) − PROCEDURE_EFFICACY_DELTA`, via `compute_efficacy` imported from `app.owm` rather than re-derived), `dead_step` (skipped ≥ `min_n` times with no measurable cost), and **`spec_drift`** — a spec whose `text` no longer appears in the skill's `content`, i.e. the body was edited without the specs. Drift is Tier A: it compares two stored things and asks nothing of a run, so it needs no executions and no outcome, and it applies to `unobservable` steps too. It reuses the pass's single skill scan rather than adding a second read of the same collection. Matching is a whitespace-flattened, case-folded substring test, so a paraphrase reads as drift — which is a dismissible proposal to a human, regenerated nightly, not a mutation. **The stale reset is real, not asserted.** The write loop iterates the **indexed** skills (plus any with drift), not the skills that still have evidence: iterating the latter could only ever revisit the set that does *not* need clearing, so a procedure whose executions had aged out of `PROCEDURE_WINDOW_DAYS` kept its last stats and its last `dead_step` proposal standing forever on keys with no TTL. A second sweep clears skills that have left the index entirely — deleted, flipped to draft, or had their specs removed — which nothing above can reach; that is OWM's actual shape (`owm.py` runs the same second pass over previously-scored points). Consequence worth knowing before building on it: **proposal ids are minted fresh on every pass**, so a dismissal survives only until the next pass regenerates the same finding under a new id. A durable dismissal would have to key on `(skill_id, kind, step_id)`. **That sweep declines on a vacuous scan.** It was skipped only when the skill scan *raised* — but a scan can succeed and return **empty** (a `QDRANT_COLLECTION` pointing at the wrong name, a collection restored empty, a payload index mid-rebuild), which writes an empty index, leaves `touched` empty, and then clears every previously-written skill's stats and proposals: silent data loss caused by a transient infrastructure state. An empty scan is not evidence of deletion, so the sweep runs only when the scan is both non-raising and non-vacuous relative to what the store already held. The decline is logged at WARNING with the affected skill ids and reported as `orphan_sweep` (`ok` | `declined: scan failed` | `declined: vacuous scan`) in the run record, because "0 orphans cleared" is what a healthy pass and a declined one both look like from outside.

**Invariants.** Each exists because the naive version is provably wrong, and each names the code fact that forced it.

- **I1 — Recognition, not declaration.** An execution opens because a spec MATCHED observed work, never because an agent said it was following a procedure. *Because* neither delivery surface carries a session identity — `skill_recall` declares no `session_id` and never calls `_resolve_identity`; `GET /briefing` has no `session_id` at all, only a per-request `briefing_id` — and because a declaration-based design is a discipline dependency, which this repo has watched fail three times.
- **I2 — Absence of evidence is never evidence of absence.** A step counts as `skipped` only if ≥1 sibling step of the same procedure was observed in the same execution; an execution with no observations at all contributes nothing. *Because* kiro's `fs_write` maps to `other` with an empty target, `run_command` returns before the gateway POST, and personal mode short-circuits both hooks — without I2 every kiro session, every shell-heavy session and every personal-mode session votes to delete each load-bearing step it never had the ability to observe. **The sibling test runs against the steps the procedure HAS**, intersecting the execution's observed ids with the current index, not against whatever ids the record happens to name: it read "this execution observed *something*", which an execution naming only retired step ids satisfies — and every current step was then tallied `skipped`, rendering 40 real executions as "observed 0 / skipped 40" for steps performed in all 40.
- **I3 — Two writers, two stores, no shared keys.** `step_specs` live on the Qdrant point and are written only by the skills create/PATCH path; every derived number lives in Redis. *Because* a semantic PATCH does retrieve → merge → re-embed → full `upsert`, which silently discards a concurrent `set_payload` — and these are exactly the two writers this feature creates.
- **I4 — Outcome requires evidence, and most sessions do not have it.** An execution contributes to Tier B only if its session carries ≥1 outcome-bearing replay event *and* `owm.session_success` returns a non-`None` answer. The event check runs **before** the eval is fetched, not after: once you hold the eval, a `failure_rate` of `0.0` because nothing carried an outcome is indistinguishable from a genuinely clean session. Evals are computed on demand when absent (`compute_session_eval`), because the evals router's own docstring records a live incident where all 19 stored evals were `trigger="manual"` and 12 days stale against 54 completed sessions. **Bridge status is part of resolving the outcome**, fetched once per pass through `owm._fetch_bridge_statuses` (reused, never reimplemented — it already carries the internal key, the route's 200-session clamp and the degrade-to-empty contract) and handed to `session_success`. This pass hardcoded `bridge_status=None` while OWM fetched it, so it discarded `abandoned` — one of only TWO failure signals this system actually produces (spec F1) — and its own "uniform outcome signal" verdict was partly self-inflicted. Bridge unreachable degrades to eval-only outcomes and never fails the pass. Residual, stated: the outcome-bearing-event check runs first, so an abandoned session carrying no such event is still excluded (**H7** — this pointer read `H6` for one review cycle, which is the WARN-path tenancy limit, i.e. exactly the mis-numbering the limits were renumbered to prevent, surviving in the one place a reader who follows the pointer lands on the wrong limit; `harden.py` cited it correctly throughout).
- **I5 — Nothing on the pre-edit path may touch Qdrant or embed.** `ProcedureObserver.__init__` takes **no vector client at all**, and a test asserts by `inspect.signature` that none is ever added. *Because* gateway stages run sequentially on every customer Edit/Write, and a slow gate is a silently skipped gate. **The Redis half of this invariant was overstated and is corrected (2026-08-06):** "one Redis GET, memoised for `PROCEDURE_INDEX_CACHE_SECONDS`, then `fnmatch` in memory" describes only the path that does NOT match. A **match** costs, per matched index entry, `HGETALL` → `HGETALL` (again, inside `record_observation`) → `HSET` (the observed map) → `EXPIRE`, plus `HSET` + `SADD` when this is the execution's FIRST observation, plus `GET` (step stats) + `SET NX` (warn latch) when an earlier load-bearing step is missing — **four round trips at minimum, eight at maximum**, not one, on the blocking path. Nothing measured it because nothing counted them. (That range was published as "five to seven" for one cycle and was wrong at both ends — the floor missed that a warn-free match on an existing execution touches neither the stats `GET` nor the latch, and the ceiling missed that `record_observation` issues TWO `HSET`s on a first observation. A guessed number inside the invariant whose whole purpose is the real number is self-refuting; count them in the code before editing this again.) Reducing it (Lua, or a pipeline) is a round-2 change, not a claim to make in advance. `record_observation` is also `HGETALL` → `json.loads` → mutate → `HSET` with **no `WATCH` and no Lua**, so two concurrent matched edits in one session can lose one another's update — bounded (one receipt, and `observed_counts` written from the same lost copy), unfixed, and on a path already machine-global per session identity.
- **I6 — The feature can never block and can never raise.** Advisory only, in its own `try/except`, on a path that already fails open; a hostile `pattern` (`../`, a 10k-char glob, a regex-looking string) returns no match rather than raising, and an unreadable index degrades to no advisory. *Because* an agent authoring a bad spec in passing must not be able to brick edits team-wide.
- **I7 — An observation is a claim that the edit HAPPENED.** The write commits only once `decide()` has settled on `allow`; a `block` or a `rethink` records nothing, bumps no unjoinable counter, and releases any warn latch claimed while building the advisory. *Because* the stage runs mid-`decide()`, where `PathDenyRule` may already have blocked and the rethink-limit escalation can still block afterwards — so the corpus this entire feature rests on was counting edits that never occurred, each one silencing that step's warn for the rest of the execution.

**`adapter` is a transport class and cannot identify the runtime.** `Adapter` is `Literal["shell-hook", "mcp", "rest"]` and `pre_tool` hardcodes `"shell-hook"` on every runtime, so a Claude execution and a kiro execution are **indistinguishable in the request**. It is stored on the execution record for diagnostics only and must never be used to infer observability. This kills the obvious mitigation for H1 (score per-runtime capability) before it is proposed — there is no runtime field to scope on, and adding one is a client release. I2 infers observability from whether *any* sibling step was seen instead, which is why it stays correct when a new runtime is added.

**Redis keys** (all on the cortex data DB; `app/procedures/store.py` is the only module that knows a key format): `proc:index` (denormalised matcher index), `proc:coverage` (per-skill `{trigger, spec_count, observable}`, what the rollup reads), `proc:exec:{session_id}:{skill_id}` (execution hash, TTL `PROCEDURE_EXEC_TTL_DAYS`), `proc:exec:__index` (a SET of live execution keys, pruned lazily by `iter_executions` — it has no TTL of its own, so it is bounded by pass cadence rather than by the 90d exec TTL), `proc:exec:…:warned:{step_id}` (the warn-once latch), `proc:stats:{skill_id}`, `proc:proposals:{skill_id}`, `proc:proposal_owner`, `proc:written` (the previous pass's write set, which is what makes the orphan sweep possible), `proc:run` (the last pass's record), `proc:unjoinable` (recognised edits dropped for want of a session id).

**`store.py` is decode-agnostic, and that is load-bearing, not defensive.** `app.state.redis_client` — the client both the gateway stage and the `/procedures` router are handed — is built by `main.py` with **no `decode_responses`** (unlike the replay/auth/vault clients beside it), while the harden pass builds its own decoding one. Every read here therefore arrives as **bytes**, and `raw.get("observed")` on a bytes-keyed dict returns `None` *silently*: `record_observation` re-minted a fresh `exec_id` and overwrote the observed map with the single step it had just seen, so one execution recorded one step and the nightly pass tallied every other step of the procedure as `skipped`; `iter_executions` returned bytes-keyed records so `GET /procedures/{id}/executions` was permanently empty; and `dismiss_proposal` interpolated a bytes skill id into the key, writing the survivors to `proc:proposals:b'<id>'` and returning `True` while the real key kept serving the proposal. Every procedures fixture in the suite was `FakeRedis(decode_responses=True)` — the one shape production does not use. The `_s()`/`_smap()` decoder is the same shape `collectors/state.py`, `dreams/state.py` and `knowledge/status.py` already carry, for the same reason. The observation receipt now carries the real `action_id` `decide()` minted (the spec's receipt is `{action_id, target, ts}`, and an empty one cannot be joined to the `agent.action.predict` event it describes), and the per-step receipt list is bounded at `store.MAX_OBSERVATIONS_PER_STEP` with the true total kept beside it in `observed_counts` — the whole blob is read-modify-written on the blocking pre-edit path for every matching edit, and every consumer reads the map's KEYS, never the values.

**REST Endpoints (on Cortex :8100), mounted only when `PROCEDURE_ENABLED`** — the `/dreams` + `/collectors` precedent: a disabled deploy 404s rather than serving a disabled-shaped body. Paths are unprefixed. `GET /procedures` → `{procedures: [{skill_id, trigger, spec_count, observable_steps, executions, steps, proposals}], count, specs_total, run, unjoinable_edits}`, rows sorted by `(-executions, skill_id)`. Rows come from `proc:coverage`, so a skill with specs appears **even when none of them are observable** (H2 requires "0 of 7 observable" to be visible, and the index-derived version made that procedure vanish); `executions` is counted live from the execution records rather than read off the nightly stats blob, which made this endpoint and `GET /procedures/{id}/executions` disagree about whether a procedure had ever run for up to a full `PROCEDURE_SCHEDULE_HOURS`. `run` is the persisted pass record (`{last_run, executions, skills, proposals, spec_drift, orphans_cleared, orphan_sweep, outcome_backed_executions, outcome_success, outcome_failure, tier_b, verdict_ready_steps, health, error}`; `health: "unknown"` and `last_run: null` before the first pass). `GET /procedures/{skill_id}/executions?limit=50` — the receipts behind the numbers. Both gate `require_scope("memory:read")` **and both are scoped to the caller's `workspace_id`** from `auth.principal.request_principal`, the way `/memory/*` and the skills write path already take it: `memory:read` is held by every agent key in the deployment, so gating on it is a permission check and not a tenancy boundary, and these two reads returned every workspace's triggers, step text, session ids, agent ids and edited file paths. Execution keys carry no workspace component, so the receipts are scoped through the skill they belong to. A row with **no** recorded workspace belongs to the deployment's own — the same rule `workspace_migration.backfill_memories` applies to an unattributed Qdrant point, so the index and the store cannot disagree about who owns one. **The WARN path is NOT scoped — see H6.** `POST /procedures/proposals/{proposal_id}/dismiss` gates `require_scope("admin")` and returns 404 for an unknown id. **Scope note, stated plainly because it is half a fix:** the skills router declares no `dependencies=` and contains zero `require_scope` calls, so every route on it is reachable by any valid key; **accepting** a proposal is a `PATCH /skills/{id}` and therefore remains as ungated as it is today. Retrofitting a gate onto a shipped surface belongs in its own change with its own test sweep. This feature adds no new ungated route and does not pretend the existing one is gated.

**MCP Tools:** `skill_create(..., step_specs=None, ...)` — `step_specs` sits between `status` and `session_id`, so call it by keyword. `skill_add_step_specs(skill_id, step_specs)` — the round-1 answer to the cold start; it PATCHes `/skills/{skill_id}` and replaces the whole list, returning how many specs were stored and how many are observable so the agent sees the coverage it just created.

**Dashboard:** a Procedures panel at the **top of the existing Skills tab** (not a new tab), rendering a run line (`procRunLine` — last pass, which closed state Tier B is in and why, a failed pass, and any unjoinable dropped edits), coverage (`X of Y steps observable`, where Y counts unobservable steps too), per-step observed/skipped counts, and proposals with a Dismiss button. It hides itself entirely on 404/503, since a disabled deploy does not mount the router. The Dismiss button hits the admin-gated route, so it works on the nginx-fronted dashboard (`DASHBOARD_API_KEY` is admin-scoped) and toasts a 403 anywhere else; the cortex-embedded SPA (`app/static/dashboard.html`) deliberately has no such panel. When `specs_total` is 0 the panel renders one line instead of an empty card: *"No procedure has step specs yet — ask an agent to compile them with `skill_add_step_specs`."*

**Briefing:** none in round 1, deliberately — a new section pins `ALL_SECTIONS` in `test_briefing_api.py` and must fit a hard-coded 2.0s per-section budget whose overrun flips `degraded=true` on the whole envelope. Not worth it before the feature has data to report.

**Prerequisite gateway fixes that landed with this feature** (all pre-existing, each silently zeroing a downstream signal): `ag:predict:{action_id}` is now written for **every** action with `"prediction": None` when absent — it was written only when a prediction was present, and the shell hook sends none, so every reconcile from Claude Code emitted `session_id=""`, never entered its session's timeline, and left `compute_session_eval`'s predict→reconcile Brier calculation computing nothing on the only path that produces real traffic. Any reader of that key must use `.get("prediction")` and truth-test it. The reconcile emit now passes `outcome=` — **and is skipped entirely when the action cannot be attributed to a session.** `ActionAfterRequest` carries only `{action_id, outcome}`, so identity comes wholly from the `ag:predict:{action_id}` record, which expires at `AGENT_RECONCILE_DEADLINE_SECONDS` (300s); a reconcile arriving after that still emitted `session_id=""` and now carried a real outcome, landing as an OUTCOME-BEARING event filed under the empty session — the exact pollution class the outcome emit was added to fix, redirected into a bucket nothing reads (`get_session_timeline("")` is not a query anything makes). It is now dropped with a debug line naming the `action_id`; the response contract is unchanged (`recorded: true`). And `record_policy_decision` was gated on the post-remap `decision` while `warn` is remapped to `allow` one step earlier, so **no warn had ever been audited**; the gate now uses the raw action and records it under its own name, while `block`/`rethink` keep recording the final decision so escalation stays visible.

**Honest limits.**

- **H1 — Round 1 observes Claude Code file edits only.** `_action_type` maps `{Edit, Write, MultiEdit} → edit_file`; kiro's `fs_write` falls through to `other` with `target=""`. A one-line client fix is round 2; until then kiro produces no observations — and I2 means it produces no *false* ones either.
- **H2 — Shell steps are unobservable.** `pre_tool` returns before the gateway POST for `run_command`, deliberately, so a step whose action is a shell command must be authored `unobservable` even though it is mechanically precise. A meaningful fraction of every real procedure will therefore be unobservable in round 1, which is exactly why the coverage number is shown rather than hidden.
- **H3 — Cold start.** No pre-existing skill has specs, so the feature does nothing at all until skills are authored or patched with them. That is correct behaviour, not a bug; the dashboard states the count and names the tool that fixes it.
- **H4 — Recognition is not intent.** A file-glob match means work of this shape happened, not that the agent chose this procedure, and two procedures matching one file both open executions. A deliberate trade — more robust than declaration, and arguably the more correct signal for the hardening question — but it does mean a broad glob such as `*.py` is a bad spec.
- **H5 — One machine-global caveat inherited unchanged.** Executions key on `session_id`, so two concurrent sessions under the same identity share exactly the behaviour the session stash already has: no better, no worse.
- **H6 — The WARN path has no tenancy boundary: on a MULTI-workspace deployment a step's text can reach an advisory in another workspace.** The two read surfaces are scoped (above) and that half is complete. The pre-edit path is not: `proc:index` is one machine-global key and `ActionBeforeRequest` carries no principal at all, so the matcher has nothing to scope on and scoping it means threading a principal through a shipped request model on the blocking edit path — its own change, with its own test sweep. What IS done: every index entry and coverage row now carries the `workspace_id` of the skill it came from, so the data a later fix needs is present. What leaks until then: an edit matching a glob authored in workspace B can produce an advisory quoting **B's step text and trigger** to a user in workspace A. **On the default single-workspace deployment — which is every deployment today, since `FIREKEEP_WORKSPACE_ID` is one env var — this is inert.**
- **H7 — I4 runs before Bridge `abandoned` is consulted.** `_resolve_outcome` requires an outcome-bearing replay event first, so a session Bridge calls `abandoned` that carries no such event is still excluded. Correct per I4 as written, rarely reachable (an execution exists only because an edit happened, and the reconcile emit stamps an outcome), but it is a place where a knowable failure is dropped.
- **H8 — `DELETE /skills/{id}` triggers no index rebuild.** Create and PATCH rebuild `proc:index` when specs are touched; delete does not, and the only other rebuild is the nightly pass — so for up to `PROCEDURE_SCHEDULE_HOURS` the pre-edit path keeps matching a **deleted** skill's globs, opening executions against it and warning about its steps. The rollup does not show it (rows come from the rebuilt coverage key), so the two surfaces disagree for that window.
- **H9 — The hardening pass mutates the evals and pattern stores as a side effect.** `_resolve_outcome` calls `compute_session_eval` on a cache miss, which **writes** the eval, its eval features and any extracted patterns. Deliberate (a pass that only read evals would have almost no sample) but not free: it runs inside the `--pool=solo` worker, where one long task blocks every other periodic task. There is also no per-session memoisation, so a session holding N execution records (one per matching skill) fetches its timeline and recomputes against it N times.
- **H10 — Tier B is structurally unreachable on a single-developer deployment.** `PROCEDURE_AGENT_CAP` (5) is spent across both buckets while a verdict needs `PROCEDURE_MIN_EXECUTIONS` (5) scored executions in each, so no step can reach a verdict from fewer than two distinct `agent_id`s. Intended (the cap exists so one identity cannot decide a team's procedure), but it means a solo deployment sees `tier_b: open` and zero proposals forever; `verdict_ready_steps` is what makes that legible rather than mysterious.

### Round 2 — Enforced Runbooks (2026-08-15)

Round 1 watches file edits and comments; round 2 makes the SHELL path enforceable. A skill whose `step_specs` carry the new `kind: "command"` (a glob over normalized command text) is a **runbook**, and a human — never an agent — can arm it with an enforcement mode: `advise` (round-1 behaviour), `require_ack` (a matched command is challenged and proceeds only after an audited acknowledgement), or `block`. Spec, pre-registered before code and amended by two external reviews plus a same-day post-implementation pass: `docs/superpowers/specs/2026-08-15-enforced-runbooks-design.md`. Server code: `cortex/app/procedures/enforce.py`; client gate: `client/firekeep_client/hooks/runbooks.py` (0.1.44+). Routes and their gates are in `docs/guides/cortex-api-endpoints.md`.

The properties that survived review, each because the naive version is provably wrong:

- **Allow is not success.** Evidence commits in two phases: `decide()` writes a PENDING record, and only a reconcile carrying `exit_status == 0` commits it. Round 1's I7 said an observation claims the edit *happened*; a command that ran and failed satisfies no runbook step, so permission-time evidence would score every crashed deploy as a completed one.
- **`require_ack` is a protocol, not a boolean.** Deterministic challenge id → audited ack with a recorded reason (`POST /procedures/ack`) → a one-use permit (TTL 10 min) bound to (workspace, member, session, command hash, skill, step, bundle version, **execution number**). Execution number is in the tuple so a permit minted in one evidence scope cannot be replayed in the next.
- **Block fails CLOSED, through an exception-tight branch.** The hook wrapper's `never_raise(0)` exists so a hook crash cannot brick the host tool — which is exactly a fail-OPEN default. The block-mode branch decides its exit code inside its own tight `try/except` before the wrapper can, and the client honours an `allow` only when it carries the `runbook_evaluated` advisory — the marker `evaluate()` appends solely on a genuinely evaluated path (readable index, joinable session, no internal exception). A reachable-but-broken server therefore reads as a block, not as an authenticated allow; our own build demonstrated the failure this prevents when a missing `AdvisoryCode` literal made pydantic reject the marker inside a catch-all and every block degraded to allow until the suite caught it.
- **Tenancy precedes enforcement.** Every lookup, permit, mode and bundle is scoped to the VERIFIED workspace principal (`request_principal`); `agent_id` stays an observability label, never authorization. Mode changes are `require_scope("admin")` on their own route — the skill PATCH path cannot touch mode, so agents may *propose* runbooks but never *arm* them.
- **The bundle is last-known-good, and coverage is reported, never assumed.** `GET /procedures/bundle` serves a versioned (sha256[:12]) workspace bundle the client stores atomically and matches locally — ungated commands cost zero network. Sessions ack the version they hold (`POST /procedures/bundle/ack`); the server enforces whatever reaches it regardless, and a block-mode runbook whose recent sessions lack acks is surfaced as NOT ACTIVELY ENFORCED rather than silently counted as protected.
- **Matcher parity is byte-identical by test, not by intent.** Client and server normalize identically (`" ".join(command.split()).strip()[:4096]`, non-strings refused, `fnmatchcase`) and mirrored parity suites pin the same literal input/output pairs on both sides — the client match is a fast path, never a different answer. Parallel Bash calls cannot cross-attribute evidence: the pre→post action stack pairs each exit status by command hash.

**Honest limits, stated up front:** command matching is mistake-catching for a WELL-MEANING agent, not adversary-proof — `bash -c`, a script file, or trivial re-quoting evades the glob, which is why modes are human-armed and the threat model's memory-poisoning finding stays open. Coverage is full only on runtimes with blocking hooks (Claude Code; kiro fires but does not enforce exit-2), advisory elsewhere, and the machine owner can always strip the hooks — this gates agents, not humans. Rollout is gated on our own dogfood: observe ≥5 real VPS deploys under `advise`, then `require_ack`, then `block`, and nothing is announced until block mode prevents one real mistake.
