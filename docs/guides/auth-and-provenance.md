## Auth (`auth/`)
Per-key API auth with scopes, enforced by a shared pure-ASGI validator (`auth/asgi.py`, `FirekeepKeyAuthMiddleware`) on **every** surface when `AUTH_ENABLED=true`: all four MCP apps (cortex-mcp :8080, bridge :8070, sentinel :8060, relay :8050 — injected via `mcp.run(..., middleware=build_auth_middleware(...))`) and Cortex REST :8100 (replaces the retired legacy `APIKeyMiddleware` / `API_KEY` env). Fail-closed: Redis DB 7 unreachable while enabled → 503 loud, never pass-through (note: compose healthchecks are TCP-only, so containers stay "healthy" during a fail-closed outage). Skip list (prefix match): `/health`, `/version`, `/.well-known/agent.json`, plus on Cortex REST `/docs`, `/redoc`, `/openapi.json`. `auth/asgi.py` also supports a separate `skip_exact_paths` (literal-match only, not a prefix) — Cortex REST uses it for exactly `/enroll`, `/enroll/anchor`, `/members/invites/accept`, and `/members/invites/anchor` (`app/main.py`'s `AUTH_SKIP_EXACT_PATHS`). Those pre-credential routes stay keyless; `/dashboard/api/*`, `/enroll/invite`, and `/enroll/invites` remain auth-gated. Literal matching is load-bearing: a bare prefix-matched `/dashboard` previously exempted the whole subtree and exposed memory content. No `/dashboard` path is on either list since 2026-10-01, when the legacy cortex-served HTML shell those exact entries existed for was removed (`docs/THREAT-MODEL.md` §5.2; guarded by `cortex/tests/test_legacy_dashboard_removed.py`). **Default `AUTH_ENABLED=true` since 2026-07-26 (audit blocker 7)** — it was `false`, which shipped every install unauthenticated. Safe to default on because `install.sh`/`update.sh` run `deploy/bootstrap-keys.sh` BEFORE the app containers start and that script writes Redis DB 7 with `redis-cli` rather than POSTing to a now-gated `/auth/keys`, so it cannot lock itself out; the installer's health probes still pass (`/health` and `/version` are skip-listed, and the one probe hitting a gated path — `GET /mcp` on cortex-mcp — is satisfied by install.sh's `2??|401|405` accept list). Compose interpolates from `.env`, so an EXISTING `.env` carrying an explicit `AUTH_ENABLED=false` keeps winning: this changes the default for new installs, not existing ones, and an existing deployment stays unauthenticated until its owner edits that line. Paired with `BIND_ADDR` (default `127.0.0.1`) on all six published app ports — the datastore bindings stay literal `127.0.0.1` and are deliberately NOT governed by `BIND_ADDR`, so widening the app surface never publishes a passwordless Redis. `docker-compose.office.yml` pins its ports with `!override` literals, so `BIND_ADDR` cannot widen the office deployment.

**Scope checks:** `require_scope` (FastAPI Depends, Cortex REST — enabled-ness from `init_auth()`, which the Cortex lifespan calls) and `require_scope_asgi` (Starlette-level, for FastMCP `@mcp.custom_route` handlers on bridge/relay). Since 2026-07-16 `require_scope_asgi` derives enabled-ness from `AuthSettings` (the `AUTH_ENABLED` env var — the same truth `build_auth_middleware` reads), NOT from `keys._AUTH_ENABLED`: the FastMCP service processes never call `init_auth()`, so that flag was permanently False there and every custom-route scope gate passed anonymously under office auth. Tests must monkeypatch `auth.asgi.get_auth_settings`, not the keys flag.

**Keys, enrollment & bootstrap:** `deploy/bootstrap-keys.sh` (idempotent, invoked by `install.sh` and `update.sh`) mints: the internal service key (`FIREKEEP_INTERNAL_KEY` in `.env` — workers; scopes `memory:write,session:read,eval:read,eval:write,session:read:workspace,relay:write:service`, NOT admin; `ensure_env_key`'s scope reconciliation adds the last two in place to a key minted before they existed), Bridge's own dedicated key (`FIREKEEP_BRIDGE_KEY` in `.env` — wired via `NB_FIREKEEP_API_KEY` to ONLY the bridge container, every other `env_file: .env` service explicitly blanks it; scopes `memory:read,memory:write,session:read,eval:read,eval:write,eval:grade,memory:write:delegated` (`memory:write:delegated` since 2026-10-04, for the distiller's `POST /memory/learn/delegated`; `memory:read` since 2026-10-01, for its prior-art and proactive `/memory/recall` calls — transitional, until those paths forward the caller's key) — the only credential carrying the service-only `eval:grade` scope, see below), the dashboard key (`DASHBOARD_API_KEY` — nginx injects it as `X-API-Key` on the dashboard's `/api/*` proxies; admin-scoped, behind nginx basic-auth = documented second door), and an admin key (plaintext printed exactly once, never stored). It no longer mints `RELAY_INTERNAL_API_KEY` (retired 2026-10-05, `docs/THREAT-MODEL.md` §5.18 — Relay writes scope decisions with the session owner's own key) and revokes an existing one through `retire_env_key`, which deletes only a record whose device is `firekeep-relay` and always drops the `.env` line. Customer devices enroll through a single-use code from Dashboard → Devices or `deploy/firekeep-admin invite --json`. The client generates the `nxs_` secret, sends only its SHA-256 hash to `POST /enroll`, and stores the plaintext in its one `[server]` connection. `firekeep-admin keys create` remains a manual/generic-client fallback. Credential IDs resolve through `auth:cred:<credential_id>`; legacy prefix ambiguity refuses rather than guesses. **Confused-deputy fix:** cortex-mcp holds no key — it forwards the caller's `X-API-Key` on proxied REST calls, so `require_scope("admin")` on vault/auth routes sees the caller's own scopes.

Under office `AUTH_ENABLED=true`, Sentinel threads `FIREKEEP_INTERNAL_KEY` (via `NS_FIREKEEP_INTERNAL_KEY`) as `X-API-Key` onto its outbound alert-broadcast (→Relay `/mcp`) and webhook (→Cortex `/webhooks/internal/fire`) calls; unset on personal VPS. Symdex's outbound Cortex calls are keyed too (SP1b §11, Task 33) — since 2026-10-04 with the enrolled **member's** key, which the client gateway resolves from `~/.firekeep/config` and passes to the symdex child as `FIREKEEP_CLIENT_API_KEY`; symdex no longer reads `FIREKEEP_INTERNAL_KEY`, and no gateway child inherits it ([`client-kit.md`](client-kit.md#what-a-gateway-backend-child-sees--the-allowlisted-environment-firekeep_clientchildenv)) — this closes the last dark integration; every outbound call to an auth-enforced surface is now keyed under `AUTH_ENABLED=true` (Symdex itself has no auth middleware and is loopback-only, so inbound calls to it need none).

**REST Endpoints (on Cortex :8100):** auth admin: `POST /auth/keys`, `GET /auth/keys`, `PATCH /auth/keys/{id}`, `DELETE /auth/keys/{id}`, `GET /auth/scopes`; enrollment public: `POST /enroll`, `GET /enroll/anchor`; enrollment admin: `POST /enroll/invite`, `GET /enroll/invites`, `GET /enroll/defaults` (the transport/host an invite gets when it names none — resolved from `BIND_ADDR`, then `VPS_IP` only under a wildcard binding), `DELETE /enroll/invites/{tid}`. `key_id` resolution verifies each Redis-scan candidate's stored `key_id` field rather than acting on the first prefix match: `DELETE /auth/keys/{key_id}` returns **409** (nothing revoked) when more than one stored record verifies against the same short id, and `GET /auth/keys` rows carry an `ambiguous: bool` field so a collision is visible in the listing rather than hidden behind whichever record the scan happened to hit first.
**Scopes:** `memory:read`, `memory:write`, `session:read`, `session:write`, `replay:read`, `relay:read`, `relay:write`, `eval:read`, `eval:write`, `vault:read`, `dex:docdex`, `dex:maildex`, `admin`, and the **service-only** `eval:grade`, `session:read:workspace`, `memory:write:delegated` and `relay:write:service` (see below).

**`session:read:workspace` (service-only, 2026-10-01):** Bridge's REST session routes (`GET /sessions`, `GET /sessions/{id}`) show a `session:read` caller only the sessions its own member owns; this scope widens that to every session in the caller's own workspace (never across workspaces). It exists for Cortex's background workers — OWM, skill scoring and synthesis, the pattern engine — which read sessions with `FIREKEEP_INTERNAL_KEY`; wildcard (`"*"`) keys pass it too. The MCP `ctx_list_sessions` tool never honours it. Same minting rules as `eval:grade` below: not enrollable, not anonymous, rejected by `create_key`. An internal key not yet upgraded by `bootstrap-keys.sh` fails closed — it sees only the owner's sessions. See `docs/guides/bridge-context-and-briefing.md` "Session ownership".

**`memory:write:delegated` (service-only, 2026-10-04):** authorizes `POST /memory/learn/delegated`, where a service writes a memory FOR a member it names (Bridge's distiller, writing a session's distillate for the member who owned the session). Cortex verifies the named member is active in the service key's own workspace and that a named credential belongs to that member (`auth/principal.py` `delegated_attribution`). Unlike `session:read:workspace` it is matched **literally** — a `"*"` key (the dashboard's, which nginx injects into every browser request) does not pass, so nobody with dashboard access can attribute a memory to another member. Same minting rules as `eval:grade`: not enrollable, not anonymous, rejected by `create_key`. **Write provenance:** every memory write records the verified `workspace_id`, `member_id` and `credential_id` plus a `runtime_id` derived from the credential and the `X-Agent-Id` label (`auth/principal.py` `request_attribution`, `runtime_id_for`); the label is display-only. See `docs/guides/memory-and-recall.md` "Write provenance".

**Route authorization — what each Cortex route demands (2026-10-01, `docs/THREAT-MODEL.md` §5.10):** passing the key middleware proves a caller holds *a* valid key, not that it may do what it asks. The core memory routes now declare their scope: `/memory/recall`, `/memory/recall/stream`, `/memory/contributors`, `/memory/handoff` → `memory:read`; `/memory/learn`, `/memory/stream`, `/memory/feedback` → `memory:write` (and, since 2026-10-05, `/memory/deprecate` and `/memory/confirm` via `require_scope("memory:write")`, confined to ids the caller could recall — `docs/THREAT-MODEL.md` §5.19) — each via `require_any_scope(<scope>, "admin")`, because `scopes_allow` treats only `*` as a superset and a literal `["admin"]` key must keep every route it had. `/skills/{id}` (GET/PATCH/DELETE) additionally resolves the id to a `memory_type == "skill"` point in the caller's workspace (404 otherwise, 503 when it cannot look), and **review decisions require `admin`**: deleting a skill, any `skill_status` change, `needs_rereview`, `stale`, `clear_duplicate_of`, and editing `content`/`trigger`/`symptoms` of a non-draft skill — so an agent key cannot approve its own draft or rewrite an approved one, while `step_specs` edits (`skill_add_step_specs`) and draft refinement stay on `memory:write`. With `AUTH_ENABLED=false` review decisions are allowed: every caller is the anonymous owner, and there is no identity to separate a human from an agent (this is a deliberate exception local to `app/skills/api.py::_has_review_authority`, not a general "anonymous passes admin"). `POST /admin/embeddings/reembed` and its progress route are `admin`; the status read is `memory:read`. `/audit/memory` and `/audit/memory/summary` require `replay:read`, stay inside the caller's workspace, and show a non-admin only events stamped with its own `member_id` (`replay.emitter.emit(..., workspace_id=, member_id=)`, written by `/memory/recall`, `/memory/learn`, the streaming recall and `skill_recall` receipts); unattributed events — everything before this change — are visible to admins and (since 2026-10-04) to the deployment owner member's non-admin keys, no one else. `/replay/*` and `/evals/*` apply the same per-event predicate (`replay/authz.py`; `docs/THREAT-MODEL.md` §5.13, `replay-evals-patterns.md`). Who calls these routes with which key, checked before gating: agents via cortex-mcp forward their own enrolled key (`ENROLLABLE_SCOPES` ⊇ `memory:read, memory:write, replay:read`, unioned onto old enrolled keys at validation); the dashboard holds `*`; Bridge's distiller writes with `FIREKEEP_BRIDGE_KEY` (`memory:write`; since 2026-10-04 through `/memory/learn/delegated` with `memory:write:delegated` when auth is on) and its prior-art / proactive recall read with the same key — hence `memory:read` was added to it, transitionally: once Bridge forwards the caller's key there (`fix/bridge-session-ownership`) the scope should be dropped from `bootstrap-keys.sh` and narrowed by hand on existing keys; Sentinel, the fleet enqueue and the briefing's outbound calls with `FIREKEEP_INTERNAL_KEY` touch none of these routes. Guards: `cortex/tests/test_peripheral_route_authorization.py`, `test_skill_route_authorization.py`, `test_audit_authorization.py`.

**`relay:write:service` (service-only, 2026-10-04):** Relay's member-bound operations — DMs, presence register/heartbeat/deregister, leases and claims, bulletin posts, task writes, scope sessions — require `relay:read` / `relay:write` (`docs/THREAT-MODEL.md` §5.14), which member keys carry and the owner-member service keys deliberately do not, so a leaked `FIREKEEP_INTERNAL_KEY` cannot act as the owner inside Relay. This scope authorizes that key's only two Relay writes: Sentinel's `relay_broadcast` alert and Cortex's fleet `POST /tasks`. Workspace-visible reads (presence, bulletin, channel backlog, task list, status, lease status) stay ungated. Same minting rules as `eval:grade`: not enrollable, not anonymous, rejected by `create_key`; `update.sh` reconciles it onto existing internal keys — until it has, Sentinel's alert broadcasts and the nightly fleet enqueue are refused (both are best-effort and logged). See `docs/guides/relay-coordination.md` "Who owns what".


**Join codes carry their member (2026-10-04, `docs/THREAT-MODEL.md` §5.15):** every enrollment ticket now records the member its credential will belong to, and redemption registers the credential for exactly that member. A new-device code (`POST /enroll/invite` without `device_id`, dashboard **Add device**) belongs to the verified caller's member; a regenerated device (`device_id` set, dashboard **Regenerate**) keeps the member its existing credentials belong to — before this, `mint_invite` put no member on the ticket, the credential fell back to the deployment owner, and a teammate's regenerated device authenticated as the owner. The member is resolved from the device's credential records (`auth.keys.resolve_device_attribution`): no credential for the device → 404, records naming different members → 409, never a guess. The member row must exist in the caller's workspace with `status=active` at issue time (404/409 otherwise) and again inside the redeeming Lua script (`member_inactive`, code not spent). `InviteRequest` deliberately has no `member_id` field — `MemberInviteRequest` subclasses it. The server-shell path (`python -m app.enroll.mint`, used by `deploy/firekeep-admin invite`) applies the same rule with the deployment owner as issuer. **Upgrade note:** a code minted by an older server carries no member and is refused unspent at redemption (`unattributed`, 409 "issued before this server recorded which member") — re-issue it. Codes live `ENROLL_TICKET_TTL_HOURS` (24h default), so only codes outstanding at the upgrade are affected.

**Credential validation reads attribution, never invents it (2026-10-04, `docs/THREAT-MODEL.md` §5.15):** `validate_key_by_hash` (the one implementation behind `validate_key`, the ASGI middleware and `require_scope`) now refuses a stored record that lacks `workspace_id`, `member_id` or `credential_id` — it used to fill the first two with the deployment owner, so any record written without attribution authenticated as the owner. It also refuses a record from another workspace; a member whose row (`auth:member:<id>`) is missing, describes a different member/workspace, or has `status != "active"`; an `expires_at` that does not parse or has no timezone (both used to mean "never expires"); and a scope document that is not a JSON list of strings (a stored dict or string turned `"*" in scopes` into a key lookup or a substring test — `'"x*"'` was a wildcard). Unknown scope strings inside a well-formed list are **dropped with a warning, not fatal**: pre-2026-07 teammate keys still carry the retired `twin:read`, and it grants nothing. The 401 body names the reason (the caller already holds that key). Auth-disabled boxes never reach this code. `status` is the enforced switch member removal flips (next paragraph). **Migration:** records with no attribution are stamped to the deployment owner, explicitly and logged, by `deploy/bootstrap-keys.sh` (`[ATTRIBUTED]`/`[INDEXED]`, before `update.sh` restarts the services; it also writes the workspace record and owner member row with `HSETNX`, so Bridge/Relay/Sentinel can validate before cortex-api has booted) and by cortex-api on **every** boot (`auth.workspace.attribute_unowned_credentials`, ahead of the one-shot migration marker — this covers deployments that never run bootstrap, such as a Kubernetes one). A field that is already set is never overwritten. `deploy/firekeep-admin keys audit` is the read-only report: per credential `ok` / `unattributed` (will be stamped) / `refused: <reason>` (will stop authenticating; revoke and re-issue) / `expired`, plus index and mapping notes. Run it before upgrading. `init_auth()` now runs `ensure_workspace` when given a client. Deferred deliberately: requiring the `auth:cred` reverse mapping and `auth:key_index` membership (ambiguous legacy records that `backfill_credential_mappings` refuses to map would be locked out). `POST /auth/keys` and `firekeep-admin keys create` still mint owner-attributed keys by design: they take no member, and per-member credentials come from member invites.

**Removing and restoring a member (2026-10-05, `docs/THREAT-MODEL.md` §5.17):** three admin surfaces, one implementation (`auth/members.py`):

| Surface | Remove | Restore |
|---|---|---|
| REST (Cortex :8100, `admin`) | `DELETE /members/{member_id}` | `POST /members/{member_id}/restore` — body: the `POST /enroll/invite` connection fields (`{"kind":"ports"}` lets the server fill transport/host) |
| Dashboard | Members → **Remove** (confirm) | Members → **Restore** (confirm; shows the new install command) |
| Server shell | `deploy/firekeep-admin members remove <id>` | `deploy/firekeep-admin members restore <id>`, then `deploy/firekeep-admin invite --member <id>` |

`firekeep-admin members list|remove|restore` runs `python -m app.members.admin` inside cortex-api (like `invite` runs `app.enroll.mint`), so it needs docker compose; on a deployment without it (Kubernetes) use the dashboard or `kubectl exec` the same module. **Remove** sets the member row to `status: removed` (the row is kept: memories, sessions, replay and relay records stay attributed to it; `GET /members` still lists it, `active_count` does not count it), then deletes every credential naming the member (`auth:key:*` found by scan, plus `auth:cred:` and `auth:key_index`), deletes their unredeemed join codes and marks their member invites `member_removed`. The status write comes first: from it on, every service refuses the member's keys on the next request (validation reads Redis DB 7 per request; there is no auth cache anywhere) and the redeem script refuses their codes unspent. Idempotent — a repeat returns `already_removed: true` and re-sweeps, which also finishes an interrupted removal. Refused with 409: the deployment owner (never removable), removing the member you are acting as, and a removal that would leave no active admin-holder (cannot happen today: every admin-capable key is the owner's). The response lists `credentials_revoked`, `join_codes_cancelled` and `member_invites_revoked`.

**What happens to the removed member's data — kept, transferred to nobody.** Member-private memories, Bridge sessions, Relay presence/DMs/leases and member-owned vault secrets stay attributed to the removed `member_id`. No credential authenticates as that member, so no member-principal read returns their private data, and nothing is re-stamped as the owner. Operator surfaces (`/memory/export`, admin vault reads) were never member-filtered and still are not — see [`dexes.md`](dexes.md) "The threat boundary"; removal neither widens nor narrows what the operator sees. Do two things by hand after removing someone who used maildex: delete their `maildex.<id>` app password (`DELETE /vault/secrets/maildex.<id>` with an admin key, or the dashboard Vault tab) and ask them to revoke it at the mail provider — it is a live third-party credential nobody can now act for. Their Relay presence never expires on its own; remove it from the dashboard. Their queued Bridge distillations fail the delegated-write member check and go to the DLQ after `MAX_ATTEMPTS`. There is **no purge** of a removed member's memories yet; restoring them returns everything.

**Restore** reactivates the **same** member id (their history and private memories are theirs again) and mints one device join code (24h, `ENROLL_TICKET_TTL_HOURS`) whose credential belongs to them; their old credentials stay deleted. Only a `removed` member can be restored through REST (409 otherwise). `firekeep-admin invite --member <id>` (`app.enroll.mint --member-id`) mints a new-device code for any **active** member and is refused together with `--device-id`.

**Scope reconciliation of service keys:** `ensure_env_key` in `deploy/bootstrap-keys.sh` no longer only checks that an env-backed key is registered — a registered key that lacks a scope its line declares gets that scope added in place and the run prints `[RECONCILED] <VAR> scopes += <added> (plaintext unchanged)`. It is a union: a scope is never removed (an operator's deliberate widening survives; narrowing stays a manual `HSET`), no key is minted or rotated, and no plaintext is printed. This is what lets a newly gated route reach deployments provisioned before the scope existed, on their next `update.sh`; before it, the only safe options were leaving a route ungated or asking every operator to re-mint. Guarded by `deploy/tests/test_bootstrap_keys.sh` (Run 3).

**Service-only scopes (`auth/keys.py` `SERVICE_ONLY_SCOPES`):** `eval:grade` exists and gates a real route (the `task_result` grade hint on `POST /evals/sessions/{id}/compute`), but no member credential ever holds it — it is subtracted from both `ENROLLABLE_SCOPES` and `ANONYMOUS_SCOPES`, `create_key` (the `POST /auth/keys` admin path) rejects it outright, and the retroactive enrolled-ceiling union at `keys.py:495-507` can never grant it to an old credential (that union only ever adds `ENROLLABLE_SCOPES`, which excludes it by construction). It is minted onto exactly one credential, `FIREKEEP_BRIDGE_KEY`, by `deploy/bootstrap-keys.sh`. Holding ANY service-only scope (or `admin`/`*`) also exempts a key from the per-credential memory write ceiling (`cortex/app/write_limit.py`, `docs/THREAT-MODEL.md` §5.19) — which is why these scopes must never become enrollable. `GET /auth/scopes` lists it separately, under `service_only`, not under `scopes`. The route gate (`cortex/app/evals/api.py` `_hint_authorized`) honors EXACTLY `eval:grade` — not `admin`, not `"*"` — checked first on the enforced identity, then (because the disabled-mode dependency returns the anonymous identity and ignores presented keys) by directly validating the presented `X-API-Key` against the auth store. An unauthorized hint is dropped with one ERROR log naming the fix; an auth-store outage is a distinct fail-closed ERROR that does not suggest re-running bootstrap.

**Synchronous fan-out forwards the caller's key (2026-10-01):** when a request handler calls another service ON BEHALF of its caller, it presents the caller's own `X-API-Key`, never a service key — cortex-mcp's `_CallerKeyAuth` established the pattern, and `GET /briefing` now follows it for the tasks, bulletins and resumable-sessions sections (`app/briefing/api.py`; `docs/THREAT-MODEL.md` §5.11). A service key on a request-path call answers for whichever subject the caller names in a parameter, which is how `agent_id=<teammate>` read a teammate's sessions. Service keys remain correct for work with no live caller (nightly passes, workers) and for deployment-wide reads (the briefing's Sentinel environment section).

**Anonymous identity (the `AUTH_ENABLED=false` path):** `keys.ANONYMOUS_SCOPES` is DERIVED as `SCOPES - {"admin", "*"}` (not a literal list — a scope added later is granted automatically instead of silently withheld). Not `[]`: with auth off the product must still work for a single user who has done no key management, and an empty set 403s every `require_scope` route. Not `["*"]` (what shipped until audit blocker 7): `admin` is the whole exposure — it gates decrypted vault reads (`vault/api.py`) and key minting (`auth/api.py`), and granting it to every anonymous caller is what put 12 real secrets on the public internet. **Narrowing the list was only half the fix** — both disabled paths (`require_scope` in `auth/middleware.py`, `require_scope_asgi` in `auth/asgi.py`) previously returned the anonymous identity WITHOUT consulting the required scope at all, so the list could say anything and `admin` routes still passed. They now run `keys.scopes_allow(anon_scopes, scope, allow_wildcard=False)` and raise 403 via `keys.anonymous_denied_detail()`. `allow_wildcard=False` is specific to that path: a real key legitimately carries `["*"]` (owner + dashboard keys) and must keep passing every gate, but a caller who never presented a key gets a plain membership test so a regression in `ANONYMOUS_SCOPES` cannot re-open vault/key-minting. Net: with auth off, everything below `admin` is open and unattributed — that is a convenience mode for a loopback-bound single user, not a safe posture on a reachable stack.

**Config:** `AUTH_ENABLED=true` (default since 2026-07-26), `AUTH_REDIS_URL=redis://redis:6379/7`, `FIREKEEP_INTERNAL_KEY`, `FIREKEEP_BRIDGE_KEY`, `DASHBOARD_API_KEY`, `BIND_ADDR=127.0.0.1`
**Office deployment:** `docker-compose.office.yml` override rebinds all app ports to 127.0.0.1 behind Caddy :443 (internal CA, path routing `/mcp/<svc>` + `/api/<svc>/`; symdex is client-side stdio only and has no server container to route in the office deployment). ## Build Provenance (`provenance/`) — Stage 1
Shared build-identity module (`provenance.get_version_info(service) -> {service, version, git_sha, build_time}`) so every service answers "what version are you running?" identically instead of four copies of the logic drifting. `GET /version` is registered on all four services — Cortex REST :8100 (`cortex/app/version.py` is a thin adapter preserving its pre-existing 3-key response shape for `cortex/tests/test_version.py`), and as an `@mcp.custom_route` on bridge :8070, sentinel :8060 and relay :8050 (matching the `/health` precedent). Unauthenticated on all four (in the auth skip list alongside `/health`) and probes no backends, so it answers even when the service's dependencies are down — a support call's first question. Values are injected at image build time: each Dockerfile declares `ARG GIT_SHA=unknown` / `ARG BUILD_TIME=unknown` / `ARG APP_VERSION=0.0.0-unprovenanced` and `ENV`s them; `docker-compose.yml`'s `build.args` passes them through from the host env; `install.sh`/`update.sh` export `GIT_SHA` (`git rev-parse --short HEAD`), `BUILD_TIME` (UTC ISO8601) and `APP_VERSION` (`git describe --tags --match 'v[0-9]*' --always --dirty`) before building — the `--match` excludes this repo's `client-vX.Y.Z` client-kit release tags so a server image never reports a client version; falls back to the short SHA until server `vX.Y.Z` tags exist. **The fallback is deliberately not release-shaped.** All seven build blocks in `docker-compose.yml` (four cortex + bridge + sentinel + relay) now pass all three args, so `install.sh`/`update.sh` stamp real provenance; What remains is the case where someone builds **outside** those scripts — a bare `docker compose build` leaves the three env vars unset and compose stamps its own `${APP_VERSION:-…}` default into the image. That default used to be `0.6.0`, which **parses as a clean release**, so the client's `serverupdate` compared it against the published series and announced `server update available: 0.6.0 -> v1.3.1` — a twenty-tag jump naming a version that never shipped (seen live on a real Keep, 2026-08-29). The sentinel is now `0.0.0-unprovenanced`, which `updater.parse_version` rejects by construction. `tests/test_provenance.py` pins every Dockerfile ARG and compose default to `provenance._FALLBACK_VERSION` so the shell layer and the Python constant can never drift again — before that guard the Python fallback was dead code in exactly the scenario it existed for, because compose's copy of the literal always won first.
