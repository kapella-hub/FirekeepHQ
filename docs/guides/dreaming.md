## Dreaming (`cortex/app/dreams/`)
Automated Celery pass that consolidates older episodic memories into durable insights and maintains one continuously-updated profile per human, both surfaced through ordinary recall/briefing paths — no human review queue (auto-approve with rails). Design: `docs/superpowers/specs/2026-08-04-dreaming-design.md`.

**Round 1 is additive: dreams are written, nothing is archived.** The original sketch synthesized a cluster and then archived its source episodes; an audit found archival is where nearly all the irreversible risk lives (no atomicity between insert and archive, restore that overwrites `timestamp`, export/import resurrecting archived points, graph rows that keep serving archived content) and cut it. Consolidation still delivers a durable, retrievable insight that outranks scattered episodes; archival is Round 2, gated on measured LongMemEval-S evidence (`benchmarks/memory/`) that dreaming does not regress retrieval quality. `DREAM_ENABLED=false` by default, like every other opt-in subsystem here.

**Execution model — one unit of work per tick.** The single Celery worker runs `--concurrency=1 --pool=solo` (`docker-compose.yml`'s `cortex-worker` command), so a long task blocks every other periodic task, including the 60s agent-gateway sweeper. Beat fires `run_dream_tick` every `DREAM_TICK_MINUTES`; each invocation processes **at most one cluster or one person profile**, then returns — progress persists in Redis (`app/dreams/state.py`'s `DreamState`, mirroring `CollectorState`'s pattern), so a backlog is worked off across many short ticks and a crash costs one unit, not a run. **`--pool=solo` means Celery's `soft_time_limit`/`time_limit` on the task are decorative — the solo pool silently ignores both, no `SoftTimeLimitExceeded` is ever raised.** `DREAM_SYNTH_TIMEOUT_SECONDS` (45s, enforced by httpx inside `synthesize()` — via `app/llm.py`'s `chat()` since phase 4 — and `synthesize_profile()`) is therefore the only control that actually binds.

**The gate.** The real order in `app/dreams/task.py` — an earlier version of this section listed a different one, so read this against the code, not against memory:

1. **`DREAM_ENABLED`** — checked by the Celery wrapper `run_dream_tick` itself, and this is the only check that happens *before any client is built*.
2. **Build clients** (`_build_clients`: sync `redis.Redis` + `VectorClient`).
3. **Redis `SETNX` lock** (`DREAM_LOCK_TTL_SECONDS`) — a tick that loses it returns `{"status": "locked"}` immediately.
4. **Activity scroll** (`_activity_metrics`) — one vector-less Qdrant scroll of up to `_ACTIVITY_SCAN_LIMIT` (5000) active non-dream points, producing both remaining gate signals.
5. **Work available** — ≥ `DREAM_MIN_NEW_MEMORIES` *non-dream* writes since the last **completed** run (`last_completed_at`, not `last_run`; counting only non-dream writes is what stops the pass from feeding itself).
6. **Idle** — no non-dream write within `DREAM_IDLE_MINUTES`, counted directly rather than via Bridge active-sessions or Relay presence, both shown by audit to get stuck. Deliberately *after* the work-available check (`should_run`'s own order): there is no point asking whether a store is quiet before knowing whether it has anything to consolidate.
7. **Generation backend reachable *and serving `LLM_MODEL`*** — a cheap `GET {LLM_BASE_URL}/models` preflight; absent generation reports `health="unavailable"`, never `error` (the `corpus_only` precedent from the Docs→Skills pipeline). The probe checks the *model*, not just the endpoint: live validation showed that with `LLM_MODEL` set to a model the backend does not serve, the endpoint probe passed, the pass walked the entire backlog marking every unit done with zero output, stamped `last_completed_at` and reported `status=complete health=ok` — the exact false-complete this gate exists to prevent, one level down. Model matching mirrors `client/firekeep_client/nightshift.py::_model_available` exactly, including its **leniency**: an empty or unreadable `/models` list means "cannot tell", never "absent", so a backend reporting an unexpected shape can never veto a runnable pass, and ollama's bare-vs-`:latest` tag forms are compared both directions.

Consequence worth knowing before tuning the beat interval: **every tick takes the lock and performs the activity scroll before the gate can close.** Only `DREAM_ENABLED` is free. A disabled-by-gate tick still costs one `SETNX`, one Qdrant scroll of up to 5000 payloads, and a `record_run` write.

**Profiles key on `member_id`, not `agent_id`.** Measured on the live store: `member_id` was uniform across all 538 active memories for one human, while `agent_id` was fragmented into **7 distinct values for that same human** — a hook-minted `agent-<host>-<hash>`, a directory-style `<Surname, Forename>`, a bare `<first-name>`, an OS `<username>`, plus `unknown`, `default` and `legacy-pre-team-continuity` — so keying on `agent_id` would have built seven partial profiles of one person. (Placeholders, not the measured strings: those are a named individual's identifiers and the argument depends on the *shape* of the fragmentation, not on the values.) Profile grouping is `(member_id, workspace_id)` — **exactly the scope `store.profile_point_id` encodes, and nothing more.** `workspace_id` is in the key because it is a tenancy boundary (a hard `must` filter in `VectorClient.search`, derived from the verified principal), so a profile that spans two workspaces is a cross-tenant leak. It is *only* those two because the grouping key and the point id must agree: an interim version grouped on the full tenancy partition `(member_id, workspace_id, namespace, project)`, which is tenancy-safe but means several groups per member all resolve to the same point — and since groups are processed largest-first, each tick overwrote the previous one and **the smallest project group's profile was what survived**, i.e. systematically the worst of the set, plus one wasted LLM call per extra group (measured: a member with buckets of 297/140/63/25 ended up with the 25-memory profile). `namespace`/`project` are consequently *not* group invariants; they are derived for the payload only when the whole group agrees on one value, and left `default`/`None` when it does not — a profile spanning three projects cannot honestly claim any one of them.

**Candidates and clustering (`select.py`, pure):** `status == "active"`, `source` not in `{corpus, dream, dream_profile}` (no dream-of-a-dream, no profile-of-a-profile), `memory_type` in `{episodic, MISSING}` (272 of 538 live active memories carry no `memory_type` at all — filtering on `== "episodic"` alone would silently ignore half the store), `confirmed_count == 0` (a human-confirmed memory is never consolidated), age ≥ `DREAM_MIN_AGE_DAYS`, **and not already consolidated** (below). OWM is the credit signal both ways: a memory below `DREAM_OWM_FLOOR` at `owm_n >= OWM_PRIOR_N` is excluded (a demonstrably misleading episode does not deserve abstraction), and symmetrically a memory with a *proven* track record at that same confidence is also excluded in round 1 — OWM evidence earned by one point does not transfer to a synthesized summary. Clustering is greedy cosine over vectors Qdrant already stores, bucketed first by `(workspace_id, namespace, project)`, `DREAM_MIN_CLUSTER=4`, `DREAM_CLUSTER_THRESHOLD=0.72`, deterministic (sorted by id) ordering.

**"Not already consolidated" is a PERSISTENT Redis set, `dreams:consolidated`** (`DreamState.mark_consolidated` / `consolidated_set`), written with a cluster's member ids only once a dream point for it has actually been *stored*, read once per tick and passed into the pure `select.is_candidate` (which never touches Redis). Without it the pass starved: `select_clusters` returns the first `DREAM_MAX_CLUSTERS_PER_RUN` clusters in deterministic sorted-bucket order and `reset_progress()` wipes the per-run done-set at completion, so **every run re-selected and re-synthesized the identical prefix forever** — proven on 30 clusters across two project buckets at cap 20, where the second bucket was never reached on any run; on the live store the project-less bucket (297 memories) would have consumed the cap and every named-project bucket after it would never have been consolidated at all. `reset_progress()` deliberately does **not** clear this set (only the `cluster`/`profile` done-sets and the `new_memories`/`clusters_done`/`profiles_done`/`errors` counters); it is a property of the store, not of a run, and clearing it restores the bug exactly. Zero-insight clusters write nothing to it — nothing was consolidated, so their members stay candidates for a later run. Because the ledger shrinks the candidate pool each tick, `DREAM_MAX_CLUSTERS_PER_RUN` is now enforced **explicitly** as a per-run budget against the `clusters_done` counter, rather than being enforced accidentally by the same clusters being re-selected until all were done. Two known consequences, stated rather than hidden: the ledger grows without bound (one short id per consolidated memory, no TTL — tens of KB at the live store's scale), and a member all of whose candidate memories have been consolidated forms no profile group, so their profile stops refreshing until new memories age past `DREAM_MIN_AGE_DAYS`.

**Synthesis (`synthesize.py`, `profile.py`):** one LLM call per unit, and since phase 4 **both** go through `llm.chat` — neither builds a request body any more. `synthesize.py` follows `knowledge/classifier.py` exactly: `llm.chat(json_mode=True)`, and **no `content or reasoning` fallback**, deleted for the same reason it was deleted there — under JSON mode an empty `content` means the grammar blocked the output, so `reasoning` is prose by construction and could never have been the JSON. `profile.py` differs in exactly one argument and it is load-bearing — but **the opposite of what this document said until 2026-08-05**. It used to send **no grammar at all** (`json_mode=False`, and before the conversion, the shared JSON body with `response_format` overwritten to `{"type": "text"}`), on the reasoning that a profile is prose so a JSON grammar would fight its system prompt. That reasoning is why the profile half **did not work at all**: **the absence of a grammar is what broke it.** Free-form generation with nothing to terminate it and no constraint on shape, handed to a small model along with a template, produced the template. Measured on the VPS 2026-08-05 (qwen3:4b, 4 vCPU, native `/api/chat`, 90s budget): a prompt-size sweep of 23,486 / 8,546 / 5,627 / 3,815 chars failed **identically at the 240s client timeout at every size** — the flat result is the finding, since a size-driven effect shows a gradient — and `max_tokens=4000` failed at 200s (4000 tokens of prose at the ~6.5 tok/s this box sustains is ~10 minutes, so no budget under it could terminate anything). At smaller caps the model returned **the system prompt echoed back**, then narrated its own procedure (`"- what they consistently ask for / Steps: / 1. Read each memory… / Let's go through the memories: / Memory [0]:…"`) — the **third** recorded instance of one failure here, after phase 1's `_DOC_LLM_PROMPT` placeholder echo and phase 3's mirrored user message. `synthesize.py` never hit any of it, and not by design: `format:"json"` happens to constrain shape enough to stop the echo *and* to terminate generation, so the sibling call was protected by an accident of being JSON-shaped. **The fix is phase 3's mechanism applied here:** `llm.chat(json_schema=_PROFILE_SCHEMA, json_schema_name="dream_profile")` with the minimal schema `{"profile": "<prose>"}` (one required string, `additionalProperties: false` — OpenAI-strict-conformant like `_suggestion_schema`, and deliberately carrying **no** `minLength`/`maxLength`: a grammar cannot decline, only stop, so a length bound truncates mid-word instead of rejecting, and `parse_profile` already owns that check). `json_mode` stays `False` in the call because `llm.chat` coerces it true whenever a schema is present — the module wants *the schema*, not json mode with a schema attached. **`parse_profile` extracts the prose back out, so the STORED payload is still prose** — the grammar is on the wire, not in the store. Extraction (`_extract_profile_text`) must handle **both rungs**, because `llm.chat` answers a pre-generation 4xx by retrying once with the schema dropped, which is what keeps a vLLM/LiteLLM/OpenAI deploy working: `{"profile": …}` → the prose; text that does not parse as JSON → prose as-is (prose is never valid JSON, so that branch cannot swallow a JSON reply); text that **opens with `{` and does not parse** → **refused**, because a completion truncated at the token cap would otherwise be stored as the literal string `{"profile": "Works on…` at the member's deterministic point id and served through every briefing; valid JSON of any other shape → refused, since `{"summary": …}` is not a profile. Extraction runs **inside** `parse_profile`, which is what makes the refusal guard and the `max_chars` bound apply to the prose rather than the envelope — `_looks_like_refusal` windows to the first 200 characters, so a guard on the raw response is defeated by any envelope whose prose starts past it (reachable on the schema-dropped rung, where the model may emit keys of its own first). The completion budget is now **`_MAX_PROFILE_TOKENS = 512`, derived and local**, no longer synthesize.py's imported 4000: the largest *acceptable* completion is `DREAM_MAX_INSIGHT_CHARS`=800 chars plus envelope ≈ 200 tokens at 4 chars/token, ≈330 at a pessimistic 2.5, so 512 is ~1.55x over the worst case — and at ~6.5 tok/s it is ~79s, i.e. **reachable inside the 90s budget**, so a runaway is stopped by the cap rather than by a 90s stall of the `--pool=solo` worker. It is a safety net; **the schema is the terminator**. Retry semantics were **re-decided and deliberately kept at one call, no retry**: the asymmetry that justified that is about the caller, not the response format — a failed profile leaves the previous profile intact, which a cluster has no equivalent of — a retry is a second full generation that could take the tick to a ~3 minute solo-worker stall, and every recorded instance of this failure class was reproducible across runs rather than flaky, so a retry most likely buys the same wrong answer twice. The system prompt's output paragraph changed with it (it used to say "no JSON", contradicting the grammar); nothing else in it did, so the schema stays the attributable variable. `profile.py` **also** loses the `content or reasoning` read, but on a *stronger* argument than synthesize's rather than the same one: not being JSON-mode, its reasoning field IS prose, so the fallback would have stored a model's raw chain-of-thought at the member's deterministic point id and served it through every briefing — the refusal incident below, arriving through a different door. `think:false` is non-negotiable and pinned by a test — without it qwen3 burns its whole budget on blocked thinking and returns empty after ~101s — but see the next paragraph for why sending it is not the same as it taking effect.

**`think:false` is necessary and NOT sufficient — the endpoint is the other half, and the completion budget was a third.** Ollama honours `think` / `chat_template_kwargs.enable_thinking` on its **native `/api/chat`** and silently **ignores both on `/v1/chat/completions`** — which is where `synthesize()` posted, because it built its own body against `LLM_BASE_URL` and that ends in `/v1`. **Since phase 4 of LLM endpoint selection it does not: `synthesize()` calls `llm.chat(json_mode=True, max_tokens=_MAX_COMPLETION_TOKENS)` and gets the native endpoint whenever the backend confirms as ollama.** What that was worth, measured on the VPS 2026-08-04 with the smallest cluster the pass ever attempts (4 members, 2,595-char prompt): **>400s on `/v1`, not completing**, against a 45s budget, versus **22.5s** native — i.e. inoperable, not slow, and the log line it left was `"Dream synthesis failed:"` with a bare `TimeoutError` whose `str()` is empty (now logged with its type). **`profile.py` was converted the same way immediately afterwards**, on the identical argument: it posted to `/v1` under the same 45s budget, so it too could not complete a call on a CPU deploy — and it is the half a human actually sees, since `GET /briefing`'s profile section serves it. A profile prompt is not a cluster prompt, so the >400s figure is not *its* measured latency; what is the same is the reasoning block the endpoint forces it to generate first, produced by the same model under the same budget. That conversion is also what deleted `build_request_body`: it was the shared hand-built `/v1` body, it survived `synthesize()`'s conversion only because `profile.py` imported it, and with no caller left a body builder describing nobody's request is precisely how this module's docstring came to lie in the first place. Measured live against ollama 0.17.5 with the production request body, 3 probes of 3: HTTP 200, `finish_reason='length'`, `completion_tokens=700` (exactly the old hardcoded cap), **content length zero**, reasoning length ~3200 chars; the identical call at `max_tokens=4000` returned correct JSON. Field impact before the fix: 2 of 3 clusters produced **zero** insights, reproducibly, across two full runs — and since a zero-insight cluster is never added to `dreams:consolidated`, those clusters were re-selected and re-attempted on every subsequent run, a treadmill that could never succeed. `synthesize._MAX_COMPLETION_TOKENS` is therefore **4000**, deliberately a named module constant rather than a config field or a function of `DREAM_MAX_INSIGHT_CHARS`: that setting caps insight *content* (800 chars, enforced by `parse_insights`) while the tokens this budget must cover are overwhelmingly reasoning the content cap knows nothing about. It is now **imported directly by `profile.py`** (it used to reach that module inside `build_request_body`) and passed by both callers as `llm.chat(max_tokens=...)`, landing as `options.num_predict` natively and `max_tokens` on `/v1`; deliberately one number, since both calls face the same `/v1` fallback regime and a second constant next door is a thing that drifts. Neither call sends the vendor flags any more — `llm.build_native_body` makes `think:false` unconditional where it is honoured, and `llm.chat`'s `/v1` branch deliberately emits standard OpenAI fields only. **Known interaction:** on `/v1` the reasoning actually gets generated instead of being truncated, so worst-case wall time rises against `DREAM_SYNTH_TIMEOUT_SECONDS=45.0` (the only control that binds under `--pool=solo`); a slow CPU backend can time out where it previously returned fast-and-empty. Both yield zero insights, but the timeout is loud and `GET /dreams` reports `degraded` rather than `ok`. That regime is no longer the default path but it is not gone: any backend that does not confirm as ollama, and any ollama demoted by a pre-generation 4xx, still lands on `/v1`. The remedy for such a deploy was never pointing `LLM_BASE_URL` at `/api` (three embedding call sites concatenate `/embeddings` onto that same variable — see LLM endpoint selection) nor raising the timeout without a measurement; it was routing through `llm.chat`, which phase 4 has now done for both dreams calls.

**A refusal is not a profile (`profile.parse_profile`).** Observed live: the model declined the task ("No human is mentioned in the memories. The text describes system behavior…"), `parse_profile` checked only empty/overlong, and the refusal was stored at the member's deterministic point id and then **served through the briefing** — overwriting the real profile, because a profile is replaced in place. `_looks_like_refusal` now rejects text whose **opening** (first `_REFUSAL_WINDOW_CHARS=200`) matches a specific refusal phrase. It is a **heuristic and documented as one**: a differently-worded refusal still gets through. Windowing to the opening is deliberate — a genuine profile may say "there is no evidence that…" mid-body, and rejecting that would be worse than the defect. The asymmetry it trades on: a false reject costs one skipped refresh (the group is marked done and picked up on a later run, previous profile intact), a false accept injects a non-answer into every briefing. Rejected as too fragile: requiring the profile to mention `member_id`, an opaque `member-<hex>` handle no valid profile has reason to quote. Output is validated, not trusted: strict JSON with one retry on malformed input then the unit is marked done-with-zero-insights (visible, never retried forever); 1–3 insights per cluster, each capped at `DREAM_MAX_INSIGHT_CHARS` (800 chars, ~200 tokens — load-bearing, since `RECALL_TOKEN_BUDGET=600` means one long memory can eat the whole budget and collapse `top_k=3` to 2 results); `source_indices` must reference real cluster members or the insight is rejected.

**Cluster sampling — the prompt is capped, the cluster is not (`DREAM_MAX_CLUSTER_MEMBERS_PER_SYNTHESIS`, default 5).** `synthesize()` used to send EVERY member of a cluster to the model, with no cap, and on the live production store that made most of the pass unrunnable. Measured on the VPS 2026-08-04 (qwen3:4b, 4 vCPU, native `/api/chat` — i.e. *after* both endpoint conversions above — budget `DREAM_SYNTH_TIMEOUT_SECONDS=45s`), against 526 real candidates forming 20 clusters sized `[23,16,10,10,10,9,8,8,7,6,6,5]`: the **uncapped 23-member cluster (~15,000 chars) never completed**, which is exactly what the real tick hit and why the pass wrote zero insights. **Do not tune this off single probes.** A single measurement per size appeared to show a clean size→latency ordering (4 members 38.1s, 5 → 52.0s, 10 → 65.9s), but repeating the SAME capped prompt three times each dissolved it: **cap 4 spanned 12.0–42.9s on identical input (a 3.6× spread), cap 5 gave 29.8–35.8s, cap 6 gave 25.1–35.8s.** On a shared 4-vCPU box the latency is variance-dominated, not size-dominated, so the apparent "5 exceeds, 6 fits at 93% utilisation" ordering does not survive repetition. What *does* survive: **every cap in 4..6 fits the 45s budget and the uncapped cluster never does.** **Capping also improves the output**, which is the durable finding. Same 23-member cluster: capped to 4 → **1** insight; capped to 6 → **3** good, specific insights; uncapped → **0**. That follows from what a cluster is: members are near-duplicates BY CONSTRUCTION (cosine ≥ `DREAM_CLUSTER_THRESHOLD=0.72`), so members past the first handful are largely redundant tokens diluting the signal and eating the generation budget. **The default is 5 for headroom under that variance, not for a winning time**: its worst observed run (35.8s) leaves ~20% of the budget spare, and it clears the prompt's floor of 2 episodes per insight. 4 has a lower median but yielded a single hedged generality; 6 is not measurably slower than 5 and is defensible on a machine that has been measured. `<=0` means no cap, for a deploy that measured its own backend. A cluster at or below the cap is returned unchanged — same members, same order, byte-identical prompt, no centroid computed.

**Which members, and how the provenance stays honest.** `select.sample_cluster` is pure and deterministic like the rest of `select.py`: it computes the cluster **centroid** (component-wise mean of the vectors the module already holds) and keeps the `k` members nearest it by cosine, ties broken by id, returning them in **id order** (prompt position is not a ranking signal, and implying one to the model would be a claim nothing supports). Centrality is genuinely computed, not asserted — a cluster is a threshold neighbourhood around an arbitrary greedy *seed*, so "the first k" would be arbitrary-but-stable rather than representative. When no centroid can be computed (missing/ragged vectors) it degrades to plain id order and says so. **Sampling changes only what the model SEES.** `DreamState.mark_consolidated` still records the WHOLE cluster — marking only the sample would leave the remainder as candidates, they would re-cluster into a near-identical cluster and be re-synthesized forever, which is precisely the starvation `dreams:consolidated` exists to prevent. And because the stored point would otherwise imply all N members were read, `store.build_dream_payload` writes **`dream_cluster_size`** (what the cluster has) alongside **`dream_sampled_count`** (what the model was shown), so "summarised from 5 of 23" is distinguishable from "23 of 23". `dreamed_from` keeps its own older meaning — the ids the model **cited** — which was already a subset before sampling existed; conflating the three loses the citation link. Deliberately **no** derived `dream_sampled: bool`: it is `sampled_count < cluster_size`, recomputable by any reader, and a stored copy is a second source of truth that can disagree the moment one writer sets one field and not the other. The index-mapping hazard is real and guarded: `source_indices` index the PROMPT, so `synthesize()` passes the same `sample` object to both `build_messages` and `parse_insights` — handing the latter the cluster instead would resolve a cited index onto a different, real, in-range memory with no exception and no log line (`test_source_indices_map_to_the_SAMPLED_members_not_the_whole_cluster`). **Not done: `profile.py`.** Its input is not unbounded — `build_profile_messages` already truncates to `_MAX_MEMORIES=40` × `_MEMORY_TRUNCATE_CHARS=600` — so it is a *badly sized* bound, not the same defect, and it was left alone rather than re-tuned unmeasured. Worth knowing that the bound permits ~24,000 prompt chars, ~5.5× the 4,369-char prompt that measured 41.9s on the same box and the same 45s budget, so profile synthesis is very likely exceeding its budget too; that needs its own measurement pass.

A **cluster insight**'s written `memory_type` is **`procedural`, never `reference`** — `parse_insights` forces it regardless of what the model returned, because `reference` means no age decay at all (permanent rank immunity), which an auto-approved unreviewed LLM-generated memory must not get; `procedural`'s 180-day half-life means a dream that stops proving useful fades on its own. **A person profile is the one deliberate exception, and it does get that immunity:** `profile.py::build_profile_payload` writes `memory_type="reference"` (top-level *and* in `metadata`, so recall's projection and GC's top-level read can never disagree), and profiles are returned by ordinary `memory_recall`, so `DECAY_REFERENCE_DAYS=0` really does make `rag.py` skip decay for them. The rationale is structural rather than a carve-out: a profile is **replaced in place** at a deterministic point id on every run instead of accumulating, so there is no growing pile of stale profiles for decay to thin, and decaying the single current profile would only demote the freshest available statement of who a person is. The blast radius is bounded by the profile never being able to feed itself — `select.is_candidate` accepts only `episodic`-or-missing types, and `_scope_filter` excludes `source="dream_profile"` from both the activity scan and the candidate scan. Earlier revisions of this section stated the `never reference` rule without the exception, which made the doc false about the code it named.

**The write path (`store.py`) is dedicated — never `/memory/learn`.** Three reasons: (1) `/memory/learn` runs contradiction detection, which auto-supersedes similar memories within a domain and — until this feature closed the gap — did not check `confirmed_count`, making a dream (by construction a high-similarity summary of a neighbourhood) the single most likely thing to auto-supersede a human-confirmed memory; (2) `VectorClient.upsert` derives the point ID as `uuid5(text)` with no ID parameter, so a dream whose text collides with an existing point would inherit that point's lifecycle (including being born archived) and make "one continuously-updated profile" impossible; (3) `upsert` puts unrecognised metadata in a nested dict while scroll/filter read top-level, which would make `source="dream"` invisible to the very filter meant to prevent dream-of-a-dream. Dreams therefore write through a raw `PointStruct` (the `skills/synthesizer.py` precedent) with **deterministic IDs** — `uuid5(DREAM_NS, cluster_key)` for insights, `uuid5(DREAM_NS, f"profile::{member_id}::{workspace_id}")` for profiles — so re-dreaming updates in place rather than accumulating near-duplicates, top-level provenance (`source="dream"`/`"dream_profile"`, `dream_run_id`, `dreamed_from=[ids]`), and no contradiction detection invoked. Two pre-existing defects this feature required fixing as a precondition, not a bonus: `contradiction.find_similar` gained the same `confirmed_count == 0` guard GC already had (previously *any* `/memory/learn` could supersede a confirmed memory), and `memory_agent`'s duplicate-detection and deep-contradiction passes now skip dream-authored points so the 6-hourly agent can't merge or supersede a dream with no dream code involved. **Both rails exclude `source == "dream"` AND `source == "dream_profile"`** — `app/db/vector.py`'s `_similarity_filter` (the `/memory/learn` contradiction path) and `app/workers/memory_agent.py`'s `_active_non_corpus_filter`. `dream_profile` was missing from both while this document claimed otherwise, which mattered precisely because a profile is broad prose stamped `domain="general"`: a plausible ≥0.85 cosine match for an ordinary general-domain learn, and a point that is *replaced in place* rather than accumulated, so an LLM text-merge or a supersession destroys the one thing the briefing reads by point id. Structurally guarded by `cortex/tests/test_dreams_safety_fixes.py`, which asserts both sources in both filters. Not fixed here and tracked separately: `memory_agent`'s passes still do not check `confirmed_count`, so they can bury a human-confirmed memory — real, pre-existing, and unrelated to dreaming.

**Briefing integration:** person profiles surface as a `profile` section in `GET /briefing` (`app/briefing/sections.py::profile_section`), a direct point-id lookup (`store.profile_point_id`, never a vector search — the id is already known). Degrades to `status: "empty"` — never `unavailable` — when no profile exists yet, which is the normal state on every fresh install before the first dream run, not a failure. The section is registered **unconditionally** so the briefing envelope carries a fixed section set on every deployment, but it short-circuits to `empty` on `DREAM_ENABLED=false` — otherwise every `GET /briefing` on every deployment in existence spends a Qdrant retrieve on a point that cannot exist. It also refuses to render a profile point whose `status != "active"`: a direct point-id read bypasses every lifecycle gate ordinary recall applies, so without that check a superseded or archived profile would keep being served forever.

**`GET /dreams`** (`app/dreams/api.py`) — status endpoint: `{enabled, last_run, clusters_done, profiles_done, insights_written, errors, health}`, `health` one of `ok`/`degraded`/`unavailable`/`error`/`unknown` (`unavailable` is the generation-backend gate above; `unknown` is the pre-first-run state). `clusters_done`/`profiles_done`/`insights_written` are read from the `dreams:run` hash (`record_run` writes them there); **`errors` is read from the `dreams:counter:errors` key instead**, because the error path bumps that counter and then calls `record_run(status="error", ...)` with no `errors` field — reading it off the hash made the number structurally always `0`.

**`insights_written` and the `degraded` verdict are what make the endpoint able to report a barren run.** Without them a run that wrote 6 dreams and a run that marked every unit done and wrote 0 returned an **identical** body (`{"clusters_done":3,"profiles_done":2,"errors":0,"health":"ok"}`) — which is how the live token-starvation above passed for healthy across two full runs. Two changes: (1) `insights_written` is a real per-run cumulative total (a `dreams:counter:insights_written` bumped per written insight, cleared by `reset_progress` like every other per-run tally, and **mirrored into the run hash on every working tick** — `record_run` was already being handed an `insights_written`, but it was *that tick's* count, so the hash held whatever the last tick did). It is read from the **hash**, deliberately unlike `errors`: the counter is cleared at completion, so reading the counter would report `0` for the run that just finished, precisely when an operator wants the number. (2) a completed run that **attempted one or more clusters and wrote zero insights** records `health="degraded"`, not `ok`. `errors` structurally cannot cover this — `synthesize()` never raises by contract, so `run_one_unit`'s outer `except` (the only thing that bumps `errors`) is unreachable on an LLM failure. Deliberate limit: a run that attempted *no* clusters is still `ok` (nothing to write is not a failure), and a profile-only run that wrote no profiles is also `ok`, because a profile write is not an insight and this counter measures one thing. Router mounted only when `DREAM_ENABLED` (the Collectors precedent: a disabled deploy 404s rather than returning a disabled-shaped body). Reads the same `dreams:run` Redis hash `DreamState` writes, but not through `DreamState` itself — `DreamState`'s methods are synchronous, built for the Celery task's own sync `redis.Redis` client (mirroring `memory_agent.py`'s lock/counter pattern), so the async FastAPI request path reads the hash directly via the shared async `get_redis` dependency instead. No dashboard tab or Operations-surface row in round 1 (see Deliberately out of scope below) — deliberately not invented; the dashboard's existing "Collectors" card (Knowledge tab) is a list of source *adapters* and dreaming is not one, so it does not belong there either.

**Deliberately out of scope for round 1:** archival of consolidated constituents (round 2, gated on LongMemEval measurement); a GPU/hybrid client-side drain; a dashboard tab or Operations row; graph-side (Neo4j) consolidation — archiving a vector does not remove its content from the graph leg, so round 1 does not reduce graph noise; SSE recall parity (`recall_streaming` applies no lifecycle/OWM multipliers, so it is excluded from any dreaming A/B claim).
