## LLM endpoint selection (`cortex/app/llm.py`) — phases 1–3
One entry point, `llm.chat()`, owns which endpoint a chat call goes to, how the body is built, and how the response is normalised. **Ollama honours `think:false` on its NATIVE `/api/chat` and silently IGNORES it — along with `chat_template_kwargs.enable_thinking` — on `/v1/chat/completions`**, so a thinking model generates its full reasoning on `/v1` no matter what is sent. The saving is endpoint-level and therefore model-independent.

**Measured 2026-08-04, live on the VPS (ollama 0.32.4, qwen3:4b, 4 vCPU, inside the cortex container), identical two-procedure document in every probe:** `GET /api/version` → `200 {"version":"0.32.4"}`; native `/api/chat` with `{stream:False, think:False, format:"json"}` → 16.18s cold / **4.00s warm**; the same call with `stream` OMITTED → NDJSON, 35 lines, `json.loads` raises; with `think` OMITTED → **111.20s** and 3552 chars of `thinking`; `/v1/chat/completions` with the pre-change classifier body → **83.19s**, 1978 chars of `reasoning`, 26 content tokens. That is 83.19s → 4.00s (20.8x; the audit measured 87x on a larger document). Alternating warm runs of the real `classify_document` on the same document: native 5.50–6.29s vs `/v1` 66.50–96.67s.

**Three facts taken from the wire, not from a design document.** `format` and `think` are TOP-LEVEL siblings of `stream`, while `temperature`/`num_predict` live inside `options`. **`"stream": False` is mandatory** — omit it and ollama streams NDJSON, `resp.json()` raises `JSONDecodeError`, which is not an httpx type and carries no `model`, so `classifier._is_backend_unavailable` returns False and every ingest goes terminal `failed`; `build_native_body` always emits it and a parametrised test asserts it on every argument combination. And **with `think:false` the response's `message` has NO `thinking` key at all** (not present-and-empty), so `parse_native_response` uses `.get()` — a subscript would raise on every successful call.

**Selection is derive-then-probe with an explicit override.** Strip a *required* `/v1` suffix off `LLM_BASE_URL` to get a native root (no suffix → never native), confirm it with one `GET {root}/api/version` accepted only on 2xx **and** a JSON object carrying a `version` key (a catch-all proxy answering 200 must not be mistaken for ollama), and **fail toward `/v1` on anything unconfirmed** — `/v1` is the contract, native is the optimisation. A vLLM/LiteLLM/OpenAI backend simply never confirms and is unaffected; its body also stops carrying ollama-only vendor flags, which real OpenAI 400s on (both `dreams/synthesize.py` and `dreams/profile.py` sent them unconditionally until phase 4 converted them, and got away with it only because `DREAM_ENABLED=false`; no call site builds a `/v1` body by hand any more). The verdict is cached per root, positive for `LLM_NATIVE_PROBE_TTL_SECONDS` (600s) and negative for `min(60, ttl)` — the asymmetry exists so a probe that fails transiently while ollama restarts cannot pin every call onto the slow path for ten minutes. A pre-generation **4xx (400/404/405/422/501)** demotes the cached verdict and retries once on `/v1`, so an older ollama that rejects `think` degrades instead of failing hard; **5xx and timeouts propagate unretried** because they may arrive mid-generation. (`422` joined that set in phase 3 for the structured-outputs fallback — vLLM's server is FastAPI, whose request-validation rejection is a 422 rather than a 400, and it is pre-generation exactly like the other four.) `llm.chat` RAISES on transport/HTTP failure and never swallows — `classifier.py` inspects the caught exception to choose between `corpus_only` and `failed`, and a helper that returned an empty result would collapse that distinction.

**There is deliberately no `asyncio.Lock` around the probe cache — do not "fix" it.** The Celery worker runs `--pool=solo` and drives async code through a fresh event loop per task; a module-level `asyncio.Lock` binds to the loop that first acquires it and raises in every later one. The benign race costs a few duplicate 2s probes on cold start; the lock would cost a crash in the worker.

**Repointing `LLM_BASE_URL` at `http://ollama:11434` is NOT a valid workaround.** Eleven chat sites concatenate `/chat/completions` onto that variable and **three embedding sites concatenate `/embeddings`** (`db/vector.py`, `workers/reembed.py`), so repointing breaks every memory write. `config.py`'s `DREAM_SYNTH_TIMEOUT_SECONDS` comment used to recommend it as the remedy for the `/v1` reasoning cost; phase 4 removed that recommendation and the comment now says explicitly that repointing is **not** the fix, naming the three embedding sites. (The line reference this paragraph carried — `config.py:205-216` — was stale as well as wrong: that range is now the `DECISION_SYNTH_TIMEOUT_SECONDS` block. Cite the setting, not the line number; line numbers in a 400-line settings class are a claim that expires on the next edit.)

**Converted so far (and deliberately not the rest):** phase 1 — `knowledge/classifier.py` and both `skills/synthesizer.py` chat calls (the docs→skills pipeline is the only path simultaneously on by default and currently failing, and the only one that stalls the solo worker for ~20 minutes); phase 2 — `decision/synthesize.py` (below); phase 4 — **both** `dreams/` chat calls, `synthesize.py` then `profile.py` (the deferral being paid off: measured 2026-08-04 on the VPS, the SMALLEST cluster this pass ever attempts — 4 members, a 2,595-char prompt — took **>400s on `/v1` and did not complete**, against a `DREAM_SYNTH_TIMEOUT_SECONDS` of **45.0**, versus **22.5s** native; a real dream tick logged a bare `TimeoutError` with an empty `str()` at 47.3s and wrote 0 insights, so dreaming was INOPERABLE on a CPU deploy rather than merely slow. `profile.py` posted to `/v1` on the same 45s budget and had the identical defect — and it is the user-facing half, since `GET /briefing`'s profile section is what serves a profile. Converting it retired `synthesize.build_request_body`, the shared hand-built `/v1` body that had survived the first half of the phase only because profile.py imported it). **Not converted:** `workers/sleep_cycle.py` (deferred out of phase 2 — see below) and `engine/rag.py` synthesis/rerank plus `mcp_server.py` handoff (never this round — off by default, or the hot recall path). This split is intentional blast-radius management, not an oversight: **do not sweep the remaining sites in one unreviewed change**, since sleep_cycle's failure path writes the DLQ and rag.py is the hottest path in the system. (This sentence used to name a count. It was written as "six" when `dreams/profile.py` was still on the list, and a number in prose is a thing that goes stale one conversion later — read the list, not the count.)

**Timeouts are per-endpoint, but NOTHING WAS ACTUALLY REDUCED — and that is the finding, not a failure of nerve.** `KNOWLEDGE_CLASSIFY_TIMEOUT_SECONDS` stays **300** for `/v1` (a thinking model measured 288.9s there — 3.7% headroom) and `KNOWLEDGE_CLASSIFY_NATIVE_TIMEOUT_SECONDS` exists as a separately tunable native budget that also **defaults to 300**. It was 120 for one review cycle and that was wrong. **The trap is that "native" does not imply "fast":** the native path is faster only because it disables THINKING, and the probe confirms *ollama*, not *a thinking model*. The office deploy runs **llama3.2:3b — a non-thinking model — so it is routed down the native path and gains nothing**, keeping its recorded ~56s classify while its headroom would have fallen 5.4x → 2.1x. Measured 2026-08-04, a non-thinking model also *accepts* `think:false` cleanly rather than 4xx-ing (`llama3:latest` 3.10s, `gemma3:4b` 1.94s, both `keys=['content','role']`), so the demote-and-retry escape hatch never fires for it either. Since `classify_document` sends the whole document untruncated while the crawler admits 2MB pages, a document ~2.2x the measured one would newly time out — and the office helm chart (separate config repo) sets none of these vars, so it would have inherited that with nobody deciding. Against that, a native classify measures ~6s, so 120 vs 300 only changes how fast a *broken* call gives up. **`SKILL_SYNTH_TIMEOUT_SECONDS` stays 300 with NO native sibling**, because skill drafting is **generation-bound, not reasoning-bound**: measured natively with `think:false` already in effect, generation runs at 5.9–7.2 tok/s and `done_reason` is `length` at every cap tried (300/400/500/800), so the model never stops on its own and `SKILL_SYNTH_MAX_TOKENS` × the token rate simply IS the cost of a draft (800 tokens → 112–135s). A 120s native budget was tried and **failed all three drafts of a real ingest at exactly 120.13s each**. `SKILL_SYNTH_MAX_TOKENS=800` is new and is the real cost control — both synthesis calls previously sent no output bound at all.

**Read timeouts are no longer reported as an absent backend.** `classifier._is_backend_unavailable`'s isinstance tuple named bare `httpx.TimeoutException`, which `httpx.ReadTimeout` subclasses — so a classify that exhausted its budget against a deployed, reachable, answering backend was recorded terminal **`corpus_only`** with a note promising classification "will run automatically once a generation model is deployed". Nothing ever re-enqueues a `corpus_only` source, so the document stayed silently corpus-only forever on a healthy deploy. `ConnectTimeout` stays named explicitly (it subclasses `TimeoutException` too, but means nothing answered, which genuinely is unavailable). The classifier's `reasoning`-field fallback is also deleted: under JSON mode an empty `content` means the grammar blocked it, so `reasoning` is prose by construction and could never have been the JSON.

**Phase 2 — the Decision Board (`cortex/app/decision/synthesize.py`).** Its suggestion pass was **inert on every thinking-model ollama deploy, and had been since SP4 shipped**: bounded at `DECISION_SYNTH_TIMEOUT_SECONDS=20.0` against a `/v1` call that generates the full reasoning block first (83.19s on a comparable body, 288.9s in the audit), so `suggested_answers`/`suggested_actions` came back empty every time while the retrieval half worked. The board is a shipped, documented, website-advertised feature. Retrieval was never at risk and still isn't — it runs before the LLM pass and outside its `try`, so `evidence`/`knowledge_found` are returned whatever the suggestion call does. **The failure was also invisible, not merely silent:** `_llm_suggest` answered any exception with `{}`, an ordinary return, so `synthesize_board` reported **`degraded: false, note: ""`** on a board that had produced nothing — a connect error against a generation-less deploy (the office embed-only ollama image is a real shipped configuration) looked healthy on every call. Only the `asyncio.wait_for` timeout escaped that, and only by accident: it cancels, and `CancelledError` is a `BaseException`. `_llm_suggest` now raises and the caller sets `degraded=True`. **`DECISION_SYNTH_TIMEOUT_SECONDS` 20.0 → 30.0** — 30 is simultaneously what the client already assumed (`client/firekeep_client/decision/server.py`'s `_DEFAULT_SYNTH_TIMEOUT = 30.0`, under a comment claiming to mirror a server default it did not match) and the most it can wait for (that file derives its HTTP timeout as synth + `_INGEST_TIMEOUT_HEADROOM` 15.0 = **45s**, so past 30 needs a coordinated client release, not an env change). 20 was below the floor even for the fast path: at the measured 5.9–7.2 tok/s it buys ~120–145 output tokens, less than a suggestion JSON for three questions. **No native sibling here, unlike classify** — a native budget could only be *lower*, which is exactly what strands non-thinking-model deploys. **No `max_tokens` either, unlike skill synthesis** — this call is JSON mode, so the grammar ends generation on its own and a cap can only truncate valid output into invalid, converting a slow success into a guaranteed `JSONDecodeError`; on `/v1` a cap is also spent on reasoning tokens before the answer starts. **Honest ceiling, measured live on the VPS after the change** (qwen3:4b, native `/api/chat`): 1 question **20.98s**/57 output tokens and 3 questions **16.31s**/111 tokens both fit; 8 questions is **37.28s**/239 tokens and still degrades. So small boards now get suggestions and a full board does not — and the binding constraint is **wall clock at ~6.5 tok/s, not output size** (239 tokens is a small answer that still costs 37s; an earlier ~400–550 estimate was high). The remaining lever is the prompt, not the budget. **Raising the budget also halved the recall margin** (the client's 45s is fixed, so `45 − synth` went 25s → 15s): the recalls run `format="raw"` so there is no generation on that path, but each does one **always-cold** embed (LRU-keyed by content hash), and `RERANK_ENABLED=true` would add `top_k × multiplier` LLM calls per recall × 9 — already over the old 25s, so not a new regression, but do not enable it on a CPU backend and expect this endpoint to answer. `sleep_cycle.py` was **deferred out of phase 2**: converting it needs a sync `chat_sync()` wrapper (it uses `httpx.post`, not `AsyncClient`) and its failure path writes the consolidation DLQ, and the cheap confirmation the design asks for — `GET /ops/queues` `event_dlq` non-zero and climbing — has not been run.

**Phase 3 — structured outputs, because fixing the endpoint and the budget was necessary and still not sufficient.** Re-measured on the deployed VPS after phase 2: the board completed in **15.07s** (no timeout), reported **`degraded: False`**, and returned **`answers=0 actions=0` on every question**. Dumping `_llm_suggest`'s raw return showed why — the model had **mirrored the USER MESSAGE back** (`{"context": ..., "questions": [{"id":"q0",...}]}`, one run corrupting a key to `"evidence_sn:"`), ignoring the system prompt's `{question_id: {suggested_answers, suggested_actions}}` contract entirely. **`format:"json"` and `response_format:{"type":"json_object"}` constrain output to SYNTACTICALLY VALID JSON AND NOTHING MORE — neither enforces a schema**, and a small model handed a JSON input under a syntax-only constraint reproduces the input's shape. The same class of failure is on record from phase 1, where qwen3:4b echoed `_DOC_LLM_PROMPT`'s template placeholders instead of filling them in. **Measured 2026-08-04 on the VPS** (ollama 0.32.4, qwen3:4b, this exact prompt, three questions): `format:"json"` → 20.62s / 16.31s, **0/3 answered on both runs**; `format:<json schema>` → 16.55s / 14.81s, **3/3 answered on both runs**, top-level keys exactly `['q0','q1','q2']`. **Adherence went 0→100% and latency did not get worse** — a constrained decode emits fewer wasted tokens, which roughly cancels the grammar's cost. `minItems:1` was measured (24.51s for the same 3/3) and **rejected**: no adherence gain, so it buys only latency and pressure to invent. Schema latency still scales with the answer, not with the constraint — n=1 8.16s, n=3 22.95s, n=8 52.75s (43/126/328 output tokens) — so **a schema does not make a big board fit a small budget**; the 8-question ceiling from phase 2 stands. `llm.chat` gained `json_schema=`/`json_schema_name=`, threaded to ollama's native `format` (the schema object goes in the same field that otherwise carries the string `"json"`) and to `/v1`'s standard `response_format: {"type":"json_schema", "json_schema": {name, strict:true, schema}}`. **Additive by construction:** a caller that passes no schema gets byte-identical bodies, so the classifier, the skill synthesizer and dreams are untouched. A schema also **implies `json_mode`**, so the fallback below cannot degrade to prose. **Non-Ollama safety is the ladder, not a flag.** There is no capability endpoint to feature-detect structured outputs against, so `chat` reuses the mechanism already in the file: attempts run most-capable-first and each rung drops exactly ONE capability, so a pre-generation 4xx is answered by giving up the least it can — schema first, endpoint second. A vLLM/LiteLLM/OpenAI deploy that rejects `json_schema` therefore retries once **on the same endpoint** without it and keeps working at pre-schema quality. Dropping the schema natively **does not demote the native verdict** (the endpoint was never the problem; demoting would push every later call in the process onto the 83.19s path for an unrelated fault), and there is deliberately **no `/v1`+schema rung** under a failed native+schema — on ollama both endpoints are the same engine, so that rung buys only a wasted round trip. **Applied to `decision/synthesize.py` only.** `knowledge/classifier.py` was measured and deliberately left alone (see below). `skills/synthesizer.py` is `json_mode=False` free-form Markdown — there is no JSON for a schema to constrain, and its phase-1 placeholder-echo needs a prompt fix, not a grammar. **And the silent half is fixed too:** `synthesize_board` reported `degraded: False` whenever the LLM returned successfully but its payload matched **no** question ids — structurally identical to the swallow phase 2 closed, one level down. It now counts what actually grounded and reports `degraded=True` with `note="suggestions-unusable"` (payload named none of the board's ids — the model answered a different question) or `"suggestions-empty"` (ids matched, every list empty), logging the offending top-level keys. A board that grounded *something* is not degraded, so the flag keeps its meaning. **Three review follow-ups, all in the honesty class.** (1) The detector counts `present` (id is a key), `usable` (its value is a dict) and `grounded` separately — collapsing the first two made it log `0/1 question ids present` while printing `top-level keys=['q0']` in the same line, a self-contradiction inside the one diagnostic that exists *because* the last bug took three phases to find; the `empty`/`unusable` split keys off `usable`, so an id present with a garbage value is still `unusable`. (2) `_string_list` discards a non-list suggestion field: `[str(a) for a in (v or [])]` turned a bare string into **one entry per character** (`"Restart the worker"` → 18 "suggestions" shown to the human) and a dict into its keys, with `degraded=False` — pre-existing and unchanged by phase 3, but the schema-dropped rung is exactly where an unconstrained model emits one. Discarded, not coerced: wrapping invents structure the model did not produce, and leaving the question ungrounded is a state this module already reports. (3) The structured-outputs diagnosis in `llm.chat` moved from the retry (where only the *fact* of a refusal is known) to **after the same endpoint accepts the identical request without the schema**, which is the only evidence the schema was the objection — an old ollama rejecting `think` was previously told it "appears not to implement structured outputs" one line before the demote message giving the real reason.

**Config:** `LLM_NATIVE_CHAT=auto|always|never` (default `auto`), `LLM_NATIVE_PROBE_TTL_SECONDS=600.0`, `LLM_NATIVE_BASE_URL=""` (only for an ollama-native backend whose root cannot be derived). Structured outputs are a per-call argument, not an env var — there is nothing to configure and nothing to turn off. Guards: `cortex/tests/test_llm.py` (**71 cases**, 54 of them pre-phase-3) plus a `conftest.py` autouse reset of the module-global verdict cache — without it a verdict decided in one test leaks into later ones, order-dependently. Phase 2 adds 9 cases to `cortex/tests/test_decision_synthesize.py` (the first to exercise `_llm_suggest` at all — every pre-existing case patched it out, which is how the silent-success bug survived review) and two compose/`.env.example` default-drift guards in `test_decision_config.py`. Phase 3 adds **17** cases to `test_llm.py` (both body shapes, the no-schema byte-identity check, the schema-implies-json-mode coercion, the `/v1` reject-and-retry across all five demote codes, the 5xx no-retry, each rung of the ladder, and the two log-honesty cases below) and **14** to `test_decision_synthesize.py`, now **30** (schema shape, no-`minItems`, no-schema-for-an-empty-board, the mirrored-input payload, `empty` vs `unusable`, partial grounding, one malformed entry not abandoning the rest, the four non-list suggestion types, and the two `present`-vs-`usable` log assertions).
