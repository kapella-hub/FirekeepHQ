## Proactive Recall — pushed memory at every prompt (client 1.0.3)

Why it exists: the live compliance table measured fleet-wide "recall before
you answer" at 46% and "recalled knowledge used" at 35% — the Keep was
accumulating faster than it was consulted, because recall was pull-based and
the one push (the session-start briefing) matches only the session's original
goal. Design record:
[`docs/superpowers/specs/2026-08-18-proactive-recall-design.md`](../superpowers/specs/2026-08-18-proactive-recall-design.md).

On every user prompt, the prompt hook sends the prompt text to
`POST /memory/recall` (`top_k: 3`, `format: "raw"`, `trigger: "prompt-hook"`)
and injects the few genuinely relevant, not-yet-seen memories as a
`[firekeep recall]` system message — or, far more often, injects nothing.
The noise discipline (this hook's own field-complaint history):

- Prompts under 24 collapsed characters or starting with `/` are skipped.
- The relevance floor reads **`metadata.raw_score`** (cosine / graph blend),
  NEVER `MemorySource.score` — the normalized score's best entry is exactly
  1.0 by construction (measured 2026-08-06: a knitting-patterns nonsense
  query scored 1.0), so flooring on it would admit noise on every prompt.
  Sources without `raw_score`, and `degraded: true` (graph-only) responses,
  inject nothing — unknown relevance fails dark, not loud. The same rules
  the Bridge briefing's `proactive_recall` consumer already applies.
- `format: "raw"` is load-bearing: synthesized recall runs an LLM pass that
  cannot fit the hook's 2.5s budget (SP0 C6's lesson, reused).
- Per-session dedupe: an injected memory id is not injected again (scratch,
  12h TTL); at most 3 per prompt, one trimmed line each.
- Fail-open: any error or timeout logs to hooklog and injects nothing.

| Knob | Default |
|---|---|
| `FIREKEEP_NO_RECALL_PUSH` / `[recall] push = false` | on by default |
| `FIREKEEP_RECALL_PUSH_MIN_SCORE` | 0.55 (raw scale) |
| `FIREKEEP_RECALL_PUSH_TIMEOUT_SECONDS` | 2.5 |

Coverage, honest (`contract/matrix.py` row `proactive_recall`): per-prompt on
Claude Code and Kiro; none on Codex (no hooks), OpenCode (bridge delivers no
prompt text) and generic MCP — for those, the session-start briefing remains
the only push.

**Measurement note (round-2 contract precedent):** a pushed recall raises
"recall before you answer" mechanically from this release's exposure date.
The `trigger` field on `ContextQuery` is carried into the `memory_read`
replay payload so deliberate vs pushed recall stays sliceable; the frozen
founding predicates themselves do not change, and "recalled knowledge used"
remains the honest judge — it is the number this feature exists to move.

## Prior Art — the Keep answers a declared goal (server v1.2.0 + client 1.2.1)

The third push surface, closing the loop the owner named: "someone on the team
builds something, someone else asks to build something similar — Firekeep
should know." The moment an agent declares a goal (`ctx_start_session`),
Bridge assembles a `prior_art` block into the tool's response: a raw recall
against the goal (`trigger: "prior-art"`, the 0.55 raw-score floor — same
calibration as proactive recall, same reason: the normalized score is 1.0 by
construction) plus up to 3 OTHER agents' in-flight session goals, unfiltered
on purpose (a wrong omission costs more than a short list at team scale).
Fail-open with a 2.5s budget: session creation is never hostage to it.

Measured motivation: "build a backup and restore system for our server"
recalls the Keep Backup release memory at raw 0.63 — above the floor — so
distilled sessions (night-shift's output) are exactly the fuel this runs on.
The instruction layer adds the pull-side twin: before building something
substantial, check `memory_recall` + symdex `get_similar_symbols` — the
compliance table measures whether agents actually do.

Coverage note: works for every runtime (it rides the MCP tool response, not
hooks). The code-level push (post-tool "you just wrote a near-duplicate of an
existing function") is deliberately round 2 — it needs care to not be a nag.

## Intelligence Features (Cortex)

- **Memory types**: `reference` (no age decay by default), `procedural` (180d), `episodic` (90d), `transient` (14d). Direct learns default to episodic unless the caller supplies a type; the sleep-cycle LLM classifies knowledge extracted from raw event streams.
- **Multi-hop graph**: 3-hop traversal with 0.5x decay per hop. Config: `MULTIHOP_ENABLED`, `MULTIHOP_MAX_HOPS`.
- **Proactive recall**: Bridge auto-queries Cortex on `ctx_update` for plan/progress. Injected into shadow as "Relevant Past Experience."
- **Episodic distillation**: Session completion preserves full decision/progress sequences with `→` separators and file paths.
- **Archive-first aging**: GC scores each active memory as `(age/half_life) × 1/(1+ln(access+1)) × (1-confidence) × (0.5 + (1 − owm_efficacy))` — the last factor is OWM's (neutral 1.0 when unscored or `OWM_ENABLED=false`). Eligible memories are archived with preview/audit/restore, not deleted. Confirmed memories, skills and corpus chunks are protected; hard purge is explicitly opt-in and off by default.
- **Token-conscious recall**: Results trimmed to `token_budget` (≥2 results always kept) then optionally synthesized by LLM into coherent Markdown. Config: `RECALL_TOKEN_BUDGET=600`, `RECALL_SYNTHESIS_ENABLED=false`. Synthesis is opt-in because a slow generation backend can add its full timeout; set `format="raw"` to skip synthesis for an individual recall.
- **Outcome-Weighted Memory (OWM, `cortex/app/owm.py`)**: recall ranked by real-world results — the nightly Celery pass (`app.owm.run_owm_scoring`, interval `OWM_SCHEDULE_HOURS=24`) joins replay `memory_read` events (which now stamp the RETURNED `memory_ids` — `app/main.py` recall handler) to session outcomes (auto-evals `failure_rate` bands: ≤0.2 success, ≥0.5 failure, middle band EXCLUDED; Bridge `abandoned` overrides as failure; eval `outcome` as fallback), computes Beta-shrunk efficacy `(s + P/2)/(n + P)` per memory (`OWM_PRIOR_N=5` — neutral 0.5 at low N by construction), and writes `owm_efficacy`/`owm_n`/`owm_updated_at` onto Qdrant payloads. Recall applies `score × (1 + OWM_WEIGHT·2·(eff−0.5))` in the lifecycle scorer (`OWM_WEIGHT=0.15`, clamped; absent field or `OWM_ENABLED=false` → bit-identical to pre-OWM ranking); the GC composite score gains an efficacy factor (neutral 0.5 bit-identical; misleading memories archive up to 1.5× faster). Deterministic end to end — no LLM, no ML (the deleted recall-ranker lesson); the pass recomputes from scratch each run over `OWM_WINDOW_DAYS=30` (matching the 30d eval TTL — a larger window is dead weight) and DELETES the OWM keys from previously-scored memories with no in-window evidence, so penalties decay back to neutral rather than ratcheting (no death spiral). Fairness: sessions count ONCE per memory, one agent identity contributes at most `OWM_AGENT_CAP=5` observations per memory (a CI bot's failing loop can't bury shared memories), and corpus chunks/skill points are excluded from scoring (skill points — as of PR3, 2026-08-24, below — get their OWN distinct scoring pass instead of being dropped; corpus stays fully excluded, unchanged). Kill switch is total: `OWM_ENABLED=false` neutralizes the recall multiplier AND the GC factor (stale payload values ignored). Scope caveats, documented: applies to `POST /memory/recall` only — the SSE streaming path applies the lifecycle gate but not the lifecycle/OWM score multipliers (pre-existing divergence, still open); the OTHER half of this caveat, that the streaming path did no `memory_ids` stamping either, is RESOLVED 2026-08-24 — see the recall/feedback receipts bullet below; abandoned-session detection rides Bridge's 200-newest status window (best-effort beyond it). **The input signal was measurably degenerate, and that was a finding about the system rather than about this module (2026-08-06, surfaced by Living Procedures) — RESOLVED 2026-08-23, see below.** Grep over the whole repo at the time: **no production emitter passed a real `outcome=` to `replay.emitter.emit` except Bridge’s session-lifecycle calls** (`bridge/app/mcp_server.py`, hard-coded `success`/`partial` regardless of what actually happened) and one in `cortex/app/main.py` — `agent.action.predict`, `agent.action.reconcile`, `memory_read` and `memory_write` all passed none. Since `_failure_rate` (`evals/scorers.py`) divided over *events that carry an outcome*, and returned `0.0` when none did, a typical completed session had exactly one such event, it said success, `failure_rate` was `0.0`, and the old `session_success` read `0.0 <= 0.2 → True` — so **effectively every session in the deployment evaluated as a success**, and `owm_efficacy` converged toward "everything worked" while the recall multiplier discriminated far less than the design intended. The Living Procedures prerequisite fixed the gateway half (`agent.action.reconcile` now emits a real `outcome=`), but a mechanical edit almost always succeeds, so it sharpened the signal only slightly; the load-bearing signals that actually existed were Bridge’s `abandoned` status and the RPC-succeeded stamp at session completion — which was not the same thing as task success. Knowledge Autopilot round 1 (2026-08-09) attacked the degeneracy from two flanks without repointing `session_success` (see [`knowledge-autopilot.md`](knowledge-autopilot.md)): the Bridge session reaper abandoned idle-active sessions so walked-away work finally lands in the failure class Bridge `abandoned` already feeds (previously those sessions sat `active` forever and counted as nothing), and the feedback multiplier (`FEEDBACK_*` settings, same Beta-shrink and clamp shape as OWM, applied as a separate factor in the lifecycle scorer) added a direct human/agent judgment channel that does not route through session outcomes at all — a session can succeed while one recalled memory was misleading, and a thumb records exactly that. **Outcome truth (2026-08-23) is the measurement pass that finally repoints `session_success`:** it no longer reads `_failure_rate` at all — it reads the raw stored eval JSON and checks the recognized `(task_result, task_result_source)` pair itself (`recognized_grade_pair`, the one grade-validity check every consumer imports), where "success"/"failure" pass through and "partial", a sourceless grade, or an absent/legacy record return `None` (excluded from the join, never guessed), with Bridge `abandoned` still overriding everything as a failure regardless of grade. The grade comes from `ctx_complete_session`’s optional `task_result` param, bound to the session’s verified owner and stored first-graded-wins, so `outcome=` on the `session_end`/`session.completed` replay events now carries the real self-reported grade (or nothing, honestly, when the caller never graded) instead of the old hard-coded RPC-succeeded stamp — see `bridge-context-and-briefing.md` and `replay-evals-patterns.md` for the full mechanism. This does not by itself make `owm_efficacy` well-calibrated: most sessions still complete with no grade at all, so the excluded population stays large and the shrinkage prior still dominates at low N — it means the signal that exists is finally the right one instead of a constant. Read `owm_efficacy` numbers against `outcome_event_count` and how many sessions actually carry a recognized grade, not against the pre-2026-08-23 degeneracy above, which is now history.
- **Recall/feedback replay receipts (2026-08-24, outcome truth PR2):** `POST /memory/recall/stream` (SSE) now emits its own `memory_read` replay event in a `finally` after the stream — fires on normal completion or client disconnect either way — carrying `memory_ids`/`result_count`/`trigger`/`namespace` but no `top_score` (same reason as the non-streaming path: it's a post-normalization max pinned at 1.0 by construction, not a signal). It also bumps `memory:access_counts` / `memory:last_recalled` for every recalled id and the untagged-call counter (`/admin/untagged-calls`), matching the non-streaming recall handler's bumps. SSE-recalled memories are therefore no longer invisible to OWM's nightly join (which keys on `memory_read`'s stamped `memory_ids`, per the bullet above), to compliance/audit review, or to the staleness clock — the `memory_ids`-stamping half of the scope caveat above is closed; the score-multiplier half is unchanged. Separately, `POST /memory/feedback` now emits a `memory_feedback` replay event — `{memory_ids, useful, comment_present, updated}`, the comment body itself never leaves the request — so the thumb that drives the `FEEDBACK_*` multiplier (described above) is now a replay-visible, auditable receipt at the moment it's applied, not just a Qdrant payload mutation.
- **Skill efficacy (2026-08-24, outcome truth PR3):** The same nightly OWM pass now ALSO scores skills. The retrieve/exclude loop above used to drop every `memory_type=="skill"` point unconditionally; it now routes them into a separate tally instead, gated independently by `SKILL_OWM_ENABLED` (default `true`) — the pass entry runs whenever `OWM_ENABLED` **or** `SKILL_OWM_ENABLED` is on, so a deployment can score skills without turning on the memory recall multiplier and vice versa, and `SKILL_OWM_ENABLED=false` makes the whole skill branch bit-neutral (memory path unaffected). Scored skills are written to a DISTINCT `skill_efficacy`/`skill_efficacy_n`/`skill_efficacy_updated_at` payload field — **never** `owm_efficacy`, because the RAG lifecycle scorer (`rag.py:1187-1192`) and the GC composite factor both read `owm_efficacy` with NO `memory_type` guard, so a skill carrying that field would be silently re-ranked and aged as if it were a memory. The tally consumes two signals: the `memory_read` exposure receipt — `skill_recall`'s `record_recall=true` path now emits one (skill ids, `result_count`, `trigger="skill_recall"`, no `top_score`, same shape as the receipts above); the briefing's skills section still deliberately does not, since an impression is not a deliberate reach — and the `memory_feedback` applied signal, joined **grade-independently** (unlike the memory join above, which requires a recognized session grade) and **skills-only**, so it never reaches the shared `stats` used for `owm_efficacy` and never double-counts against the `set_feedback` counter (`rag.py:1194+`) that already counts memory feedback. Same stale-reset discipline as the memory path: a skill scored in a prior run but absent from this run's evidence has its three `skill_efficacy*` keys deleted rather than left stale. Surfaced read-only via `SkillResponse.skill_efficacy`/`skill_efficacy_n`/`skill_efficacy_updated_at` and the autopilot inbox's `low_efficacy_skills` section (see [`knowledge-autopilot.md`](knowledge-autopilot.md)) — unlike memory's `owm_efficacy`, `skill_efficacy` has no ranking or eviction effect yet (deferred).
- **Team continuity**: All memories carry `project` and `agent_id` (contributor) fields. `GET /memory/contributors` reports per-contributor activity. `POST /memory/handoff` generates an LLM-synthesized handoff brief for a project. `memory_handoff` MCP tool wraps this.
- **Recall scope on the graph leg — a real fix for handoff, a PARTIAL MITIGATION for recall.** `query_related`/`query_related_multihop` take a namespace and nothing else — no `project`, no `workspace_id` — so a scoped recall was answered by a vector leg that honoured the scope and a graph leg that ignored it. Proven live: a handoff for a project that **does not exist** returned HTTP 200 narrating another project's work, and every leaked row arrived tagged `(graph)`. It is a cross-**workspace** hole, not merely cross-project. `rag.py::_scope_verdict` now adjudicates each graph row against the Qdrant payloads of the memories it names. **What that actually closes, measured 2026-08-06:** of the **5459** nodes `query_related` can return (`Domain|Concept|Action|Outcome|Resolution`), only **27 carry `memory_ids`** — **0.49%**. `POST /memory/handoff` passes `unattributed_graph="deny"` and IS fixed (verified live: the nonexistent-project probe goes 2 sources → 0, which is also what first makes its `{"empty": true}` short-circuit reachable). `POST /memory/recall` keeps `"admit"` and is therefore **only partially mitigated**: `workspace_id` is non-None on every authenticated recall, so denying unattributable rows would not scope the graph leg, it would delete 99.51% of it from every request. Closing the rest needs project/workspace properties written onto graph nodes at extraction time plus a 5459-node backfill, and a decision about what a project-scoped recall should do with sleep-cycle knowledge that legitimately belongs to no project. Not fixed, and not claimed to be. Guards: `cortex/tests/test_handoff_graph_scope.py`, `cortex/tests/test_recall_scope_leaks.py`.

## Memory identity v2 — scoped point identity, the v1 bridge, and quarantine (2026-08-28)

Design record: [`docs/superpowers/specs/2026-08-27-memory-identity-v2-design.md`](../superpowers/specs/2026-08-27-memory-identity-v2-design.md). The defect this closes: a learned memory's identity used to be its text alone — `uuid5(FIREKEEP_UUID_NAMESPACE, text)` — so identical text learned in two workspaces landed on ONE Qdrant point: the first workspace's memory left its own recall, the second workspace's write silently took it over, and `_merge_lifecycle` carried the first workspace's `agent_id`/`project`/`created_at` forward under the second's ownership. Proven live by a LongMemEval retest: two clean identical-input ingests over the same fixture differed on 3,677 point owners.

**The v2 scheme (D1).** A memory's Qdrant point id is now `uuid5(FIREKEEP_UUID_NAMESPACE, seed)` where `seed = json.dumps(["mem2", workspace_id, normalize_namespace(namespace), text], separators=(",",":"), ensure_ascii=False)` — JSON-array encoding, not delimiter-joined, because text may contain any delimiter a join would need. `mem2_seed()` and `memory_point_id()` (`cortex/app/db/vector.py`) are the one place this is built; a guard test asserts no bare `uuid5` over memory text exists anywhere outside that helper and the migration tool. **Fail-closed minting:** `VectorClient.upsert()`'s `point_id is None` branch — the mint path used by transfer imports and the backfill drain, the two callers that omit `point_id` — raises `VectorStoreError` when `metadata["workspace_id"]` is empty; there is no unscoped mint. `/memory/learn` itself never hits this branch: `main.py` precomputes the identical `memory_point_id(workspace_id, namespace, text)` and passes it explicitly as `point_id=` (D2 — the same precomputation the v1 bridge below has to account for) — a verified `workspace_id` is already required to reach that call, since it comes from `require_scope`. Callers that pass an explicit `point_id` are exempt because their ids are already scoped by a different scheme: corpus (`corpus/store.py:175-184`, source-scoped `corpus_point_id`, still routed through `upsert()`) and dreams (`upsert_point`, raw deterministic ids, a separate method entirely). `transfer.py`'s import now OVERRIDES any `workspace_id`/`member_id` carried in the imported item with the request principal's — never `setdefault` — closing both an unattributed import (`workspace_id=None`) and a hand-crafted body asserting a foreign workspace.

**The immutability invariant.** Namespace, workspace_id and text are identity INPUTS, so no code may `set_payload` any of them without re-keying the point — an in-place mutation would silently desynchronize the stored payload from the id that is supposed to derive from it. `upsert()` normalizes the namespace ONCE at its top (`normalize_namespace`, from `app.models`) and reuses that same normalized value for both the stored payload and the seed, so the payload-derivability invariant holds by construction even for a caller that passes a raw namespace (transfer.py does). The one-time task `workers/migrate_namespaces.py`, which used to mutate payload namespaces in place with no re-keying, is deleted under exactly this invariant (its Celery `include` entry in `workers/sleep_cycle.py` removed with it).

**The graph gets the same boundary (D4).** Chain-node identity (`Neo4jClient._content_hash`) is now computed over the same canonical `[kind, workspace, namespace, node-text]` shape, applied per node (action/outcome/resolution); `CONTENT_HASH_LENGTH` truncation is unchanged. `find_similar` gained a required `workspace_id` filter, closing cross-workspace auto-supersession (`contradiction.detect_and_supersede` previously ran with no tenancy boundary at all). Existing chain nodes are **not** re-keyed — splitting an already-merged node would need ownership facts the MERGE already destroyed — so the migration instead stamps `legacy_unscoped: true` on every node whose id matches the v1 hash of its own text. `rag.py::_scope_verdict` checks `legacy_unscoped` FIRST, before its own "nothing is scoped, admit" early return, and denies unconditionally regardless of the `unattributed` lever: a legacy node's own identity is untrustworthy (it may have MERGEd rows from more than one workspace before the migration could tell them apart), so no coincidental agreement with the declared scope rescues it. This is the graph analogue of vector quarantine below, and — like it — disclosed as **permanent**: recovering per-workspace ownership on these nodes isn't possible.

**The v1 bridge — transitional (D5).** v2 code deploys before the migration runs, so during the compatibility window a relearn of pre-existing text would otherwise mint a fresh v2 point beside its v1 original and, worse, resurrect an archived/superseded/deprecated memory as a brand-new ACTIVE point — defeating `_merge_lifecycle`'s core invariant. `MEMORY_ID_V1_BRIDGE` (default `true`) gates ~10 lines in `upsert()`: on a v2-id lifecycle-prefetch miss, it also retrieves the OLD point (`_v1_point_id(text)` — bare `uuid5(FIREKEEP_UUID_NAMESPACE, text)`) and feeds that payload into `_merge_lifecycle`, so status, counters, archive provenance, and `created_at`/`agent_id`/`project` all survive into the v2 twin. It has to cover two id sources: a minted id (`point_id=None` — transfer/backfill) AND `/memory/learn`'s shape, where `main.py` precomputes the identical `memory_point_id` and passes it in explicitly (D2) — the primary relearn path, and the one D5 exists to protect. There is no reliable way to tell "an explicit id that happens to equal the scheme" from "the route computed it itself", so the bridge recomputes the scheme id and compares equality (`is_memory_scheme_id`); a caller-supplied id from a different scheme (corpus, dreams, skills) fails the equality check and the bridge correctly doesn't fire — a formula divergence fails safe. Regression-tested: archive a memory, relearn its exact text, assert it does not come back active. **Retire after the migration** — once every point in the live collection carries a v2 id, the v1 lookup is a permanent miss and the flag can be turned off.

**Quarantine — invisible on both recall legs, adopted only by an explicit admin act.** A memory-shaped payload with no verified `workspace_id` (an orphan the migration finds on the live store, not something new code can create — fail-closed minting prevents fresh ones) is copied at its EXISTING id with `workspace_id: "__quarantine__"` (`QUARANTINE_WORKSPACE`, `cortex/app/workspace_migration.py`) plus `legacy_unscoped: true`. No real principal ever holds that workspace id, so the vector leg's ordinary `workspace_id` filter excludes it from every recall exactly like any other workspace would, and the graph leg's `_scope_verdict` denies it via the same `legacy_unscoped` check above — uniformly invisible on both legs, never "recallable but only via the graph" (which review proved was true of an earlier design). `migrate_single_workspace()` (`main.py`, runs at every `cortex-api` boot) is now gated on its own completion marker (`MEMORY_MIGRATION_KEY` — previously written, never read) AND explicitly skips quarantine/`legacy_unscoped` points via `_is_quarantined()` — without both, the first restart after a freeze migration would silently adopt the whole quarantine bucket into the deployment's single workspace. Adopting a quarantined point back into service is a deliberate admin act (a manual payload edit reassigning `workspace_id`), not an automated recovery path.

**D9 — disclosed follow-ups, out of scope for this branch:**
- Skills' ids (`SKILL_NS`, `cortex/app/skills/synthesizer.py`) don't fold workspace — same defect shape (`uuid5(SKILL_NS, "source::title")`, no tenancy input to the seed), and skills write via a raw `AsyncQdrantClient.upsert()` call that bypasses `memory_point_id` entirely.
- Graph `Domain`/`Concept` nodes keep their existing global text keying (unchanged).
- `rag.py`'s admit-by-default for unattributable graph rows is narrowed only for `legacy_unscoped` rows here — the broader gap described in the "Recall scope on the graph leg" bullet above (99.51% of graph nodes carry no `memory_ids` at all) is untouched by this branch.
- `_merge_lifecycle`'s field semantics are unchanged; D5's bridge only changes what can reach it.
- `CONTENT_HASH_LENGTH` sizing is unchanged.

Config: `MEMORY_ID_V1_BRIDGE`, `MIGRATION_FREEZE` — see `docs/guides/cortex-configuration.md`. The freeze-copy-cutover migration itself (the tool, its state machine, and the operator runbook) is documented in [`docs/guides/backup-and-restore.md`](backup-and-restore.md#migration--the-identity-v2-freeze-runbook).

## Secrets Vault (`vault/`)
Encrypted secret storage for infrastructure credentials, API tokens, and connection strings. Uses Fernet symmetric encryption with values encrypted at rest in Redis DB 7 (shared with auth, distinct key prefix `vault:secret:`).

**MCP Tools:** `vault_store`, `vault_retrieve`, `vault_list`, `vault_delete`
**REST Endpoints (on Cortex :8100):** `POST /vault/secrets`, `GET /vault/secrets/{key}`, `DELETE /vault/secrets/{key}`, `GET /vault/secrets` (list metadata only)
**Config:** `VAULT_ENABLED=true`, `VAULT_KEY=<fernet-key>` (required), `VAULT_REDIS_URL=redis://redis:6379/7`
**Generate key:** `python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"`

## Corpus (`corpus/`)
Business knowledge documents chunked and stored in Qdrant for semantic recall. Chunks are naturally discoverable via `memory_recall` (tagged `source=corpus`). Source metadata tracked in Redis. Corpus stores chunks only — there is no entity/relationship graph (a former Neo4j extraction path was removed; see `docs/HISTORY-NOTES.md`).

**MCP Tools:** `corpus_ingest`, `corpus_sources`, `corpus_delete`
**REST Endpoints (on Cortex :8100):** `POST /corpus/ingest`, `GET /corpus/sources`, `DELETE /corpus/sources/{source_name}`, `DELETE /corpus/dex-sources/{source_id}` (bulk — one bounded call removes every tracked source named `docdex:<source_id>:<file>` in the caller's workspace)
**Config:** `CORPUS_ENABLED=true`

**Tenancy is stamped at write time.** `corpus.pipeline.ingest_document` had NO workspace parameter at all, so every point written through `POST /corpus/ingest`, `POST /knowledge/ingest` and `POST /skills` landed with `workspace_id=null` — and `memory_recall` applies `workspace_id` as a hard Qdrant `must`, so none of it was retrievable. Measured live, same query: with `workspace_id=None` the freshly ingested chunk was the TOP hit at 0.8193; with the caller's real workspace it was ABSENT and recall returned unrelated 0.58 matches. A probe skill scored 0.877 at rank 1 unfiltered and vanished under the filter. All five PRE-EXISTING corpus chunks carried a real workspace, because the startup `migrate_single_workspace` backfill heals orphans — which made the damage window "until someone restarts cortex-api" (24h on that box) rather than permanent, and is why this looked intermittent. A migration is not a substitute for stamping at write time. The principal's `workspace_id`/`member_id` now thread from the request through `ingest_document` → `store_chunks`, through `ingest_knowledge_document` → the `classify_and_draft_from_doc`/`draft_skill_from_doc` Celery kwargs → the draft skill payload, and into the `POST /skills` payload. Worker-only paths that have no HTTP principal (`run_url_ingest`, the Confluence collector) stamp the DEPLOYMENT workspace explicitly rather than leaving null. Values are emitted only when known, never as an explicit `None`: `upsert` promotes them to top-level payload keys, so writing null on a re-ingest would overwrite whatever the migration had backfilled. Guards: `cortex/tests/test_ingest_tenancy.py`.

**Member visibility, typed documents, authz and the generation gate (Docdex Phase V — spec `docs/superpowers/specs/2026-08-15-docdex-design.md` §4).** Ingest accepts `source_type="document"`, a `visibility` field (`"workspace"` default; `"member"` = visible only to the ingesting member) and a bounded client `metadata` dict (≤16 keys, ≤2048 chars JSON-serialized, str→str only; the server-controlled keys `workspace_id`/`member_id`/`visibility`/`ingest_id`/`source_name`/`chunk_index`/`total_chunks`/`committed` are rejected 422, never silently overridden). `visibility` is stamped explicitly on every new chunk; ABSENCE keeps its legacy meaning ("workspace"), which the shared visibility-filter builder (`cortex/app/db/visibility.py`) honors at every member-principal egress — both recall paths and the source listings; a caller with no member identity gets no private chunks (fail closed). The dashboard and `/memory/export` are OPERATOR surfaces under the spec's threat boundary (member-private hides from other members, not from the server operator) and deliberately do not consume the builder. Source records carry server-stamped ownership (`workspace_id`, `member_id`, `visibility`, `dex`) and list/delete/re-ingest are principal-aware: a private source — whose NAME is itself private data — lists and mutates only for its owner or an admin key; a cross-workspace name answers 404 exactly like a missing one (no existence oracle); `docdex:`-prefixed names are reserved, so writes and deletes need the `dex:docdex` scope (or admin) even for the owner. Corpus point identity is source-scoped (`uuid5(workspace|source|ingest|chunk)` — identical text across sources or members never collapses to one point, so deleting one member's source can never remove another's chunk; memory points keep text-derived dedup). Re-ingest is generation-gated: chunks are written `committed: false`, one `set_payload` flips the whole run live at swap completion, and recall excludes uncommitted chunks — a mid-ingest failure leaves the old generation fully live and the partial new one invisible until the next successful ingest sweeps it. The bulk route removes a whole dex client source in one call, driven from the tracked source records (then per-source exact-name Qdrant deletes — never a prefix query) and returns `{deleted_sources, deleted_chunks}`, where `deleted_chunks` is `"unknown"` unless the store reports real counts (it currently does not — the number is never fabricated). Guards: `corpus/tests/test_ingest_visibility.py`, `test_point_identity.py`, `test_source_authz.py`, `test_committed_generation.py`, `test_bulk_delete.py`, `cortex/tests/test_visibility_builder.py`.

**Usage:** Agents ingest docs via `corpus_ingest` (copy-paste text or fetch URL first). Corpus chunks are tagged with `source=corpus` and `tags=["corpus", source_type, source_name_slug]` so they appear in regular memory recall alongside operational memories. Re-ingesting a source with the same name automatically replaces old content via a staged swap (new chunks are written and committed first; the previous generation is deleted only afterward, so a mid-ingest failure leaves the old content intact).

## Memory Improvements (`cortex/app/`)
Phase 1–3 upgrades for storage hygiene, retrieval precision, and team continuity.

**Phase 1 — Storage Hygiene:**
- Archive-first aging: `score = (age/half_life) × 1/(1+ln(access+1)) × (1-confidence) × (0.5 + (1 − owm_efficacy))` (OWM factor neutral at 1.0 when unscored/disabled). Confirmed memories, skills and corpus chunks are protected. Eligible active memories are recoverably archived; hard purge is disabled by default.
- Dedup threshold: `DEDUP_SIMILARITY_THRESHOLD=0.78` (replaces old fixed 0.85)

**Phase 2 — Retrieval Precision:**
- Token budget: trims results to `RECALL_TOKEN_BUDGET` tokens (always keeps ≥2), then optionally synthesizes via LLM
- `format` param on `memory_recall`: `"synthesized"` (default) runs LLM synthesis, `"raw"` skips it

**Phase 3 — Team Continuity:**
- `project` and `agent_id` fields on all memories; `project` is normalized to lowercase
- `agent_id` = contributor identity (person's name). An interactive `firekeep install` prompts for it (default: the configured value, else the OS username) and writes it to `[identity]`. `CHANGEME` remains the skeleton value only on a non-interactive install that passed no `--agent-id`. `FIREKEEP_AGENT_ID` still overrides the configured identity per-process.
- `/memory/learn` reads `X-Agent-Id` / `X-Session-Id` from request headers and persists them to the Qdrant payload (top-level fields, so `/memory/contributors` and project filters can read them directly). Default is `"unknown"` when headers are absent.
- **Recall returns provenance** (`app/db/vector.py: _projected_metadata`, `app/engine/rag.py: _provenance_suffix`). `upsert` promotes `_PROMOTED_PAYLOAD_KEYS` (`agent_id`, `session_id`, `project`) to top-level payload AND strips them from the nested `metadata` sub-dict; `search`'s projection named only source/tags/domain/timestamp, so the promotion moved them out of the one place the reader looked and every memory written since reported no author at recall. The projection now derives those keys from the same constant (emitting them only when present, so a pre-promotion record keeps its nested value instead of being overwritten with `None`), and `_format_markdown` appends ` — {agent}, {YYYY-MM-DD}` to each line. `agent_id="unknown"` and the legacy sentinel render as nothing rather than as noise; `session_id` reaches `sources[].metadata` for auditing but is never rendered (32 hex chars an LLM cannot use). This matters beyond attribution: without it a caller cannot tell a teammate's memory from its own session's output, which is what made recall look effective while measuring nothing.
- **Recall returns feedback handles.** `RecallResponse.memory_ids` is the ordered, de-duplicated list of stable Qdrant IDs represented by returned vector sources and graph rows linked through `memory_ids` (maximum 50). The MCP `memory_recall` rendering appends those exact values as a directly callable `memory_feedback(memory_ids=[...], useful=...)` footer in both raw and synthesized modes. It emits no footer when a result has no attributable memory. Agents should submit feedback only for recalled knowledge they actually acted on; the IDs are a machine handle, not additional prose for the model to interpret. The same list drives access counters and `memory_read` replay receipts, so feedback and outcome-weighted recall refer to the same returned set.
- Legacy sentinel: memories created before the `agent_id` field was wired (~3.9K records) are tagged `agent_id="legacy-pre-team-continuity"` via `cortex/scripts/backfill_legacy_agent_id.py`. The backfill is idempotent and only touches records with `agent_id` missing or `"unknown"` AND `timestamp` before today's UTC date.

**MCP Tools (updated/new):**
- `memory_recall` — now accepts `token_budget=600`, `format="synthesized"`, `project=None`; top_k default 3
- `memory_handoff` — generate LLM handoff brief for a project: `memory_handoff(project, since_days=7, agent_id, session_id)`

**REST Endpoints (on Cortex :8100):**
- `GET /memory/contributors?project=X&since_days=7` — list contributors with activity stats
- `POST /memory/handoff` — body: `{project, since_days}` — returns synthesized handoff Markdown. Scoped on both legs: it passes `unattributed_graph="deny"` so a graph row that cannot be attributed to the requested project is refused rather than narrated (see the recall-scope bullet above; `/memory/recall` deliberately keeps `"admit"` and is only partially mitigated).
