## Replay Engine (`replay/`)
Structured trace log across all services. Every memory read/write, session update, environment change, and coordination event is recorded with trace links (observed/declared/inferred).

**Emitters by service:**
- Cortex emits `memory_read` and `memory_write` on every `/memory/recall` and `/memory/learn` (tagged with `X-Session-Id` / `X-Agent-Id` from request headers, defaulting to `"unknown"` when absent — see `/admin/untagged-calls` for discipline visibility).
- Bridge emits `session.started` / `session.updated` / `session.completed` / `session.abandoned` on the corresponding `SessionManager` lifecycle methods, best-effort with lazy import and exception swallowing.
- Relay emits `coordination` events for presence updates, claims, and direct messages.
- Sentinel emits `env_change` events for container, git, and file activity.
- Agent Gateway emits `agent.action.predict` / `reconcile` events for the predict-then-act surface.

**MCP Tools:** `replay_timeline` (default limit=20), `replay_inspect` (opt-in `brief=True` for one-line payload summary), `replay_context_at`, `replay_narrow`, `replay_summary`

**`replay_narrow` answers three outcomes, not one.** An empty `suspects` list had three causes and one shape, so the tool gave a byte-identical reply for a real event id and for `deadbeefdeadbeefdeadbeefdeadbeef` — echoing the fabricated id back with the same confident sentence. That matters more here than usual: a census of the 3,000 most recent events in `rp:events` (27,305 total) found `parent_span_id` populated **0** times and `trace_links` populated **0** times, every event carrying `trace_id == span_id == id`, so the one message was covering "no cause found", "no such event" AND "this feature has no data". `replay/narrowing.py::narrow` now returns `failure_event_found` and `session_has_trace_links` (defaults keep the body backward-compatible) and the MCP tool prints a distinct sentence for each — including one that says plainly that the deployment records no trace links and points at `replay_timeline` instead. Neither field changes the ranking. **Not fixed:** the emitters still pass no `parent_span_id`/`trace_links`, so narrowing remains structurally inert until they do; that is instrumentation work across cortex/bridge/relay/sentinel, not a bug in the algorithm. Guards: `replay/tests/test_narrowing_outcomes.py`.
**REST Endpoints (on Cortex :8100):** `GET /replay/sessions/{sid}/events`, `GET /replay/events/{eid}`, `GET /replay/sessions/{sid}/context-at/{eid}`, `GET /replay/sessions/{sid}/summary`, `POST /replay/sessions/{sid}/narrow`
**Config:** `RP_ENABLED=true`, `RP_REDIS_URL=redis://redis:6379/6`, `RP_RETENTION_DAYS=30`, `RP_STREAM_MAXLEN=100000`

## Auto-Evals
Computes quality metrics from replay traces on session completion. 11 Tier 1 metrics (directly measurable): tool_success_rate, memory_freshness_at_recall, failure_rate, claim_contention_rate, outcome_event_count, etc.

**`outcome_event_count`, and why the briefing stopped saying "quality looks good" (2026-08-06).** `_failure_rate` and `_tool_success_rate` are both ratios over events that CARRY an outcome, and they disagree about the empty case: `_tool_success_rate` returns `None` (filtered out of the metric dict — an honest "cannot tell"), while `_failure_rate` returns `0.0` (indistinguishable from "no failures"). Since no production emitter passes `outcome=` except Bridge's session-lifecycle calls, a completed session holds ~48 events of which exactly ONE carries an outcome — the session reporting its own success. Measured live on the owner's store via `GET /briefing`: 19 sessions, `event_count` 48.3158, `tool_success_rate` 1.0, `failure_rate` 0.0, `sessions_with_failures` 0. Neither of `quality_section`'s thresholds (`tool_success_rate < 0.9`, `failure_rate > 0.1`) can fire against those, so its unconditional else-branch — `insights.append("quality looks good")` — ran on every request. **It read as a verdict while being a constant, on the first thing a human reads about their own system** (the dashboard-health-check failure class: not "no signal" but "confident wrong signal"). `_outcome_event_count` is added so a reader can tell an informative `0.0` from a vacuous one, and `quality_section` now reports `no failure signal (N outcome-bearing event(s) per session) — thresholds cannot fire, so this is not a clean bill of health` below `_MIN_OUTCOME_EVENTS_FOR_A_VERDICT` (2.0, chosen so it fires only on today's degenerate ~1 and self-silences once real instrumentation lands), and the factual `no quality threshold breached across N session(s)` otherwise. A threshold that DID fire is still reported as-is — a real problem is evidence regardless of sample size — and an eval predating the counter gets the neutral wording, since absence of the counter is not evidence of degeneracy. **`_failure_rate` itself is deliberately unchanged**: `owm.session_success` and the Living Procedures Tier B gate both key off it, so flipping it to `None` repoints two shipped signals and is its own measurement pass, not a fix in passing. Guards: `cortex/tests/test_quality_verdict_is_not_a_constant.py` (12 tests, including a discriminator that runs the pre-change branch against the live numbers and asserts it produces the reassuring string).

**`memory_freshness_at_recall` was pinned at 1.0 for the same structural reason (2026-08-06).** `RecallResponse.score` is `max()` over per-entry scores that `engine/rag.py::_min_max_normalize` has already rescaled, and that function sets the best entry in the set to exactly **1.0 by construction** — so the field reads 1.0 whenever ANY result survives the score floor, however poor the match. Measured live through `POST /memory/recall`: *"how do I deploy to the VPS"* → `1.0` (sources `[1.0, 0.6091, 0.4537]`), *"what is the qdrant collection name"* → `1.0`, and a deliberate nonsense query, *"zzz nonsense query about knitting patterns"* → **`1.0`**. The nonsense query is the proof that this is a constant and not a relevance signal. The replay `memory_read` payload carried it as `top_score`, `_memory_freshness_at_recall` averaged it, and the briefing duly reported `memory_freshness_at_recall: 1.0` across all 19 evaluated sessions — a freshness proxy documented as *"stale memories tend to score lower"* that is incapable of reporting staleness, its only job. **This is the same defect already found and fixed one layer over**, for the recall confidence band in `_format_markdown`, whose comment states the principle: *a band that cannot come out low is not a band*; that fix reads `metadata["raw_score"]`, the pre-normalization value (cosine for vector entries, the weighted jaccard/distance blend for graph ones). The same remedy is now applied to the metric: `main.py::_raw_top_score` emits `raw_top_score` beside `top_score`, skipping entries that carry no `raw_score` (resolution bonuses carry a sentinel `1.2`) so they cannot prop the value up, and returning `None` rather than `0.0` when nothing carries one. `_memory_freshness_at_recall` prefers it and falls back to `top_score` for older events, so history stays readable — but those events are the pinned kind, so judge trends on windows after 2026-08-06. **`RecallResponse.score` is deliberately NOT repointed**: it is a public response field and changing its meaning is breaking; it is documented as normalized instead. Guards: `cortex/tests/test_recall_score_is_normalized_not_relevance.py` (19 tests, including a discriminator that runs the pre-change reader and asserts it returns 1.0 on the events the new one scores 0.21).

**`brier_score` (predictor calibration) is structurally unpopulated, and that is correct until agents declare predictions (2026-08-10).** Measured live: 31 evaluated sessions, `brier_score` absent from every one. The scoring chain itself is sound — `agent.action.predict` events keyed by `action_id`, joined to `agent.action.reconcile` events, Brier over (stated confidence, reconciled match score) pairs, verified emitter-to-consumer — but the only real gateway traffic is the pre-edit hook, and the hook deliberately sends **no prediction**: it is a shell script gating an edit it cannot predict the outcome of. With no stored prediction, `record()` scores `None` and the pair is excluded, so Brier is never computable. **The wrong fix is fabricating hook confidence** — a constant synthetic prediction would produce a calibration number that measures nothing about any agent, the "confident wrong signal" class this guide documents twice above. The right fix shipped instead: the instruction layer (client rendered block + Cortex MCP handshake) now tells agents to declare consequential actions via `action_before(..., confidence=)` and reconcile via `action_after` — the `decision_board`/`memory_feedback` lesson a third time: a capability nothing instructs agents to use does not exist. The `action_before` docstring also states that confidence is what makes a prediction scorable. The dashboard's Calibration card already handles absence honestly ("No prediction events yet"). Expect `brier_score` to stay absent until instructed clients (0.1.40+) generate declared-prediction traffic; a populated value before that would itself be suspicious.

**`EvalResult` attribution fields (Living Instructions round 2, 2026-08-12).** `EvalResult` gains optional top-level fields read from the `session_start` replay payload the eval already loads — Bridge persists the five `X-Firekeep-*` headers there at `ctx_start_session` (see `bridge-context-and-briefing.md`): `runtime`, `client_version`, `instructions` (`{rendered, expected, gateway}` — only the keys whose headers actually arrived), `briefing_delivered` (`bool(session_start payload briefing_id)` — the fetch receipt that already existed; `None` when the timeline has no `session_start` at all, which is absence, not `False`), and `agents` (already computed per session by `get_session_summary` and previously discarded). All optional with defaults so every record stored before this release keeps parsing, and **`metrics` stays `dict[str, float]` — attribution is never a metric**: a runtime label averaged into a quality score would be the category error the whole layer exists to prevent. **Nothing backfills.** Eval writes never overwrite and the 30-day TTL (`RP_RETENTION_DAYS`) bounds the population, so for a full window after rollout the store legitimately mixes attributed and unattributed records; sessions from pre-0.1.41 clients carry no headers and read as unattributed **forever** — the compliance table's `unknown` exposure bucket discloses them rather than smoothing them into either side. A backfill that guessed would be manufacturing exposure evidence for sessions that recorded none.

**`ctx_working_state` measures agent discipline, not hook capture — the cb36570 relabel asserted the opposite of the code (spec Correction 1, 2026-08-12).** `_context_snapshot_count` counts events carrying a `context_ref` (`cortex/app/evals/scorers.py:220`), and the only writer of `context_ref` in the codebase attaches one exclusively when `ctx_update` is called with `category` `"decision"` or `"plan"` (`bridge/app/mcp_server.py` — the `category in ("decision", "plan")` gate in `ctx_update`'s replay emit, ~:386-400 after the attribution changes; the spec cites the pre-shift :341). Every hook write — stop, prompt, precompact — is `category="scratch"`, emits `context_ref=None`, and is never counted. So the founding measurement's 62% was agent plan/decision discipline all along, and the external-review relabel that claimed "the per-turn stop-hook snapshot also satisfies this" was itself wrong: the review confirmed the finding by call-site reasoning (stop hook calls `ctx_update`; `ctx_update` feeds the counter) without checking the category gate between them. The lesson is the one this guide keeps re-earning — verify the full emitter→scorer path before publishing a claim on a measurement surface. It also retires the round-2 item "an agent-driven variant needs an event the hook does not emit": the distinction already exists structurally.

**`POST /evals/sessions/{sid}/compute` is gated on `eval:write` OR `admin`** (`require_any_scope`, the helper added for the vault read routes — FastAPI ANDs stacked dependencies, so two `require_scope` calls cannot express OR). It was `admin`, and Bridge posts to it on EVERY `ctx_complete_session` carrying `FIREKEEP_INTERNAL_KEY` — whose scopes are `memory:write, session:read, eval:read, eval:write` and deliberately NOT admin (`deploy/bootstrap-keys.sh` says so in a comment). So every completion got HTTP 403, Bridge treated 4xx as permanent and never retried, and the live logs read `Eval trigger permanent failure for session ...: HTTP 403` on every session. Measured: all 19 stored evals carried `trigger="manual"` and the newest was **12 days stale** against 225 indexed sessions and 54 completed in the recent window. Blast radius is everything downstream of eval outcomes — OWM's ranking signal joins replay `memory_read` events to auto-eval outcomes and had no fresh evidence; quality trends and regression detection were frozen; the pattern A/B tip-effectiveness join had nothing to join. `eval:write` already exists, is already granted to the internal key, and is exactly what this endpoint does; `admin` gates decrypted vault reads and key minting. **`admin` is kept alongside it rather than replaced by it, and that is required, not belt-and-braces:** `keys.scopes_allow` treats only `"*"` as a superset, NOT `"admin"`, so swapping the gate outright would have 403'd every key holding a literal `["admin"]` and no wildcard — including the one that could call this endpoint before the change. Widening a gate must not narrow it for somebody else. Two honesty fixes came with it: `trigger` is now a request parameter instead of the hardcoded `"manual"` (Bridge sends `session_complete`, so "all evals say manual" stays diagnosable), and `ctx_complete_session` reports `eval_triggered: "dispatched"` rather than `"scheduled"` — the call is detached by design (SP0 D5), so the response CANNOT know the eval computed, and it claimed otherwise throughout the outage. Bridge logs a permanent 4xx at ERROR now, not WARNING. **Not done:** surfacing repeated eval-trigger failures on the dashboard Operations tab. Guards: `cortex/tests/test_evals_compute_scope.py` (including a behavioural check that an `["admin"]`-only key still passes the real dependency), `bridge/tests/test_fire_and_forget_eval.py`.

**MCP Tools:** `eval_session`, `eval_summary`
**REST Endpoints (on Cortex :8100):** `GET /evals/sessions/{sid}`, `GET /evals/summary`, `POST /evals/sessions/{sid}/compute`, `GET /evals/trends?window=N`

**Quality Trends (`cortex/app/self_diagnosis.py`):** Compares recent N sessions vs previous N to detect improving/stable/degrading trends per metric. Dashboard Evals tab shows trend arrows. `detect_regressions()` returns metrics that have degraded beyond threshold.

## Pattern Engine (`cortex/app/patterns/`)
Background analysis that discovers what strategies work across sessions. Extracts features from replay traces (tool sequences, memory usage, file paths, duration, outcome), runs 6 pattern detectors, and produces strategy cards with confidence scores.

**Pattern Detectors:** memory-first usage, file hotspots, tool sequence correlation, memory usage levels, session duration buckets, failure mode detection.

**Pattern Categories:** `procedural` ("do X before Y" — briefing eligible at trial+), `risk` ("area X has elevated failure rate" — briefing eligible at trial+), `behavioral` ("sessions with trait X succeed more" — analytics only, never shown in briefings). Detector mapping: memory_first/tool_sequence → procedural, file_hotspot/failure_mode → risk, memory_usage/duration → behavioral.

**Promotion Ladder:** `candidate` → `observed` → `trial` → `validated` → `stale` → `retired`, with `quarantined` as a side state reachable from any stage. Only `trial` and `validated` procedural/risk patterns appear in briefings (max 3 tips). Promotion criteria: observed (evidence ≥ 10, confidence ≥ 0.3), trial (evidence ≥ 15, confidence ≥ 0.5, stable), validated (evidence ≥ 25, confidence ≥ 0.65, positive tip lift). Patterns go stale after 30 days without matching sessions.

**Hard Limits:** Max 50 active patterns (candidates excluded from count). Confidence decay: -0.02/week without new supporting sessions. Auto-retirement when confidence drops below 0.2. Duplicate descriptions are deduplicated on creation.

**Quarantine:** Instant kill switch — removes a pattern from all briefings immediately. Unquarantine returns the pattern to `candidate` stage for re-evaluation.

**Feedback Loop:** When briefing shows strategy tips, records which patterns were shown. After session completion, compares outcomes of sessions with tips vs without. Effective tips get reinforced; counterproductive tips decay. A/B testing randomly assigns sessions to treatment (tips shown) or control (tips withheld) groups for causal measurement. Tips shown via `GET /briefing` are recorded under the server-minted `briefing_id` (not yet a `session_id` at that point), while outcomes are keyed by `session_id` — a disjoint key space that would otherwise silently break the join. Bridge only learns a session's `briefing_id` if the caller passes it to `ctx_start_session`; `GET /briefing`'s `instructions` field renders it into the suggested call (see Briefing Endpoint above) so a compliant agent supplies it. `GET /patterns/effectiveness` closes the join: it fetches Bridge `GET /sessions` (carrying the internal key), reconciles each session's Bridge-stored `briefing_id` field to its `session_id`, and passes that map into `compute_tip_effectiveness` so tips shown through the briefing join to their session's outcome — for sessions whose agent passed the id along. Bridge unreachable degrades to an empty map (session_id-keyed logs from `POST /patterns/tip-shown` still join; briefing-keyed logs don't) rather than failing the endpoint.

**Cross-Agent Learning:** `GET /patterns/relevant?exclude_agent=X` returns patterns from other agents' sessions. Briefing hook adds a "Cross-Agent Learnings" section for multi-agent setups.

**REST Endpoints (on Cortex :8100):** `GET /patterns/?stage=X&category=Y`, `GET /patterns/relevant?goal=X&exclude_agent=Y`, `POST /patterns/analyze`, `POST /patterns/tip-shown?group=treatment|control`, `GET /patterns/effectiveness`, `POST /patterns/{id}/quarantine`, `POST /patterns/{id}/unquarantine`

**Experiment Framework (optional):** Datasets define filtered session subsets and experiments compute chi-square / Cohen's h / CI statistics. Gated behind `PATTERN_EXPERIMENTS_ENABLED=false` (default off). When enabled, also registers: `POST /patterns/datasets`, `GET /patterns/datasets`, `GET /patterns/datasets/{id}`, `DELETE /patterns/datasets/{id}`, `POST /patterns/experiments`, `GET /patterns/experiments`, `GET /patterns/experiments/{id}`, `POST /patterns/experiments/{id}/conclude`. Models: `Dataset`, `Experiment` in `cortex/app/patterns/models.py`. Statistics: `cortex/app/patterns/statistics.py`.
