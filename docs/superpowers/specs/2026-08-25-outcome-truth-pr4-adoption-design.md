# Outcome Truth PR4 — grading adoption: instrumentation, the server-side nudge, and a pre-registered experiment

**Status:** reviewed (one self-adversarial pass, 2026-08-25 — freeze-safe compliance predicate, observational-vs-arm analysis split, stable-hash + empty-`owner_member` handling, H2 minimum-N all folded in). Grounded in a 5-stream code read of the post-PR3 tree. Ready to plan.
**Date:** 2026-08-25
**Depends on:** PR1 (the grade exists + binds to `owner_member`), PR2 (receipts), PR3 (skill efficacy). All shipped + deployed. **All three are data-inert:** the deployed OWM pass over 229 real sessions returned `sessions_joined: 0` — nothing grades tasks, so every downstream signal is the neutral prior. PR4 is the adoption layer that turns the apparatus on.
**Scope:** the pre-registration document + the server-side-only instrumentation and nudge that can ship without touching the client kit (peer is mid-release on `client/`). The **controlled per-session A/B** and the **proactive client-rendered nudge** are a defined follow-on (PR5), because the code read shows they *require* the client channel.

## The reality the code forces (why PR4 is shaped this way)

The instinctive PR4 — "tell agents to grade their tasks and A/B it" — collides with three hard facts in the current code:

1. **The server's handshake instruction channel is dead for kit agents.** Cortex's `FastMCP(instructions=_INSTRUCTIONS)` (`cortex/app/mcp_server.py:59-83`) is discarded by the local gateway, which forwards only `tools/list` and serves its *own* `GATEWAY_INSTRUCTIONS` (`client/firekeep_client/gateway.py:200-224,275-289,369-387`). This is not hypothetical: `client/firekeep_client/adapters/base.py:480-510` records that `action_before` shipped into `_INSTRUCTIONS` alone (f23133a) and was **dead for a full release** until it was added to the *client-rendered* blocks. The one genuine server→kit-agent channel is **tool descriptions**, forwarded verbatim (`gateway.py:326-351`).
2. **Descriptions don't trigger proactive behavior — but grading isn't a proactive ask.** The repeated lesson (`mcp_server.py:39-41`, `base.py:446-449`): rewording a tool description does not make an agent *call a tool it wasn't going to call*. Grading is different — agents **already** call `ctx_complete_session` (stop hook + the rendered `MEMORY_INSTRUCTIONS` "ctx_complete_session when done", `base.py:404-405`). Strengthening that tool's description shapes *how* an in-hand tool is called (a parameter-usage hint, the channel `action_before`'s param doc already rides). That is the realistic ceiling of a server-only intervention — real but mild.
3. **A per-session controlled A/B needs the client channel.** `tools/list` is served once at gateway startup, before any session exists, so the description channel cannot vary per session — only per **agent** (via `X-Agent-Id`, and only by overriding FastMCP's static-docstring listing). The proven per-session randomizer (`briefing/api.py:71` `random.choice`) rides the **session-start hook** — client-side. So the differential treatment a clean A/B needs is a client-rendered-instruction capability.

**Consequence:** PR4 (this spec) instruments the experiment, pre-registers it, and ships the *mild* server-side nudge — all server-side, no client collision. The *controlled experiment with the effective proactive nudge* is **PR5**, delivered through the client-rendered block once the peer's release lands, run against the substrate PR4 builds. Instrumenting before intervening is also correct pre-registration hygiene.

## Decisions

**D1. Stamp `experiment_group` per session onto the eval record — the randomization unit is the verified `owner_member`.** At `start_session` (`bridge/app/session.py:199-259`), derive `experiment_group` deterministically from a STABLE hash of `owner_member` (not Python's `hash()` — it is salted per-process and would give different arms across restarts; use e.g. `int(hashlib.sha256(owner_member.encode()).hexdigest(), 16) % 2` → `"A"`/`"B"`), sticky per member, no storage, **orthogonal to the grade** (assigned before the grade CAS at `session.py:587-598`, never a function of outcome). **Empty `owner_member` (auth disabled, or an unauthenticated session) → `experiment_group = None`, not a hashed arm:** `hash("")` would dump every unauthenticated session into one arm and poison the randomization; a `None`-grouped session still gets D4's nudge and still counts in the overall before/after adoption, it is simply excluded from the per-arm (PR5) comparison. Record the exclusion count so the denominator stays honest. Ride it on the `session_start` replay payload (`bridge/app/mcp_server.py:429-435`, beside the existing attribution fields) → read it in `compute_session_eval` (`cortex/app/evals/compute.py:196-224`, the same loop that reads `runtime`/`briefing_delivered`) → persist `experiment_group: str | None = None` on `EvalResult` (`models.py:82-91`, defaulted so old records parse). This is the join key the pre-registered analysis needs; it costs no new event, no new store, no CAS change. It is stamped **now** so that when PR5's differential nudge ships, historical group labels already exist. (`owner_member` is verified/unforgeable — `mcp_server.py:150-163` — and immutable-per-session, exactly the stickiness guarantee wanted.)

**D2. Measure adoption in the compliance layer as `graded / completed`, per group — freeze-safe.** `cortex/app/autopilot/compliance.py` is the only layer built on predicate-hit / exposed-rate semantics (`compliance.py:298-312`). The freeze is load-bearing (KEYS + PREDICATES anchor the pre-registered baseline, `compliance.py:59-63`). Three changes that respect it:
- **Enrich the dict passed to predicates — do NOT change the predicate signature (self-review correction).** Predicates are `Callable[[_Metrics], bool]` called with `e["metrics"]` (`compliance.py:64,265`), and each reads a metric key (`m.get("memory_read_count")`, `_num(m.get("brier_score"))`). The grade is a *top-level string* `EvalResult.task_result` (`models.py:101`), NOT in `metrics`. Naively passing the whole record instead would make every frozen predicate read its metric off the top level, get `None`, and flip to always-False — silently mutating the frozen baseline. Instead, at the call site (`compliance.py:265`) build a merged view `{**e["metrics"], "task_result": e.get("task_result"), "task_result_source": e.get("task_result_source"), "experiment_group": e.get("experiment_group")}` (`_Metrics` is already `dict[str, Any]`; string values type-check; no grade key collides with a metric key). Existing predicates read their metric keys unchanged; the new predicate reads the promoted grade keys.
- **Add a frozen row** `grade_self_reported` to `INSTRUCTIONS` (`compliance.py:64`): predicate `lambda m: recognized_grade_pair(m.get("task_result"), m.get("task_result_source")) is not None`, a new never-used key (freeze-compatible — the freeze forbids *mutating* an existing predicate, not *adding* rows; precedent: the round-2 `recall_visibly_used`/`outcome_bearing` rows). Import `recognized_grade_pair` from `evals.models`.
- **Report adoption per `experiment_group`** so the readout is `graded / all-completed`, split by arm — the denominator is all completed evals in the arm (assignment is unconditional on grading, D1). Surfaced at `GET /autopilot/compliance`. Every existing frozen predicate's output must be byte-identical (pinned by the existing compliance tests staying green — that is the freeze guard).

**D3. Validate grade HONESTY with a deterministic optimism-skew detector — free signals, no LLM judge.** The whole point of grading is a *true* signal; the failure mode is agents self-reporting `success` when the task failed (the "confident wrong signal" this arc exists to kill). No independent grader exists (`_RECOGNIZED_SOURCES = ("self_reported",)`, `models.py:9`), and Tier-2 LLM judging is a declared-but-unimplemented seam that won't run on embed-only deploys. So PR4 ships a deterministic detector over the three genuinely-independent signals already on every eval:
- **Bridge `abandoned` vs self-report `success`** — a hard, external contradiction (`owm.py:66-85`).
- **`has_failures` / `failure_event_ids` vs self-report `success`** — a soft contradiction (`compute.py:163-166`).
- **Per-agent Brier calibration** where the agent declared predictions (`trust.py:188-210`) — thin coverage, but the cleanest calibration signal.
Emit an **optimism-skew rate** (self-reported-success sessions that carry an independent failure contradiction, over all self-reported-success sessions), per group, **visibility-only**, disclosed with its denominator and an `unknown`/`approximate` bucket the compliance-table way. **Guardrail (do not repeat the scorer trap):** `tool_success_rate`/`failure_rate` are NOT independent of the self-report (outcome population ≈ 1 = the self-report itself, `scorers.py:171-178`) — the detector must only use them filtered to `outcome_event_count >= 2`, and leans on abandoned/`has_failures`/Brier as the backbone.

**D4. Ship the mild server-side nudge: strengthen the `ctx_complete_session` tool description.** In `bridge/app/mcp_server.py:661-685`, sharpen the docstring (which FastMCP serves as the tool description, forwarded to every kit agent incl. hookless Codex/generic) so that passing `task_result` is the stated default expectation — leading with an honest-grading framing that makes reporting `failure`/`partial` explicitly safe (optimism-bias reduction), and pointing at `task_evidence` as the "what did you actually verify?" anchor. This is a param-usage hint on an already-called tool, not a proactive trigger — the defensible server-side ceiling. It ships to everyone (no A/B), establishing the **baseline** adoption + honesty under the mild nudge; PR5's proactive client nudge is then measured as the *incremental* lift over this baseline.

**D5. This document IS the pre-registration.** Committed before the intervention's effect can be observed, and not revised after seeing data (a later revision is a new, dated pre-registration, never an edit):
- **H1 (adoption):** the mild tool-description nudge (D4) raises the fraction of completed sessions carrying a recognized grade from the measured ~0 baseline to a non-trivial rate. *Pre-registered success threshold: adoption ≥ 20% of completed sessions within a 2-week window after D4 deploys* (a deliberately modest bar for a description-only nudge — the strong lift is PR5's job). Measured by D2.
- **H2 (honesty):** among self-reported-`success` sessions, the optimism-skew rate (D3) stays below a pre-registered bound. *Pre-registered: skew ≤ 15%, i.e. ≤15% of self-success sessions carry an independent failure contradiction* — evaluated once the store holds a pre-registered minimum of self-`success` sessions (propose N ≥ 30; until then the metric reports `unknown`/insufficient-N, never a spurious "clean"). A skew above the bound is a finding that the nudge wording needs honesty scaffolding before grades can be trusted downstream — and is a reason to gate OWM/skill-efficacy from consuming grades until fixed.
- **Analysis — PR4 is observational (before/after); no inferential stats in PR4.** PR4 ships D4 to *everyone*, so within PR4 there is no differential-by-arm treatment to test — its evidence is two simple rates: (a) adoption *before/after* D4 deploys (an interrupted-time-series read: the known ~0 pre-D4 baseline vs post-D4 adoption from D2) and (b) the honesty-skew rate from D3. Both are plain proportions against the pre-registered thresholds; **PR4 builds no `statistics.py`/`Experiment` machinery** (YAGNI — nothing runs an inferential test here). The generic two-proportion spine (`_chi_square_2x2`/`_cohens_h`/`_confidence_interval_diff`/`minimum_sample_size`, the `Dataset`/`Experiment` shell with `Experiment.pattern_id` made optional) and a new McNemar/Cohen's-κ agreement helper are **PR5's** to build and use, when the client nudge actually varies by `experiment_group` and a controlled arm difference (and a paired self-vs-independent agreement) can be tested. `experiment_group` is the only PR5-facing thing PR4 lands early, because it must be stamped *before* the intervention to have honest pre-dated arm labels.
- **Decision rule:** if H1 holds and H2 holds → proceed to PR5 (the controlled client-nudge A/B) to measure the proactive lift and, if honest, promote grading to default. If H1 fails → the description channel is too weak (expected); PR5's client nudge is the real test. If H2 fails → fix honesty scaffolding (evidence-required wording) before any grade feeds OWM/skill efficacy.

## Deferred to PR5 (the controlled experiment) — with rationale

- **The proactive client-rendered grading nudge** in `base.py` `MEMORY_INSTRUCTIONS` — the genuinely effective adoption driver, and the only channel that (a) triggers proactively and (b) can vary **per session** for a clean A/B (via the session-start hook, keyed on the `experiment_group` D1 already stamps). Deferred because `client/` is mid-release (peer-contended) and because instrumenting first is correct pre-registration order. PR5 delivers the differential nudge, coordinated with the peer's client release, and runs H1'/H2' as the *controlled* experiment against this substrate.
- **The Tier-2 LLM judge** as a *sampled* honesty confirmation on the stratified disagreement subset (self-success ∧ independent-contradiction) — writing the already-reserved `llm_judged_metrics`/`llm_judge_model` (`models.py:70-72`), gated behind an enable flag + the `_generation_backend_available` probe (`dreams/task.py:327-391`) + a dedicated timeout, off the completion hot path. Deferred because the deterministic detector (D3) is sufficient to pre-register and works on embed-only deploys; the judge is an accuracy upgrade, not a prerequisite.
- **Surfacing `task_evidence` onto the eval record** for evidence-as-treatment analysis — today it is write-only in bridge DB 3 (`session.py:630`), never on `EvalResult`. Needed only if evidence-prompting becomes its own arm (a PR5 variant).
- **The inferential-statistics spine** — reuse `statistics.py`'s two-proportion tests + the `Dataset`/`Experiment` shell (with `Experiment.pattern_id` made optional) for the arm-difference test, plus a new McNemar/Cohen's-κ helper for the paired self-vs-independent agreement. Deferred because PR4 runs no inferential test (its readouts are plain proportions vs pre-registered thresholds); PR5 builds and uses this when the arms actually differ.

## Non-goals

- **Whether the outcome-truth loop improves agent outcomes** (does OWM/skill-efficacy ranking, fed by real grades, actually raise success rates). That is the *downstream efficacy* experiment — a long feedback loop that requires grades to already flow (H1) and be honest (H2). It is PR6+, not PR4.
- Any change to the grade CAS, the recognized-grade contract, the receipts, or skill efficacy. PR4 only adds an orthogonal `experiment_group` label, a compliance readout, an honesty detector, and a tool-description edit.

## Disclosed residuals

- The D4 server-side nudge reaches all kit agents but is **mild by construction** (description-channel ceiling); a low baseline adoption is an expected, pre-registered outcome, not a failure of the instrumentation.
- Server-side assignment is per-`owner_member` and orthogonal to the (uniform) D4 nudge, so PR4 itself is **observational** (baseline), not a controlled A/B — the control/treatment split becomes meaningful only in PR5 when the nudge varies by arm. The `experiment_group` is stamped now purely to have clean, pre-dated arm labels for PR5.
- The honesty detector's coverage is bounded by how often the independent signals fire (Bridge `abandoned` is rare; Brier needs declared predictions); it is a lower bound on skew, disclosed as such.
