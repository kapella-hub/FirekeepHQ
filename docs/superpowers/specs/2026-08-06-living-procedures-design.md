# Living Procedures — design

**Date:** 2026-08-06
**Status:** design, round 1
**Feature flag:** `PROCEDURE_ENABLED=false` (opt-in, like every other subsystem here)

---

## 1. What this is

A skill today is advice text. It is written once, injected into a briefing, and never
observed again. Nothing in the system knows whether anyone followed it, which of its steps
mattered, or whether it is still true.

Living Procedures makes a skill an **observed procedure**: when work matching one of its
steps happens, Firekeep opens an execution record, watches which other steps do and do not
happen, warns — advisory only — when a step that has historically predicted failure is
about to be left undone, and nightly correlates per-step evidence against session outcomes
to propose (never apply) changes to the procedure itself.

The one-line claim:

> Your runbooks recognise the work you are doing, warn before you leave a load-bearing step
> undone, and get better every time anyone runs them — with the evidence to show which steps
> actually matter.

## 2. Why this is defensible

The feature is copyable. Its output is not.

A competitor can implement step matching in an afternoon. What they cannot do is arrive with
**41 recorded executions of your release procedure, each joined to whether that session
succeeded**. That corpus is generated by real work over real time; it cannot be bought,
scraped, or generated by compute. A clone installs the feature and owns an empty ledger, and
the ledger is what produces every number the product shows.

This is the only class of feature where the value curve is superlinear in tenure and the
gap is *visible in the product* — a procedure card that reads "hardened by 41 executions;
step 3 skipped in 24 of 31 successful runs" is a statement a new installation structurally
cannot make.

Round 1 deliberately does not attempt the second-order version of this (using the same
corpus to certify model upgrades, or to fine-tune a local model). Both become available
once execution records exist; neither is designed here.

## 3. What the codebase audit changed

This design was pitched before the code was read. An eight-reader sweep plus an adversarial
critic found **21 places where the pitch contradicted the code** and 14 places where it
proposed building something that already exists. The corrections below are load-bearing —
the pitched version would have shipped inert, which is the failure mode this repo has
already paid for three times (the `/v1` endpoint, the untagged-calls nagging, the
scroll-then-substring skill matcher).

| Pitched | What the code says | Correction |
|---|---|---|
| Bind when `skill_recall` or the briefing delivers a skill to a session | `skill_recall` (`cortex/app/mcp_server.py:1177-1208`) declares no `session_id` and never calls `_resolve_identity`; `_get_client()` passes no default headers. `get_briefing` (`cortex/app/briefing/api.py:60-71`) has no `session_id` at all — only a per-request `briefing_id`. The session stash may also not be populated before `ctx_start_session`. | **Bind by recognition, not delivery.** An execution opens when a step spec matches observed work. No delivery hook, no session identity at recall time, and the noise risk of binding an arbitrary skill from an empty-goal briefing disappears. |
| Steps are addressable entities | `create_skill` folds `req.steps` into one Markdown string after the literal heading `## Steps` (`cortex/app/skills/api.py:141-148`). `parse_skill_content` returns `body` as one blob (`synthesizer.py:156-177`). There is no `steps` payload key, no step id, no ordering guarantee. Live check: **25 active skills, none with step structure.** | Step specs are **self-contained** — each carries its own `text`, so nothing depends on parsing `## Steps`. The body remains the human-readable rendering. |
| `action_before`/`action_after` events carry file paths | `agent.action.reconcile` emits `session_id=entry["session_id"] if entry else ""` (`agent_gateway/service.py:257`), and `entry` exists only when a prediction was sent — which the shell hook never sends. Its payload is `{action_id, outcome, source, prediction_match_score}`; no path. | **Observe intent-side only**, from `agent.action.predict`, which does carry `session_id=req.session_id` and `action.target` (`service.py:190-202`). Rules receive one dependency (the replay-redis closure, `main.py:414-415`) and are awaited sequentially on the blocking pre-edit path. The bias this removes points exactly at "delete the load-bearing step". |
| Record the replay event id as a receipt | `emit()` returns the Redis **stream** entry id (`replay/emitter.py:224`), not the `event_id` that `GET /replay/events/{id}` resolves; cortex's `_replay_emit` is typed `-> None` and discards it (`main.py:98-104`). `rp:eid:` expires at 30 days and `trim_old_events()` is **never scheduled**. | Receipts are **self-contained** — the execution record holds `{action_id, target, ts}` and owns its own `exec_id`, which is what populates the already-existing-and-unused `Advisory.evidence_event_id` (`agent_gateway/models.py:53`). No dependency on a TTL'd index. |
| Night Shift backfills specs for legacy skills | Night Shift's task type **is** the relay task title, hard-coded `_TASK_TITLE = "distill_session"` (`client/firekeep_client/nightshift.py:54`); relay tasks carry no kind field and TTL at 7 days; the drain is a manual CLI command. | Per-step stats on the skill point | A semantic PATCH retrieves, merges onto the current payload, re-embeds and does a full `upsert` (`skills/api.py:249-268`) — silently discarding any `set_payload` written between the retrieve and the upsert. Two further findings are pre-existing defects that this feature would inherit; both are fixed
as prerequisites in §7.

## 4. Architecture

Five stages. Every one rides a seam that already exists.

```
                    ┌─────────────────────────────────────────────┐
   skill_create ───▶│ 1. COMPILE   step_specs on the Qdrant point │
   PATCH /skills    └──────────────────────┬──────────────────────┘
                                           │ (write) rebuild
                                           ▼
                              ┌───────────────────────────┐
                              │  proc:index  (Redis DB 6) │  denormalised
                              │  flat list of glob specs  │  matcher index
                              └─────────────┬─────────────┘
                                            │ 1 GET, 30s in-process cache
   Edit/Write ──▶ POST /agent/action/before ─┤
   (pre_tool)                                ▼
                          ┌──────────────────────────────────────┐
                          │ 2. RECOGNISE + 3. OBSERVE + 4. WARN  │
                          │  inside AgentGatewayService.decide() │
                          └────────┬──────────────────┬──────────┘
                                   │ write            │ Advisory
                                   ▼                  ▼
                    proc:exec:{session}:{skill}   advisories[] ──▶ pre_tool prints
                         (Redis DB 6, 90d)                          on allow
                                   │
                                   │ nightly
                                   ▼
                     ┌──────────────────────────────────┐
                     │ 5. HARDEN  (Celery, memory-agent │
                     │  shape) → per-step efficacy      │
                     │  → proposals (never applied)     │
                     └────────────────┬─────────────────┘
                                      ▼
                         dashboard Skills tab → human PATCH
```

### Stage 1 — Compile

`SkillRequest` and `SkillPatchRequest` gain an optional `step_specs: list[StepSpec]`.

```python
class StepSpec(BaseModel):
    id: str                      # uuid4, minted server-side if absent, stable thereafter
    text: str                    # the step, verbatim — self-contained, no parse dependency
    kind: Literal["file_glob", "unobservable"] = "unobservable"
    pattern: str = ""            # fnmatch glob; required when kind == "file_glob"
    load_bearing: bool = False   # author's claim; the harden pass proposes revisions
```

The **authoring agent compiles its own specs** — it holds the full session context and a
capable model at exactly the moment it calls `skill_create`, which is the same argument that
makes client-authored skills work on a GPU-less deploy. The server runs no LLM for this. The
tool schema carries the field and its docstring explains it; a rendered instruction-layer
line is a follow-up, not a round-1 dependency, because unlike `decision_board` this is not
a *decision to act proactively* — it is a field on a call the agent is already making.

`kind="unobservable"` is a first-class, honest value: a step like "ask the customer to
confirm" cannot be watched, and recording that is strictly better than inferring it.

**Round-1 shell caveat, stated at authoring time:** `run_command` is not observable (§6, H2),
so a step whose action is a shell command must be authored `unobservable` even though it is
mechanically precise. The tool docstring says this.

### Stage 2 — Recognise

There is no bind-on-delivery hook. Inside `decide()`, after the policy evaluation:

1. If `req.action.type != "edit_file"`, do nothing. (This check is the reason this lives in
   the gateway service and not a policy rule — `PolicyContext` cannot make it.)
2. Read `proc:index`; `fnmatch` `req.action.target` against every `file_glob` spec.
3. For each matching `(skill_id, step_id)`, open-or-extend
   `proc:exec:{session_id}:{skill_id}` and append the observation.

An execution is therefore *created by evidence*. Nothing declares it, so nothing can lie
about it, and there is no silently-discarded `(None, skill_id)` key.

If `req.session_id` is empty or `"unknown"`, no execution is opened — an execution that
cannot be joined to an outcome is not evidence. This is counted and surfaced, not hidden.

### Stage 3 — Observe

The observation write is **live**, during the session, not reconstructed at pass time. This
is a deliberate reversal of the pitch: reconstructing from replay at T+8 days runs into a
30-day nominal retention whose trim task is never scheduled, an approximate `MAXLEN`, and
Bridge keys that TTL at 7 days. Writing live means the feature owns its own durability.

```
proc:exec:{session_id}:{skill_id}   HASH   TTL PROCEDURE_EXEC_TTL_DAYS (90d)
  exec_id        proc_<uuid4hex12>
  skill_id       <skill uuid>
  session_id     <as sent by pre_tool — the same id evals key by>
  agent_id       <req.agent_id>
  adapter        <req.adapter>          # shell-hook | mcp | rest — see the note below
  opened_at      <iso8601>
  last_seen_at   <iso8601>
  observed       {"<step_id>": [{"action_id":…, "target":…, "ts":…}, …]}
  warned         {"<step_id>": "<iso8601>"}      # warn-once latch, per (exec, step)
```

Every write is fire-and-forget inside the stage's own `try/except`: a Redis failure must
never fail a customer's edit.

**`adapter` does not identify the runtime, and that is why I2 is not optional.** `Adapter` is
`Literal["shell-hook", "mcp", "rest"]` (`agent_gateway/models.py:11`) — a transport class —
and `pre_tool` hardcodes `"adapter": "shell-hook"` on every runtime (`pre_tool.py:144`). A
Claude execution and a kiro execution are therefore **indistinguishable in the request**.
This kills the obvious mitigation for H1 (scoring per-runtime capability) before it is
proposed: there is no runtime field to scope on, and adding one is a client release. I2 —
which infers observability from whether *any* sibling step was seen, rather than from a
capability table — is the only defence that works without one, which is the argument for
preferring it even if a runtime field existed.

### Stage 4 — Warn

When an edit matches step *N* of procedure *P*, and some **earlier load-bearing** step of *P*
has no observation in this execution, append one `Advisory`.

"Earlier" means **earlier in the `step_specs` list**, which is the only ordering that exists:
there is no step index in the skill body and no ordering guarantee in `## Steps`. The list
order is therefore the procedure's order by definition, and the compile guidance says so —
an author who reorders the list changes the semantics, which is correct and intended.

```python
Advisory(
    code="procedure_step_missing",          # new AdvisoryCode literal (§7)
    message=("Procedure 'Publish a client release' — step 2 (\"bump the bundled symdex "
             "wheel and its bootstrap checksum\") has no evidence in this session. "
             "Skipped in 3 of 4 prior failing executions; present in 11 of 11 successes."),
    evidence_event_id=exec_id,              # the pre-existing, unused slot
)
```

Warn-once per `(exec_id, step_id)` via the `warned` field — the same once-only shape as the
existing `RethinkCounter` (`service.py:34-47`). The advisory reaches the human through a
channel that is **already live**: `pre_tool` prints advisories on an `allow` decision
(`client/firekeep_client/hooks/pre_tool.py:160-164`), under a comment explaining that the
gateway remaps `warn → allow`. **No client release is required.**

Because the client joins only `a.get("message")` and flattens with `"; "`, the statistics
must be pre-formatted into that one string. They are.

The stats in the message come from the same Redis keys the nightly pass writes; if they are
absent (fewer than `PROCEDURE_MIN_EXECUTIONS` executions), the message states the step is
missing and says nothing about history. It never invents a number.

### Stage 5 — Harden

A nightly Celery pass in the shape of `skill_staleness_pass` (`cortex/app/skills/staleness.py:36-108`)
— injectable sync clients, scroll-with-filter, returns a counts dict, registered inside
`run_memory_agent` — because that shape already solves the sync-client-in-a-worker problem.

For each active skill with specs, over executions in the last `PROCEDURE_WINDOW_DAYS`:

1. **Resolve the outcome.** Read `rp:eval:{session_id}`. If absent, compute it (the pass
   calls the same computation `POST /evals/sessions/{sid}/compute` uses). This is not
   defensive padding: the evals router's own docstring records a live incident where all 19
   stored evals were `trigger="manual"` and 12 days stale against 54 completed sessions, so
   a pass that merely *reads* evals would have almost no sample.
2. **Apply I4.** Drop the execution if the eval has no outcome-bearing event.
3. **Apply I2.** Within a surviving execution, a spec'd step is `observed` or `skipped`;
   `skipped` counts only if ≥1 sibling step of the same procedure was observed in that same
   execution. Otherwise the execution is evidence-free for that step and contributes nothing.
4. **Fairness, borrowed from OWM verbatim:** one session counts once per step; one
   `agent_id` contributes at most `PROCEDURE_AGENT_CAP` observations per step.
5. **Score.** `compute_efficacy` (imported from `app.owm`) over `(skipped, outcome)` and
   `(observed, outcome)`, gated at `n >= PROCEDURE_MIN_EXECUTIONS`.
6. **Propose.** Write proposals to Redis. Never mutate the skill.

Three proposal kinds:

| kind | condition | proposed change |
|---|---|---|
| `dead_step` | skipped in ≥ `PROCEDURE_MIN_EXECUTIONS` executions **and** `efficacy(skipped) >= efficacy(observed) - PROCEDURE_EFFICACY_DELTA` — i.e. skipping it costs nothing measurable | remove the step, or mark it optional |
| `load_bearing` | `efficacy(skipped) < efficacy(observed) - PROCEDURE_EFFICACY_DELTA` at `n >= PROCEDURE_MIN_EXECUTIONS`, and the spec is not already `load_bearing` | set `load_bearing=true` (turns on the warn) |
| `spec_drift` | a spec's `text` no longer appears in the skill's `content` | recompile specs — the body was edited without them |

Like OWM's stale-reset sweep (`owm.py:181-210`), a proposal with no supporting evidence in
the window is **deleted**, not left standing. Verdicts decay back to neutral; they do not
ratchet.

## 5. Invariants

These are the load-bearing properties. Each exists because the code audit found a specific
way the naive version is wrong.

**I1 — Recognition, not declaration.** An execution is opened by a spec matching observed
work, never by an agent declaring that it is following a procedure. *Because* neither
delivery surface carries a session identity, and because a declaration-based design is a
discipline dependency, which this repo has watched fail three times.

**I2 — Absence of evidence is never evidence of absence.** A step is `skipped` only if a
sibling step of the same procedure was observed in the same execution. *Because* kiro's
`fs_write` maps to `other` with an empty target (`pre_tool.py:27-32`), `run_command` returns
before the gateway POST (`pre_tool.py:89-94`), and personal mode short-circuits both hooks
(`hooks/__main__.py:191-198`). Without I2, every kiro session, every shell-heavy session and
every personal-mode session votes to delete load-bearing steps. I2 is self-calibrating: it
needs no runtime capability table, which is what keeps it true when a new runtime is added.

**I3 — Two writers, two stores, no shared keys.** `step_specs` lives on the Qdrant point and
is written only by the PATCH path. Every derived number lives in Redis. *Because* a semantic
PATCH does retrieve → merge → re-embed → full `upsert`, which discards a concurrent
`set_payload`.

**I4 — Outcome requires evidence.** A session contributes only if its eval contains ≥1
outcome-bearing event. *Because* `_failure_rate` returns `0.0` on no evidence and `0.0`
reads as success.

**I5 — Nothing on the pre-edit path may touch Qdrant or embed.** One Redis GET, memoised
in-process for 30s, then `fnmatch` in memory. *Because* rules and gateway steps run
sequentially on every customer Edit/Write, and a slow gate is a silently skipped gate.

**I6 — The feature can never block.** Advisory only, in its own `try/except`, on a path that
already fails open. There is no severity that escalates. *Because* an agent authoring a bad
spec in passing must not be able to brick edits team-wide.

## 6. Honest limits

Stated here rather than discovered later.

**H1 — Round 1 observes Claude Code file edits only.** `_action_type` maps `{Edit, Write,
MultiEdit} → edit_file`; kiro's `fs_write` falls through to `other` with `target=""`. A
one-line client fix lands in round 2; until then kiro produces no observations — and I2 means
it produces no *false* ones either.

**H2 — Shell steps are unobservable.** `pre_tool` returns before the gateway POST for
`run_command`, deliberately. Routing Bash through the gateway is a real latency and behaviour
change, so it is a round-2 decision, not a round-1 assumption. Since many procedure steps
*are* shell commands, a meaningful fraction of every procedure will be `unobservable` in
round 1. The product must say so — a procedure card shows "4 of 7 steps observable" — because
a coverage number the user cannot see is the same silent-cap failure this repo bans elsewhere.

**H3 — Cold start.** No existing skill has specs. Until skills are authored or patched with
them, the feature does nothing at all, which is the correct behaviour but must not be
mistaken for a bug. The dashboard states the count.

**H4 — Recognition is not intent.** A file-glob match means work of this shape happened, not
that the agent chose this procedure. Two procedures matching one file both open executions.
This is a deliberate trade: it is more robust than declaration and, for the hardening
question ("when work of this shape happens, which steps correlate with success?"), arguably
the more correct signal. It does mean a broad glob such as `*.py` is a bad spec, and the
compile guidance says so.

**H5 — One machine-global caveat inherited unchanged.** Two concurrent sessions under the
same identity already share a session stash (documented in `CLAUDE.md`). Executions key on
`session_id`, so they inherit exactly that behaviour — no better, no worse.

## 7. Prerequisite fixes

Two pre-existing defects. Both are small, both are worth fixing regardless of this feature,
and this feature would inherit both.

**P1 — `agent.action.reconcile` emits an empty `session_id`.** `service.py:257` reads
`entry["session_id"] if entry else ""`, and `entry` is written only when a prediction was
sent, which the shell hook never sends. Every reconcile from Claude Code is therefore filed
under the empty string and is invisible to `get_session_timeline(sid)` — which also means
`compute_session_eval`'s predict→reconcile Brier calculation (`evals/compute.py:81-102`) has
been computing nothing on the hook path. Fix: fall back to `req`'s own identity. Server-side,
one line, no client release.

**P2 — `warn` decisions are never recorded.** `record_policy_decision` is gated
`if decision != "allow"` (`service.py:142`), but `warn` is remapped to `allow` at
`service.py:102-103` *before* that check. Every warn ever produced by `FileRiskRule`,
`SessionHealthRule` and `RecentFailureRule` has been dropped; `summarize_policy_decisions`
carries structurally unreachable `"warn": 0` and `"allow": 0` slots (`policy/store.py:72`).
Fix: record against the pre-remap action. Without it, this feature's warns are unauditable
and the dashboard Policy tab shows nothing.

Two documentation defects found in passing, fixed in the same pass: `owm.py`'s module
docstring names `OWM_SUCCESS_MAX_FAILURE_RATE` / `OWM_FAILURE_MIN_FAILURE_RATE`, which do
not exist — the bands are hardcoded constants (`owm.py:37-38`) — and it implies a minimum-N
gate the code does not have.

## 8. Config

All new, all optional, all inert while `PROCEDURE_ENABLED=false`.

| Var | Default | Purpose |
|---|---|---|
| `PROCEDURE_ENABLED` | `false` | Master switch: gates the gateway stage, the pass, and the API routes |
| `PROCEDURE_WARN_ENABLED` | `true` | Sub-flag — observe without warning (evidence-gathering mode for a first deployment) |
| `PROCEDURE_MIN_EXECUTIONS` | `5` | Minimum executions before a step's efficacy is used for a warn or a proposal |
| `PROCEDURE_PRIOR_N` | `5` | Beta prior handed to `compute_efficacy` (mirrors `OWM_PRIOR_N`) |
| `PROCEDURE_EFFICACY_DELTA` | `0.15` | How far a skipped-step efficacy must fall below the observed-step efficacy to propose `load_bearing` |
| `PROCEDURE_WINDOW_DAYS` | `30` | Evidence window (matches the 30d eval TTL — a larger window is dead weight) |
| `PROCEDURE_EXEC_TTL_DAYS` | `90` | Execution-record TTL; deliberately > the window so a window never reaches past its data |
| `PROCEDURE_AGENT_CAP` | `5` | Max observations one `agent_id` contributes per step (mirrors `OWM_AGENT_CAP`) |
| `PROCEDURE_INDEX_CACHE_SECONDS` | `30` | In-process matcher-index cache TTL |
| `PROCEDURE_SCHEDULE_HOURS` | `24` | Hardening pass cadence |

Per the change-consistency checklist, each lands in `cortex/app/config.py`,
`docker-compose.yml` (**including `cortex-beat`**, since `beat_schedule` is built from
`get_settings()` at import time), `.env.example`, and a drift guard in the shape of
`test_decision_config.py`.

## 9. Surfaces

**REST (Cortex :8100), mounted only when `PROCEDURE_ENABLED`** — the `/collectors` and
`/dreams` precedent: a disabled deploy 404s rather than returning a disabled-shaped body.

- `GET /procedures` — per-skill rollup: spec count, observable count, execution count,
  per-step efficacy, open proposals.
- `GET /procedures/{skill_id}/executions?limit=` — the receipts behind the numbers.
- `POST /procedures/proposals/{proposal_id}/dismiss` — a human rejecting a proposal;
  accepting one is a `PATCH /skills/{id}` with revised `step_specs`, which keeps I3's
  single-writer property.

**Scope note, stated plainly because it is half a fix:** the skills router today declares no
`dependencies=` and contains zero `require_scope` calls (`main.py:564`) — every route on it
is reachable by any valid key, or anonymously when `AUTH_ENABLED=false`. The new
`/procedures` router does **not** inherit that: it gates `memory:read` on the reads and
`admin` on the dismiss. But **accepting** a proposal is a `PATCH /skills/{id}`, so the
accept path remains as ungated as it is today. That is deliberate — retrofitting a scope
gate onto `/skills` changes the auth posture of a shipped surface and belongs in its own
change, with its own test sweep, not smuggled in here. The asymmetry is: this feature adds
no new ungated route, and does not pretend the existing one is gated.

**MCP:** `skill_add_step_specs(skill_id, step_specs)` — so an agent can compile specs for an
existing skill without a PATCH tool. Round-1 answer to the cold start.

**Dashboard:** a Procedures card on the existing Skills tab, beside the stale/`needs_rereview`
rows that are already a propose→human→PATCH loop. Note the existing tab uses bare `fetch`
with no timeout or status check and its PATCH handlers have no `.catch` (`index.html:4924`,
`4987-5008`); new handlers use `fetchJSON`, catch, and are `window.`-exported, since an inline
`onclick` handler that is not exported fails silently at click time with no build- or
test-time detection.

**Briefing:** none in round 1. `/dreams` shipped with no briefing section and no dashboard
tab deliberately; adding a section pins `ALL_SECTIONS` in `test_briefing_api.py` and must fit
inside a hard-coded 2.0s per-section budget whose overrun flips `degraded=true` on the whole
envelope. Not worth it before the feature has data to report.

## 10. Testing

The repo's own scar tissue dictates the shape here: **every pre-existing Qdrant fake in the
cortex suite ignores its filter argument**, and the single filter-and-rank-honouring double
is `scoring_query_points` (`tests/test_skill_search.py:49`). A filter-dependent pass tested
against a filter-ignoring fake goes green while doing nothing — which is exactly how the
scroll-then-substring skill matcher survived review.

- **Filter-honouring doubles**, and each guard proven by mutation: reverting the fix must
  turn a specific test red.
- **I2 by construction:** a kiro-adapter execution, a personal-mode session and a
  zero-observation session each contribute nothing — asserted as "the efficacy is unchanged",
  not as "no exception was raised".
- **I3 by race:** a semantic PATCH interleaved with a pass write, asserting both survive.
- **I4:** an eval with `failure_rate=0.0` and no outcome-bearing event is excluded; the same
  eval with one outcome-bearing event is included.
- **I5:** the gateway stage performs no Qdrant call and no embed — asserted against a client
  double that raises on any call.
- **I6:** a spec whose `pattern` is hostile (`../`, a 10k-char glob, a regex-looking string)
  cannot raise out of `decide()`, and an index that fails to load degrades to no advisory.
- **P1/P2** each get a regression test that fails against today's code.
- **Cold start:** a deployment with zero specs performs no Redis reads on the edit path.

## 11. Out of scope for round 1

Named so they are decisions, not oversights.

- kiro `fs_write → edit_file` mapping (one client line; needs a client release).
- Shell/`run_command` observation (a real latency and behaviour change).
- Tier-2 progress-semantic matching (no reachable structured source — §3).
- Night Shift spec backfill (the task-type vehicle does not exist — §3).
- Any briefing section (§9).
- The Proving Ground — replaying historical decision points to certify a model upgrade.
  Its substrate is exactly the execution records this feature creates, which is why it is
  cheap *later* and impossible *now*.

## 12. Open questions
