# LLM endpoint selection — design (from the audit workflow)

## Recommendation

Add ONE new module, `cortex/app/llm.py`, exposing a single async entry point that owns endpoint selection, body construction and response normalisation for chat calls. Selection is option (c)+(d) with (b) as an explicit override, plus a narrow 4xx safety net borrowed from (a):

1. DERIVE a candidate native root from `LLM_BASE_URL` — it must end in `/v1`, which is stripped (`http://ollama:11434/v1` -> `http://ollama:11434`). No `/v1` suffix means no derivable root, so never native.
2. PROBE `GET {root}/api/version` once, lazily on first use, with a dedicated 2.0s timeout. Accept as Ollama only if it returns 2xx AND a JSON object containing a `version` key — a 200 from a catch-all proxy must not be mistaken for Ollama. Cache the verdict per-process, keyed by base_url: positive for `LLM_NATIVE_PROBE_TTL_SECONDS` (600s default), negative for `min(60, ttl)`.
3. Native body (shape taken verbatim from the repo's own working caller, `benchmarks/memory/bench/qa.py:89-96`): `{"model", "messages", "stream": False, "think": False, "format": "json" if json_mode else omitted, "options": {"temperature": ..., "num_predict": ...}}` -> read `resp.json()["message"]["content"]` and `["message"]["thinking"]`.
4. OpenAI body: the existing shape (`response_format`, top-level `temperature`/`max_tokens`) and NOTHING ELSE — read `["choices"][0]["message"]` for `content`/`reasoning`.
5. On a native 400/404/405/501 (returned before generation, so the retry is ~free), demote the cached verdict to negative and retry once on `/v1`. Do NOT retry on 5xx or timeout — those may be mid-generation.
6. The helper RAISES on transport/HTTP failure and never swallows. Each caller keeps its existing try/except and its existing degradation semantics.

New config: `LLM_NATIVE_CHAT: str = "auto"` (`auto|always|never`), `LLM_NATIVE_PROBE_TTL_SECONDS: float = 600.0`, and optional `LLM_NATIVE_BASE_URL: str = ""` for when the native root is not derivable but the operator knows it.

Adopt it in three phases, NOT all at once. Phase 1 (the smallest change that captures most of the win): the helper + `classifier.py` + both `synthesizer.py` chat calls — the docs->skills pipeline is the only path that is simultaneously on by default and currently failing, and the only one that stalls the solo worker for ~20 minutes. Phase 2: the Decision Board, and (after checking `GET /ops/queues`) `sleep_cycle.py`. Phase 3: dreams. Never this round: `rag.py` synthesis and rerank, `mcp_server.py` handoff.

Timeouts: `KNOWLEDGE_CLASSIFY_TIMEOUT_SECONDS` 300 -> 120, `SKILL_SYNTH_TIMEOUT_SECONDS` 300 -> 120, `DECISION_SYNTH_TIMEOUT_SECONDS` 20 -> 30, `DREAM_SYNTH_TIMEOUT_SECONDS` 45 unchanged, all hardcoded timeouts unchanged.

## Rationale

WHY A HELPER AND NOT AN ENV CHANGE. The tempting one-liner — repoint `LLM_BASE_URL` at `http://ollama:11434` — is disproven by grep: 11 chat sites concatenate `/chat/completions` and three embedding sites concatenate `/embeddings` (`db/vector.py:875`, `:954`, `workers/reembed.py:29`). Repointing breaks embeddings, i.e. every write path. The native path needs its own base and its own body shape, which is exactly what a helper is for.

WHY THE REQUEST/RESPONSE SHAPE IS NOT GUESSWORK. `benchmarks/memory/bench/qa.py:90-96` already posts `{"model", "messages", "stream": False, "options": {"temperature": 0}}` to `{base_url}/api/chat` and reads `resp.json()["message"]["content"]`. Two facts follow that a design written from memory would have got wrong: `stream: False` is mandatory (omit it and Ollama streams NDJSON, `resp.json()` raises `JSONDecodeError`, and `classifier.py:163` records the ingest as terminal `failed` — a silent, total rollout failure), and `temperature` belongs inside `options`, not at top level. `num_predict` is likewise an `options` key (`dreams/synthesize.py:4` names it). The implementer must still confirm `format`/`think` placement against the 3.3s probe response before writing code.

WHY THE OPENAI PATH MUST STOP SENDING VENDOR FLAGS. `dreams/synthesize.py:129-130` sends `think: False` and `chat_template_kwargs` on the `/v1` path unconditionally. Nobody has been burned because `DREAM_ENABLED=false`. A shared helper used by default-on paths cannot inherit that: real OpenAI rejects unrecognised request arguments with a 400. So the OpenAI branch sends only standard OpenAI fields. This makes constraint 1 structural rather than aspirational — the non-Ollama path is strictly more standards-compliant than today's dreams code.

WHY LAZY-AND-CACHED, NOT STARTUP. The API, the Celery worker and beat are separate processes (docker-compose.yml:220, :455, :574); a startup probe would couple app boot to LLM availability and would still need re-running per process. Lazy-on-first-use with a per-process TTL cache gives one 2s probe per process per 10 minutes. The precedent already exists: `dreams/task.py:305-356` probes `GET {LLM_BASE_URL}/models` with a dedicated 5.0s timeout for exactly this class of question, and its docstring already articulates the lenient-failure discipline this design copies.

WHY THERE MUST BE NO asyncio.Lock AROUND THE PROBE. The Celery worker runs `--pool=solo` and drives async code via a fresh event loop per task. A module-level `asyncio.Lock` binds to the loop that first acquires it and then raises in the next one. A benign race costs at most a few duplicate 2s probes on cold start; a cross-loop lock costs a crash in the worker. Document the absence as deliberate, or someone will "fix" it.

WHY THE PROBE FAILS TOWARD `/v1`. `/v1` is the contract; native is the optimisation. This matches the repo's own idiom (`write_text_if_changed` fails toward writing; `resolver.is_bypassed` fails toward not-bypassed). The asymmetric negative TTL (60s vs 600s) exists because a probe that fails transiently while Ollama restarts would otherwise pin every call onto the 289s path for a full 10 minutes — and with the reduced timeouts, that window would produce a burst of hard failures instead of slow successes.

WHY THE HELPER RAISES. `classifier.py:164` calls `_is_backend_unavailable(exc)` on the caught exception to decide between the `corpus_only` and `failed` terminal states. If the helper swallowed and returned an empty result, that discrimination becomes impossible and every failure collapses into one indistinguishable bucket. Constraint 4 ("never raise into a request path") is already satisfied by the callers: `classify_document` is wrapped end-to-end (`classifier.py:103-175`), `synthesize_from_document` at `:206-214`, `synthesize_board` at `:107-142`.

WHY THE `reasoning` FALLBACK GOES. `classifier.py:126-127` feeds `msg["reasoning"]` to `json.loads` when content is empty. Under JSON mode this cannot help by construction — if content is empty the grammar blocked it, so `reasoning` is prose. The measured call returned 4357 chars of it. Dropping the fallback changes no terminal state (`JSONDecodeError` either way) and removes a misleading line from the code.

TIMEOUTS, EACH FROM A MEASUREMENT:

`KNOWLEDGE_CLASSIFY_TIMEOUT_SECONDS` 300 -> **120**. The binding constraint is NOT the VPS. Native classify measured 3.3s (36x headroom at 120s), but the root CLAUDE.md records the office deploy running llama3.2:3b at "~56s on CPU" for a classify — and llama3.2:3b is not a thinking model, so the endpoint fix saves it nothing and its 56s stays 56s. 60s would have looked defensible from the VPS number alone and would have broken the office deploy. 120s is 2.1x the office measurement and 36x the VPS one. The upper bound is the `--pool=solo` worker (docker-compose.yml:455): a 300s classify blocks sleep-cycle consolidation, memory-backfill-drain, agent-gateway-sweep and dream-tick for five minutes, and post-fix a 300s classify can only mean something is already wrong.

`SKILL_SYNTH_TIMEOUT_SECONDS` 300 -> **120**. This one is an inference, and I am flagging it as the number I am least sure of. Basis: dreams measured 22.5s native for a few-hundred-token JSON on the same qwen3:4b/4-vCPU box (config.py:195), and a skill card is ~300-500 content tokens, so ~25-45s native on the VPS; scaling the office deploy's 56s classify by output length suggests 60-90s there. 120s holds 2.5-5x on the VPS and roughly 1.3-2x on office. It also caps the fan-out stall: N drafts x 300s is a 20-minute worker outage for a 3-procedure document, N x 120s is under 6. Measure one real draft on the office deploy before tightening further.

`DECISION_SYNTH_TIMEOUT_SECONDS` 20 -> **30**. Not taste — 30 is simultaneously the client's stated assumption and the client's hard ceiling. `client/firekeep_client/decision/server.py:50-55` sets `_DEFAULT_SYNTH_TIMEOUT = 30.0` with the comment "Kept env-tunable to mirror the server default", plus `_INGEST_TIMEOUT_HEADROOM = 15.0`, giving the client a 45s budget. The server default is 20.0 (config.py:133), so the two already disagree; 30 aligns them. The 45s client budget must also cover up to 9 sequential recalls, but those are ~10ms each ("9.8ms" per config.py:161), so ~30s is what is actually available. Do not go past 30 without a coordinated client release. Note honestly that 30s may still not be enough for 8 questions of suggestions on CPU — the real lever there is bounding output via `num_predict`, not raising a timeout the client will cut off anyway.

`DREAM_SYNTH_TIMEOUT_SECONDS` 45 -> **unchanged**. It was measured at 22.5s against the native path with 2x headroom, and config.py:205-216 already says in as many words that the number is right for `/api` and that "pointing LLM_BASE_URL at /api restores the measured 22.5s path". The fix makes 45 correct again rather than aspirational.

Hardcoded timeouts (`rag.py:191` 30.0, `rag.py:1041`/`main.py:585` 15.0, `mcp_server.py:314` 60.0, `sleep_cycle.py:390` 120.0, `memory_agent.py:275` 60.0) — **unchanged**. The first two guard features that are off by default; changing numbers on code paths this round does not convert is churn.

DISCOVERED IN PASSING, NOT IN THE AUDIT SCOPE: `sleep_cycle.py:378-396` posts to `/v1/chat/completions` in JSON mode with `timeout=120.0` and, on `httpx.HTTPError`, sends the whole batch to the DLQ. On a thinking model needing ~289s that is a guaranteed timeout on every batch, every 60s beat tick, silently filling `{REDIS_STREAM_KEY}:dlq`. I did not measure this — the cheap confirmation is `GET /ops/queues` and reading `event_dlq`. If it is non-zero and climbing, this is a larger silent loss than the knowledge pipeline and should be promoted into phase 2. It needs a sync wrapper (`httpx.post`, not `AsyncClient`), which is why it is not in phase 1.

## Risks

- MOST LIKELY WAY TO BREAK THE ROLLOUT: omitting `"stream": False` on the native body. Ollama's /api/chat streams NDJSON by default; `resp.json()` then raises JSONDecodeError, which is not an httpx type and contains no 'model', so `_is_backend_unavailable` returns False and every ingest goes terminal `failed`. The repo's own working caller sends it (benchmarks/memory/bench/qa.py:90). Assert it in a unit test on the body builder.
- TEST BLAST RADIUS IS REAL AND UNDER-APPRECIATED. `tests/test_knowledge_classifier.py:51` patches `app.knowledge.classifier.httpx.AsyncClient`; `test_skill_synthesizer.py` and `test_decision_synthesize.py` follow the same module-scoped pattern. Moving the httpx call into `app/llm.py` makes every one of those patches stop intercepting — tests will attempt real network calls or fail confusingly. All of them must be repointed at the `app.llm` seam, or (better) the helper must be injectable so tests patch one place. Budget for this; it is the largest mechanical cost of the change.
- OLDER OLLAMA REJECTS `think`. The flag is comparatively recent. An older daemon may 400 the native body — turning a call that was merely slow into one that fails hard. This is precisely why the 4xx-demote-and-retry-once safety net is in the design and is not optional; without it, upgrading Ollama becomes a prerequisite of this fix.
- PROMPT/OUTPUT SEMANTICS MAY DRIFT. Ollama's native `format: "json"` and /v1's `response_format: {type: json_object}` both guarantee syntactic validity, but the prompts in classifier.py:69-89 and decision/synthesize.py:16-37 were tuned against the /v1 grammar's behaviour. Same model, same prompt, so the risk is low — but verify a real classification returns the expected `primary_type`/`procedure_titles` shape on the native path before trusting the pipeline end-to-end.
- TIMEOUT REDUCTIONS MUST NOT LAND WHERE THE NATIVE PATH DOES NOT ENGAGE. If a deployment's probe says not-Ollama (or LLM_BASE_URL lacks the /v1 suffix), classify stays at 289s and a 120s budget converts today's 11-seconds-of-margin success into a guaranteed timeout. Confirm the verdict on each target deploy — one curl against `{root}/api/version` — before or alongside shipping the config change.
- A FALSE-POSITIVE PROBE IS POSSIBLE IN PRINCIPLE. Something non-Ollama answering `/api/version` with a JSON `version` key would be treated as native and every call would fail. Mitigated by requiring both the 2xx and the JSON `version` key, by the 4xx retry, and by `LLM_NATIVE_CHAT=never`. Low likelihood, cheap escape hatch.
- THE SOLO WORKER'S LOAD PROFILE CHANGES SHAPE. Post-fix the fan-out drafts stop timing out and start actually running, so the worker does more real work per document — but at ~30s per draft instead of 300s. Net strictly better (a 3-procedure ingest goes from ~20 minutes of blockage to ~2), and `acks_late=True` (skill_synthesis.py:57-61) stays far inside Redis's default 3600s visibility timeout. Worth watching once rather than assuming.
- DIAGNOSTIC LOSS: with `think: false` the `reasoning`/`thinking` field is empty by design, so a future 'why did the model return nothing' investigation has less to look at. Keep the field on the normalised result object and log it (bounded) at DEBUG rather than discarding it.
- PARTIAL CONVERSION LEAVES A SPLIT-BRAIN CODEBASE. After phase 1, four converted sites use `app/llm.py` and seven still hand-roll `/v1`. That is the intended trade (blast radius over purity, per constraint 3), but it must be written down in cortex/CLAUDE.md with the phase plan, or the next agent will find the inconsistency and 'fix' it in one unreviewed sweep across sleep_cycle's DLQ semantics and rag.py's hot path.
- OUT OF SCOPE BUT ADJACENT: `classify_document` sends the whole document as the user message with no truncation, while the crawler admits pages up to `KNOWLEDGE_CRAWL_MAX_PAGE_BYTES=2000000`. Making classify fast makes it easier to hit the context ceiling on a large page. Not caused by this change; do not fix it here; do not be surprised by it.

## Rejected alternatives

- (a) TRY NATIVE FIRST, FALL BACK ON 404 — rejected as the primary mechanism, adopted only as a narrow 4xx safety net. As a detection strategy it makes a *generation* request the probe: on a slow CPU backend a wrong first guess can burn the full timeout before teaching you anything, which is the opposite of constraint 5. The 404 signal is also not clean in the field — a reverse proxy or gateway in front of Ollama can answer 405, 502, or an HTML 404 body, and some return 200 with an error payload. And to avoid paying that cost per call you must cache the verdict anyway, at which point you have built (c) with a far heavier probe. Retained ONLY for fast pre-generation 4xx (400/404/405/501) as an older-Ollama safety net, never for 5xx or timeouts.
- (b) AN EXPLICIT FLAG ALONE — rejected as the sole mechanism, adopted as a required component. Constraint 2 is explicit that the default path must get faster without operator action; a flag defaulting to `never` reaches nobody, and one defaulting to `always` 404s every vLLM/LiteLLM/OpenAI deploy, which constraint 1 rules out as worse than the bug. `LLM_NATIVE_CHAT=auto|always|never` therefore exists as the override on top of detection, not instead of it.
- (c) STARTUP PROBE, LITERALLY AT STARTUP — the probe endpoint is right, the timing is wrong. Cortex API, the Celery worker and beat are three separate processes (docker-compose.yml:220, :455, :574), so 'startup' means three probes anyway; and probing during lifespan couples app boot to LLM availability, so an Ollama that is slow to come up degrades the whole service's start. Lazy-on-first-use with a TTL cache gives the same one-probe-per-process economics without the boot coupling, and re-probes after a restart of the backend instead of pinning a verdict for the process lifetime.
- (d) `/api/tags` AS THE PROBE — rejected in favour of `/api/version`, though the /v1-suffix derivation from this option IS adopted (it is required regardless, since you cannot construct a native URL without it). `/api/tags` returns the full model inventory, a much larger body for a question that only needs a yes/no. The 'it also tells you whether the model exists' argument is already served elsewhere: `dreams/task.py:339-356` probes `/models` and checks the configured model against the listing, deliberately leniently. Conflating liveness detection with model-availability checking in one call would put a second failure mode into the endpoint decision.
- (e) STRIP THINKING SOME OTHER WAY — rejected on this repo's own measurements, not on preference. The prompt-level route ('/no_think') is chat-template- and build-specific, i.e. exactly the model-dependence the endpoint fix avoids, and it would need re-validating per model. The bigger-budget route was already tried and documented: `dreams/synthesize.py:36-71` raised `_MAX_COMPLETION_TOKENS` from 700 to 4000 and records the outcome — the reasoning is GENERATED regardless, so the budget buys correctness at full wall-clock cost, and its own comment at :61-70 admits this raises worst-case latency and names pointing at /api as the real fix. The model-choice route means telling every customer to abandon thinking models. None of these approach the measured 87x, and none are endpoint-level, so none are model-independent.
- REPOINTING `LLM_BASE_URL` TO THE NATIVE ROOT — the tempting one-liner, disproven by grep. Eleven chat sites and three embedding sites concatenate their own suffix onto it (`db/vector.py:875`, `:954`, `workers/reembed.py:29` for embeddings alone). Repointing breaks every embedding write. Worth stating explicitly because config.py:214 currently *recommends* it as the fix for the dreams timeout, which is safe advice only for a deployment where nothing else uses that variable — i.e. no deployment.
- CONVERTING ALL 11 CALL SITES IN ONE CHANGE — rejected on blast radius, which constraint 3 asks to be weighed rather than assumed away. Seven of the eleven are either off by default (rag synthesis, rerank, dreams x2), structurally different (sleep_cycle and memory_agent use sync `httpx.post` and sleep_cycle's failure path writes the DLQ), or already degrade acceptably (mcp_server handoff returns raw recall text). Converting them buys little and risks the hot recall path and the consolidation DLQ in the same release as the fix that matters.

## Implementation sketch

- STEP 0 — VERIFY BEFORE WRITING CODE. Re-run the 3.3s native probe and capture the FULL response body. Confirm three things from the wire, not from this design: that `format` and `think` are top-level siblings of `stream`; that the response is `{"message": {"content": ..., "thinking": ...}, "done": true}` as `benchmarks/memory/bench/qa.py:96` implies; and that `num_predict` lives inside `options`. Also run `curl {root}/api/version` on the VPS and record the exact body. Paste both into the new module's docstring — this repo's convention is that measurements live next to the code they justify (see dreams/synthesize.py:36-71).
- STEP 1 — `cortex/app/llm.py`. Pure functions first, so they are testable without a network: `native_root(base_url) -> str | None` (require and strip a trailing `/v1`, tolerate a trailing slash, return None otherwise); `build_native_body(...)` and `build_openai_body(...)`; `parse_native_response(data) -> (content, thinking)` and `parse_openai_response(data) -> (content, reasoning)`. The OpenAI builder emits ONLY standard OpenAI fields — no `think`, no `chat_template_kwargs`.
- STEP 2 — detection. `async def _is_native(settings) -> bool`: honour `LLM_NATIVE_CHAT` (`always` -> True if a root is derivable or `LLM_NATIVE_BASE_URL` is set, else WARN once and False; `never` -> False); otherwise consult the module-level cache `{base_url: (verdict, expires_at)}`, and on miss `GET {root}/api/version` with a dedicated 2.0s timeout, accepting only 2xx + JSON object containing `version`. Positive TTL `LLM_NATIVE_PROBE_TTL_SECONDS` (600), negative TTL `min(60.0, ttl)`. Export `reset_probe_cache()` for tests. Add a comment stating that the absence of an asyncio.Lock is deliberate: the Celery solo pool runs a fresh event loop per task and a module-level Lock binds to the first loop that acquires it.
- STEP 3 — the entry point. `async def chat(*, settings, messages, timeout, json_mode=False, temperature=None, max_tokens=None, client=None, purpose='') -> ChatResult` where `ChatResult` is a frozen dataclass `{content, reasoning, endpoint, raw}`. It picks the endpoint, posts, calls `raise_for_status()`, and normalises. It RAISES on transport/HTTP failure — no swallowing, no silent substitution of `reasoning` for `content`. On a native 400/404/405/501 it demotes the cached verdict and retries once against `/v1`; on 5xx or timeout it re-raises unchanged. Log the verdict once per process at INFO when first computed.
- STEP 4 — config. Add `LLM_NATIVE_CHAT: str = 'auto'`, `LLM_NATIVE_PROBE_TTL_SECONDS: float = 600.0`, `LLM_NATIVE_BASE_URL: str = ''` to `cortex/app/config.py` near the LLM block (line 46-49). Per the repo's Change Consistency Checklist, mirror them into `docker-compose.yml` (cortex-api, cortex-mcp, worker, beat — the same four services that already receive `KNOWLEDGE_CLASSIFY_TIMEOUT_SECONDS`), `.env.example`, and the config tables in `cortex/CLAUDE.md` and the root `CLAUDE.md`.
- STEP 5 — convert `classifier.py`. Replace the `httpx.AsyncClient` block at :106-120 with one `llm.chat(..., json_mode=True, temperature=0.1, timeout=...)` call. DELETE the reasoning fallback at :126-127 and say why in a comment (under JSON mode an empty content means the grammar blocked it, so `reasoning` is prose by construction — it can never be the JSON). Keep the outer try/except and the returned dict shape byte-identical.
- STEP 6 — fix the mislabelling in `_is_backend_unavailable` (classifier.py:53-67), in the SAME release. Remove the bare `httpx.TimeoutException` from the isinstance tuple at :60 and keep `ConnectError` + `ConnectTimeout` (note `ConnectTimeout` subclasses `TimeoutException`, so it must be named explicitly or it is lost). A `ReadTimeout` then falls to the `failed` branch with a concrete reason instead of claiming 'generation backend unavailable ... will run automatically once a generation model is deployed' about a backend that is deployed and answering. Consider a distinct `timed_out` status if the dashboard can render one; otherwise `failed` with the reason is already a large improvement.
- STEP 7 — convert `synthesizer.py` `_call_llm_doc` (:320-336) and `_call_llm` (:307-318) to the helper with `json_mode=False`. Add an explicit `max_tokens`/`num_predict` sized to a skill card (~800) — these two are the only converted sites with no output bound at all today. Leave `_embed` (:354-364) untouched: it is not a chat call, embeddings do not reason, and `db/vector.py` is the hottest and most fragile path in the system.
- STEP 8 — timeouts, same release as steps 5-7. `KNOWLEDGE_CLASSIFY_TIMEOUT_SECONDS` 300.0 -> 120.0 (config.py:121) and `SKILL_SYNTH_TIMEOUT_SECONDS` 300.0 -> 120.0 (config.py:289), each with a comment carrying its measurement AND naming the office deploy's ~56s llama3.2:3b classify as the binding lower bound — otherwise the next reader sees 3.3s and tightens to 30. Update the `${...:-300}` defaults in docker-compose.yml (:272, :421, :323, :489) and `.env.example` to match; a stale compose default silently overrides the code default.
- STEP 9 — tests. New `cortex/tests/test_llm.py`: native-root derivation (with/without /v1, trailing slash, path-prefixed proxy); probe caching (one probe for N calls, positive vs negative TTL, per-base_url keying); `stream: False` present in every native body; no `think`/`chat_template_kwargs` in any OpenAI body; response normalisation for both shapes; the 4xx-demote-retry; and that a 5xx or timeout propagates. Then repoint the existing patches: `test_knowledge_classifier.py:51` and siblings currently patch `app.knowledge.classifier.httpx.AsyncClient`, which will no longer intercept — patch the `app.llm` seam instead. Do not change any assertion about the returned dicts; those are the contract that proves the conversion is behaviour-preserving.
- STEP 10 — verify on the VPS before phase 2. Ingest one known multi-procedure document. Expect: classify seconds not minutes; `GET /knowledge/sources` reporting `classified` with `skills_queued=N`; and N drafts actually appearing in the review queue. That last one is the whole point — today the endpoint reports 'classified, 3 skills queued' next to a permanently empty queue.
- PHASE 2 (separate change). (a) Convert `decision/synthesize.py:74-96`, raise `DECISION_SYNTH_TIMEOUT_SECONDS` 20.0 -> 30.0 (config.py:133) to match what `client/firekeep_client/decision/server.py:53` already assumes, bound the output with `max_tokens`, and FIX THE SILENT-SUCCESS BUG: `_llm_suggest`'s `except Exception: return {}` at :101-103 makes every non-timeout failure return an empty dict with no exception, so `synthesize_board` reports `degraded=False, note=''` on a board that produced nothing. It must signal failure to its caller (raise, or return a sentinel) so `:137-139` sets `degraded=True`. `tests/test_decision_synthesize.py:59-72` patches `_llm_suggest` out entirely, so this path is currently untested — add the test with the fix. (b) Check `GET /ops/queues` for `event_dlq`; if it is non-zero and climbing, add a sync `chat_sync()` wrapper (`httpx.Client`) and convert `sleep_cycle.py:378-391`, whose 120s budget against a ~289s call would be DLQ-ing every consolidation batch every 60s.
- PHASE 3 (separate change, lowest urgency since `DREAM_ENABLED=false`). Convert `dreams/synthesize.py` and `dreams/profile.py` to the helper: `build_request_body` (:119-132) disappears into `llm.chat`, with `profile.py:250`'s `response_format` override becoming `json_mode=False`. Reduce `_MAX_COMPLETION_TOKENS` from 4000 on the native path — with `think: false` honoured, 4000 no longer buys headroom, it only permits a runaway. `DREAM_SYNTH_TIMEOUT_SECONDS` stays 45.0. Rewrite the config.py:205-216 caveat and the synthesize.py:1-19 docstring: they currently instruct the reader to repoint `LLM_BASE_URL`, which this change makes both unnecessary and (per the embeddings grep) actively harmful advice. `tests/test_dreams_synthesize.py:16,108` assert the flags on the body and will need rewriting against the new builders.
- DOCUMENTATION (do not skip — the audit's own note 1 is that this knowledge already existed in one file and the other modules 'did not get the memo'). Add an 'LLM endpoint selection' subsection to `cortex/CLAUDE.md` and the root `CLAUDE.md` covering: the 87x measurement, why `/v1` ignores the flags, the auto/always/never contract, the probe and its caching, the phase plan naming which call sites are converted and which are deliberately not, and the fact that repointing `LLM_BASE_URL` is NOT a valid workaround because embeddings ride the same variable.
